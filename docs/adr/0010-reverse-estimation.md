# ADR-0010: 逆算(調整推定)の探索空間・型の定義・一致度

- 状態: 採用(§3 は P1-11 で改訂。**§3.1・§3.3(想定ダメージ幅の対象)・§4〜§7 は P1-12 で §R に置き換え**

- 日付: 2026-09-21(§3 を P1-11 で改訂: 観測%と表示%を別概念に分離 / P1-12 で探索空間・結果の形・Recall を再設計)
- 関連: P1-8、P1-11、docs/requirements.md「調整の推定(逆算)」、docs/test-strategy.md「逆算(調整推定)のテスト」、
  api/openapi.yaml(`/api/calc/reverse`、`ReverseRequest` / `ReverseCandidate`)、
  ADR-0005(データ駆動の効果定義)、ADR-0009(一括計算のプリセット)、
  CLAUDE.md 絶対ルール2(engine は純粋)・絶対ルール6(テストを弱めない)・
  ドメイン規約(逆算は engine 内の総当たり探索 / 持ち物・技・ポケモンをハードコードしない)

## 背景

要件は「実際のダメージから相手の調整候補を複数挙げる。正確さより候補の提示を優先」
「候補は『無振り』『HB特化』などの名前付きの型にまとめ、一致度の高い順に表示」
「同じ相手の観測を複数入力すると候補を絞り込める」を求める。

test-strategy は合格基準を **Recall@5: 1回観測 ≥80%、2回観測 ≥95%(全ポケモンから固定シード1,000ケース)**
と定めている。この基準は絶対ルール6により緩めない。

未決だったのは次の4点で、本 ADR がそれを決める。

1. 何を総当たりするのか(探索格子の次元と範囲)
2. 格子点をどう「型」に畳み込むのか(バケット規則・命名・事前順位)
3. 一致度をどう定義し、どう全順序にするのか
4. Recall の分母、つまり「正解」とは何か

## 決定

### 1. engine の純粋関数 `CalcReverse`。`CalcDamage` の合成にすぎない

`engine/reverse.go` に `CalcReverse(ReverseInput) (ReverseResult, error)` を置く。

- 独自のダメージ式を書かない。格子点ごとに `CalcDamage` を呼び、その 16 ロールを観測と突き合わせるだけ。
  `engine/damage.go` は変更しない(ゴールデン `make test-golden` への影響を作らない)。
- 時刻・乱数・ファイル・DB を触らない。同じ入力からは常に同じ結果(順序を含む)を返す。
- 格子は小さい(§4)ので WASM でも同期実行できる。

### 2. 両側を対称に扱う(`Side`)

| `Side` | 観測の意味 | 未知側 | 逆算する関連ステータス |
|---|---|---|---|
| `defender` | 自分が**与えた**ダメージ(相手 HP の減少) | 相手の防御側 | H と B(物理)/ D(特殊) |
| `attacker` | 自分が**受けた**ダメージ(自分 HP の減少) | 相手の攻撃側 | A(物理)/ C(特殊) |

- 既知側は `Known Individual`(解決済みの個体)、未知側は `UnknownSpecies Species`(種族だけ)で渡す。
  未知側の SP・性格・持ち物は探索対象なので、呼び出し側は渡さない。
- 関連ステータスは技の分類で決まる。`physical` → 防御側 `def` / 攻撃側 `atk`、
  `special` → `spd` / `spa`。`status`・未知の分類は `physical` と同じ扱いにする
  (変化技はダメージ 0 なので候補の順序は事前順位だけで決まる。エラーにはしない)。
  **追記(2026-09-25、issue #317・ADR-0117 §3)**: 変化技・威力 0 の技、および全候補でダメージが 0 になる
  入力(相性・特性の無効)は、候補を返さず `ErrMoveDealsNoDamage`(境界では `invalid_input`)にした。
- `Side=attacker` のとき、観測 % の分母は**既知側(自分)の実 HP** で一意に定まる。
  `Side=defender` のときの分母は**候補ごとに変わる**(H の振りが未知だから)。
  この非対称性が逆算の情報源そのものなので、%の分母は必ず「その候補の防御側実 HP」を使う。

### 3. 「観測%」と「表示%」を別概念にする(P1-11 で分離)

%は2種類ある。**同じ関数に混ぜない**。名前で取り違えられないようにする。

| 概念 | 何のため | 精度 | 丸め | engine の名前 |
|---|---|---|---|---|
| **観測%** | 逆算の入力。プレイヤーが実機画面から読み取った値との照合 | 整数% | round-half-up(**仮定**) | `ObservedPercent(damage, maxHP) int` |
| **表示%** | アプリが画面に出す値 | 小数第1位(0.1%) | 最小側=切り捨て / 最大側=四捨五入 | `DisplayPercentTenthsFloor` / `DisplayPercentTenthsRound` |

#### 3.1 観測%(逆算の入力。P1-11 では挙動を変えない)— **P1-12 で §R2 に置き換え(`ObservedPercent` は削除)**

`Observation` は `Percent`(ゲーム表示の整数%)または `Damage`(HP の実点数)の**どちらか一方**を持つ。
両方指定・両方未指定・0以下・`Percent > 100` は `ErrInvalidObservation`。

観測%の丸めは **round-half-up の整数%** と仮定し、整数演算1関数に閉じ込める。

```
ObservedPercent(damage, maxHP) = (damage*200 + maxHP) / (2*maxHP)   // = floor(100*damage/maxHP + 0.5)
                                 maxHP <= 0 は 0
```

- **これは仮定である。**ポケモンチャンピオンズの実機が切り捨て表示なのか四捨五入なのか、
  小数第1位まで出るのかは未確認(plan.md ブロッカー「観測ダメージの入力と丸め」。**人間の確認待ち**)。
  確認が取れたらこの1関数と本節だけを差し替える。丸め規則そのものの再設計は **P1-12**。
  engine の float 禁止規約に合わせ、丸めは整数演算のみで行う(`Percent` も engine では `int`)。
- P1-11 の変更は**改名だけ**(旧 `DisplayPercent` → `ObservedPercent`)。式・戻り値・照合結果は同じで、
  Recall@5 の基準(§7)も変えない。改名する理由は、表示%が 0.1% 精度になったことで
  `DisplayPercent` という名前が「画面に出す値」と読めてしまい、逆算の照合に 0.1% 値が
  紛れ込む事故が起きやすくなるため。
- 実装は `Percent` を `int` で持つ。OpenAPI の `observedPercent` は `number` なので、
  P3-1 の calc-svc が「整数でなければ 400」を課して `int` に写す(§9)。
- `Damage` 観測は完全一致(ロールの実点数が一致)で判定する。

一致・不一致の距離はすべて**観測%ポイント**(整数)に揃える。`Damage` 観測の距離は
`max(1, |roll - Damage| * 100 / HP)`(整数除算。`|roll - Damage| = 0` のときだけ 0)で%ポイントに換算する。
下限 `1` を置く理由: 点数差があるのに整数除算で `差*100/HP = 0`(HP が大きいと差 1〜2 で起きる)になると
dist=0 = Exact 扱いになり、「dist=0 のときだけ 1.0」「Exact ⇔ MatchScore==1.0」(§6.1, §6.2)が壊れるため。

#### 3.2 表示%(アプリが画面に出す値。P1-11 で追加)

requirements.md §2 のとおり、アプリが表示するダメージ%は**小数第1位**(例 73.4%)。
HP 比率から直接求め、整数%に丸めてから表示しない。float でダメージ%を近似しない
(CLAUDE.md ドメイン規約)ので、**engine は 0.1% 単位の整数(tenths)を返す**。
小数にするのは境界(`engine/wasmapi` の DTO、API の JSON)だけ。

```
DisplayPercentTenthsFloor(damage, maxHP) = damage*1000 / maxHP                 // 切り捨て。最小側
DisplayPercentTenthsRound(damage, maxHP) = (damage*2000 + maxHP) / (2*maxHP)   // 四捨五入。最大側
    どちらも damage <= 0 または maxHP <= 0 のときは 0
```

- **戻り値の単位は 0.1%**。`734` は `73.4%`。関数名に `Tenths` を入れるのは、
  `int` の値が%そのものだと読み違えると 10 倍ずれるため。
- **最小側は切り捨て、最大側は四捨五入**(ユーザー決定。DECISIONS.md 2026-09-21 (4))。
  「最低これくらい入る」を保守的に示すのが目的なので、下限を切り上げない。
  上限は「最大でどこまで届くか」なので、切り捨てて過小に見せず四捨五入する。
  したがって `Floor(d,h) <= Round(d,h) <= Floor(d,h)+1` が常に成り立つ。
- **どちらの関数を使うかを間違えないよう、正規の入口は範囲を返すメソッドにする**:
  `func (r DamageResult) DisplayPercentRangeTenths() (minTenths, maxTenths int)`
  = `(Floor(Rolls[0], DefenderHP), Round(Rolls[15], DefenderHP))`。
- **境界**:
  - `maxHP <= 0` は 0(ゼロ除算しない)。engine は純粋関数で panic しない。`ObservedPercent` と同じ扱い。
  - `damage <= 0` は 0。engine は負のダメージを作らないが、Go の整数除算は 0 方向に丸めるため
    負値では floor の意味が壊れる。定義域全体で floor を成立させるために 0 で止める。
  - `damage > maxHP` は **100 を超えた値をそのまま返す**(例 `1370` = 137.0%)。上限で切らない。
    根拠: 現行の `DisplayPercent` も切っていない(挙動を変えない)。加えて、過剰打点の大きさは
    「確定1発だがどれだけ余裕があるか」の判断材料で、100% に丸めると情報が消える。
    画面が「100%で頭打ち」に見せたいなら、それは表示層の判断であって engine の値ではない。
- **既知の帰結(特別扱いしない)**: `rolls[0] == rolls[15]`(乱数幅が無い)のとき、
  最小側と最大側で丸めが違うので表示が 0.1 ずれることがある(例 HP16・1ダメージ固定 →
  `6.2% 〜 6.3%`)。ここで「同じ値なら同じ丸め」の例外を入れると、ダメージ 1〜1 と 1〜2 で
  規則が切り替わる不連続ができ、規則が1行で説明できなくなる。最小側は常に保守的、
  最大側は常に四捨五入、で通す。実ダメージ(`minDamage` / `maxDamage`)も併せて返すので
  情報は失われない。気になるなら表示層が「1ダメージ(6.2%)」と畳めばよい。

#### 3.3 逆算候補の想定ダメージ幅も表示%にする — **P1-12 で §R2・§R3 に置き換え**

(この節は P1-11 時点の決定。P1-12 で候補が代表点1つではなく SP の範囲(`Ranges`)を返す形に
変わったため、以下の「代表点の」「観測%のまま」は成り立たない。§R3 のとおり
`MinPercentTenths` / `MaxPercentTenths` は**代表点ではなく `Ranges` 全体の幅**になり、
候補の照合に使う値も `ObservedPercent`(round-half-up 仮定)ではなく **§R2 の区間モデル
(`Observation.Matches` / `Distance`)** に置き換わった。フィールド名は変わらない。)

`ReverseCandidate` の想定ダメージ幅は画面に出す値なので、表示%(0.1% 単位)で持つ。
フィールド名も単位が分かる形にする: `MinPercentTenths` / `MaxPercentTenths`
(= 代表点の `DisplayPercentRangeTenths()`)。

理由: JSON のキー `minPercent` / `maxPercent` は計算結果(`CalcResult`)と逆算候補の両方に出る。
片方が整数%、もう片方が 0.1% だと、同じキー名が2つの尺度を指すことになり §3 の分離が
契約の側で崩れる。**`minPercent` / `maxPercent` はどこでも同じ意味(表示%)**に揃える。

一方、**候補の照合に使う値は観測%のまま**(`ObservedPercent`)。CalcReverse の内部で
16ロールを観測%へ写して距離を測る部分(§6)は P1-11 で変更しない。
P1-12(逆算の再設計。結果は SP の範囲)で候補の持ち物・形は作り直すので、
P1-11 側の変更は「単位と名前を表示%へ合わせる」だけに留める。

#### 3.4 確定数の確率(`ko.chancePercent`)を必ず表示できる形にする

`engine.KOChance` の生値(ADR-0006)は、**確定(`Guaranteed`)のとき `ChancePercent` が 0**、
倒せないとき(`Hits == 0`)も 0 である。これをそのまま画面に出すと「確定n発なのに 0%」になる。
ゴールデンの期待値がこの生値に依存している(`tools/golden/generate.mjs` が確定時に
`ChancePercent: 0` を書く)ので、**生値の意味は変えない**。代わりに engine に表示用の
メソッドを1つ足す。

```
func (k KOChance) DisplayChancePercentTenths() int   // 0.1% 単位
    Hits == 0(倒せない)      -> 0
    Guaranteed                  -> 1000   (= 100.0%)
    それ以外                    -> round(ChancePercent * 10) を [1, 999] に収める
```

- 精度は表示%と揃えて小数第1位。
- `[1, 999]` に収めるのは、`0.0%` を「不可能」、`100.0%` を「確定」に予約するため。
  確率 0.04% が `0.0%`、99.98% が `100.0%` と出ると、確定/不可能と区別できなくなる。
- `ChancePercent` は確率であってダメージ%ではないので、engine が既に float64 で持っている
  (ADR-0006)値をそのまま丸めてよい。ダメージ%の float 禁止はここには当たらない。
- 生値も境界には残す(`ko.chancePercent`)。画面が使うのは `ko.displayChancePercent`。

### 4. 探索格子(総当たり)— **P1-12 で §R1 に置き換え**

未知側の関連ステータスの SP を全格子で列挙し、性格クラス3種と持ち物候補を掛ける。

| `Side` | 格子 | 点数 |
|---|---|---|
| `defender` | H の SP 0..32 × B(D)の SP 0..32 × 性格クラス3 | 33 × 33 × 3 = 3,267 |
| `attacker` | A(C)の SP 0..32 × 性格クラス3 | 33 × 3 = 99 |

- SP 合計上限 66 は 32+32=64 なので格子全体が常に合法。実数値は既存の `RealStats` に任せ、
  逆算側で実数値の式を再実装しない。
- 性格クラスは**関連ステータスへの効果**で3種に畳む。下降側(`Minus`)は結果に影響しない代表値を置く。

  | クラス | 代表 `Nature`(関連ステータスが `def` の例) |
  |---|---|
  | `plus` | `{Plus: def, Minus: atk}` |
  | `neutral` | `{}`(無補正) |
  | `minus` | `{Plus: atk, Minus: def}` |

  相手側の `atk` / `spa` はこの計算で使われないため、`Minus` の置き方は結果を変えない。
  関連ステータスが `atk` のときだけ相手方を `spa` にする(HP には補正を掛けられない)。
- **持ち物候補は引数**(`ItemCandidates []*Item`、解決済み。`nil` 要素は「持ち物なし」)。
  engine に持ち物一覧を持ち込まない(ADR-0005 / ADR-0009 と同じ方針)。
  `nil` / 空スライスのときは `[]*Item{nil}` と同じ(持ち物なしの1通り)。
- **特性は未知側ゼロ値固定**。格子に入れない(§8 の限界)。
- ランクは 0、状態異常は `none`、レベルは 50 固定。場・急所・技・既知側は全観測で共通。

#### 実装上の注意(性能)

16 ロールは観測の数によらず同じなので、`CalcDamage` は**格子点 × 持ち物ごとに1回だけ**呼び、
観測の突き合わせはその結果を使い回す。観測ごとに呼び直すと多観測で線形に遅くなる。

### 5. 型(Archetype)= 格子の畳み込み単位 — **P1-12 で廃止(§R6)**

#### 5.1 バケット規則

SP を3つのバケットに畳む。

| バケット | SP |
|---|---|
| `none` | 0 |
| `mid` | 1..31 |
| `full` | 32 |

型 = (H のバケット × 関連ステータスのバケット × 性格クラス)。
`Side=attacker` では H の次元を持たない。したがって型の数は
**defender 27・attacker 9**(持ち物候補を掛けたものが候補の数)。

この規則は**全単射的な全射**である。どの格子点もちょうど1つの型に属し、どの型も空でない。
Recall の分母(§7)はこの写像で定義する。

#### 5.2 キーとラベル

**キーは構造そのもの**とする。ADR-0009 のプリセット enum には依存させない。

```
defender: h<HPバケット>-<統計文字><バケット>-<性格クラス>   例 hfull-bnone-plus
attacker: <統計文字><バケット>-<性格クラス>                例 afull-plus
```

統計文字は `atk`→A、`def`→B、`spa`→C、`spd`→D。

ラベル(表示名)は要件の「名前付きの型」に対応する日本語名で、よく使う8型は固定表(§5.3)、
残りは次の生成規則で作る。

```
部品 = [ H部, X部, 性格部 ] のうち空でないもの
  H部    : none → (なし) / mid → "H中間" / full → "H振り"     (Side=attacker では常になし)
  X部    : none → (なし) / mid → "<X>中間" / full → "<X>振り"
  性格部 : plus → "<X>補正" / neutral → (なし) / minus → "<X>下降"
ラベル = 部品を "+" で連結。部品が空なら "無振り"
```

例: `hfull-bmid-plus` → 「H振り+B中間+B補正」、`hnone-bnone-minus` → 「B下降」、
`amid-neutral` → 「A中間」。

**ADR-0009 の `hb_boost` / `hd_boost` は人間の確認待ちなので、
本 ADR はその定義に依存しない**。ラベルが偶然一致していても、型の同一性はキー(構造)側にある。
ADR-0009 の定義が変わっても、変えるのはラベルの対応表だけで、バケット規則も Recall の分母も動かない。

#### 5.3 事前順位(カタログ順)

同点のタイブレークに使う決定的な事前順位。**実際の対戦で使われやすい順**に並べる。

defender(X = B または D):

| 順位 | H | X | 性格 | キー例 | ラベル |
|---|---|---|---|---|---|
| 0 | none | none | neutral | `hnone-bnone-neutral` | 無振り |
| 1 | full | none | neutral | `hfull-bnone-neutral` | H振り |
| 2 | full | none | plus | `hfull-bnone-plus` | H振り+B補正 |
| 3 | full | full | plus | `hfull-bfull-plus` | HB特化 |
| 4 | full | full | neutral | `hfull-bfull-neutral` | HB振り(無補正) |
| 5 | none | full | plus | `hnone-bfull-plus` | B特化(H無振り) |
| 6 | none | full | neutral | `hnone-bfull-neutral` | B振り(無補正) |
| 7 | none | none | plus | `hnone-bnone-plus` | B補正のみ |
| 8.. | 残り19型 | | | | 生成ラベル |

8 以降は次の入れ子順で、既出を飛ばしながら並べる:
`H ∈ [full, none, mid]` × `X ∈ [full, none, mid]` × `性格 ∈ [plus, neutral, minus]`。

attacker(X = A または C):

| 順位 | X | 性格 | キー例 | ラベル |
|---|---|---|---|---|
| 0 | none | neutral | `anone-neutral` | 無振り |
| 1 | full | plus | `afull-plus` | A特化 |
| 2 | full | neutral | `afull-neutral` | A振り(無補正) |
| 3 | none | plus | `anone-plus` | A補正のみ |
| 4.. | 残り5型 | | | 生成ラベル |

4 以降は `X ∈ [full, none, mid]` × `性格 ∈ [plus, neutral, minus]` の順で既出を飛ばす。

上位 0〜7(attacker は 0〜3)は「SP を 0 か 32 のどちらかに振り、性格は無補正か上昇補正」
という**現実的な調整**の全組合せであり、これが §7 の真値の母集団と一致する。
事前順位が実質的な事前分布として働くことは意図した設計であり、隠さない(§8)。

### 6. 一致度と順序 — **P1-12 で §R3・§R4 に置き換え**

#### 6.1 格子点の一致度

格子点 g と観測 o について、g の 16 ロールを**観測%**(§3.1 の `ObservedPercent`。整数%)に
直した集合を使う。ここは照合であって画面ではないので、表示%(0.1%)は使わない。

- `dist(g,o)` = ロールの観測%と `o` の値の差(絶対値、%ポイント)の**最小値**
- `near(g,o) = 1 / (1 + dist(g,o))` ∈ (0,1]。**`dist=0`(= 完全一致)のときだけ 1.0**
- `pointExact(g)` = すべての観測で `dist=0`

複数観測の合成:

- `pointNear(g) = mean_o near(g,o)`(相加平均)∈ (0,1]、**= 1.0 は全観測完全一致と同値**
- 乱数は観測ごとに独立に選ばれてよい(同じロールを引く必要はない)

#### 6.2 候補(型 × 持ち物)の一致度

```
MatchScore = max_{g ∈ 型}  pointNear(g)       ∈ (0,1]
Exact      = ∃ g ∈ 型 : pointExact(g)         ⇔ MatchScore == 1.0
```

max を取るのは「この型はその観測を説明できるか」を測りたいからである。
`ExactPoints`(完全一致した格子点数)と `Points`(型の格子点数)も返すが、**順序には使わない**(§6.4)。

代表 SP・代表性格は `MatchScore` を達成した格子点のうち、走査順
(H 昇順 → 関連ステータス昇順 → 性格 `plus`,`neutral`,`minus` の順)で**最初のもの**。
`MinPercentTenths` / `MaxPercentTenths` はその代表点の想定ダメージ幅を**表示%**(0.1% 単位)に
したもの(§3.3)。`rolls[0]` は切り捨て、`rolls[15]` は四捨五入。

#### 6.3 順序(全順序・決定的)

1. `MatchScore` 降順
2. 型の事前順位(§5.3)昇順
3. 持ち物候補の `ItemCandidates` 内の添字 昇順

2 と 3 で必ず一意に決まるので全順序になり、入力が同じなら順序も常に同じ。

#### 6.4 却下した一致度(実測で劣ったもの)

尤度 `∏_o (一致するロール数 / 16)` を主キーや第2キーに使う案を実測で比較した
(1,000ケース・防御側。表示が 100% を超える観測を**除外していた旧標本**での当時の測定):

| 順序 | 1回観測 Recall@5 | 2回観測 Recall@5 |
|---|---|---|
| `MatchScore` → 事前順位(**採用**) | 95.2%(952/1000) | 97.1%(971/1000) |
| `MatchScore` → 尤度 → 一致点率 → 事前順位 | 78.5% | 85.5% |
| `Exact` → 一致点率 → 尤度 → 事前順位 | 83.8% | 94.8% |
| `Exact` → 最大尤度 → 事前順位 | 35.2% | 41.5% |

採用行は旧標本・固定シード `0x50314238` で再現できる値。他の3行は却下時の測定値で、
現行の標本(§7 item 6 の 100% 丸め)では測り直していない。ただし採用案が現行標本でも合格していること
(§7 の実測)と、却下案の差が十分大きいこと(1回観測で 11〜60 ポイント)から、判断は変わらない。

尤度は「観測がどれくらい出やすいか」としては正しいが、**真値の観測は 16 ロールから一様に引かれる**ため、
真値の型でも珍しい%が出る。尤度で並べ替えると真値が沈む。
現実的な調整を上に置く事前順位のほうが、この問題設定では強い。

### 7. Recall@5 テストの真値(= 分母の定義)— **P1-12 で §R5 に置き換え**

test-strategy の手順を次のように具体化する。

1. **種族**: `testdata/golden/defense-species.jsonl.gz` に現れる全種族(1,392件)を
   `Key` 昇順に並べたもの。既存ゴールデンと同じ母集団を使い、逆算用に別の種族表を作らない。
2. **乱数**: xorshift64 を固定シードで自前に持つ。`math/rand` の実装差に依存させない。
   シードは `0x50314238` に固定する。**テストを通すためにシード・ケース数・しきい値を動かさない**
   (絶対ルール6)。基準に届かないときは §6.3 の順序規則のほうを直す。
3. **技**: タイプ18種 × 分類2種 × 威力 {60,80,90,100,120} から選ぶ代表技。
4. **既知側**: 現実的な調整(無振り、または関連ステータス 32 + 上昇補正)。
5. **真値(未知側)**: SP は 0 か 32、性格は無補正か上昇補正、持ち物は候補集合から。
   → §5.3 の上位8型(attacker は上位4型)のいずれかに必ず属する。
6. ダメージ 0・無効相性・観測 0% のケースは引き直す(観測にならないため)。
   **観測%が 100% を超えるケース(相手が瀕死になる)は除外せず、100 に丸めて分母に残す。**
   ゲームの HP バーは 100% で頭打ちなので現実に近く、基準も厳しくなる
   (これは**観測**側の話。engine が返す**表示%**は 100 を超えてもそのまま返す。§3.2)。
7. 16 ロールから一様に1段階を選び、`ObservedPercent` で観測化する。2回観測は独立に2段階選ぶ。
8. `CalcReverse` にかけ、**真値の型(`ArchetypeOf` が返すキー)と真値の持ち物 ID が一致する候補が
   上位5件に入った割合**を Recall@5 とする。

**「正解」は SP の完全一致ではなく型の一致である。** SP を当てるのではなく
「無振りか / H振りか / HB特化か」を当てるのが要件なので、分母もそれに合わせる。
`ArchetypeOf(side, category, sp, nature)` を公開し、テストと実装が同じ写像を使うことで、
分母の定義がテスト側にコピーされないようにする。

#### 実測(固定シード `0x50314238`・1,000ケース・全1,392種族)

| side | 1回観測 Recall@5 | 2回観測 Recall@5 | 基準 |
|---|---|---|---|
| defender | 92.9%(929/1000) | 95.6%(956/1000) | ≥80% / ≥95% |
| attacker | 95.0%(950/1000) | 95.5%(955/1000) | ≥80% / ≥95% |

(参考: 100% 超の観測を除外していた旧標本では defender 95.2% / 97.1%、attacker 100% / 100% だった。
100% への丸めで両側とも下がる。)

**2回観測の余裕は defender で 0.6 ポイント、attacker で 0.5 ポイントしかない。**
§6.3 の順序規則を1つでも変えると割り込むため、**順序規則は ADR とテストで固定し、実装の都合で変えない**。
attacker が旧標本より大きく下がる原因は、(仮説)強い攻撃側では観測が 100% に張り付き、
100% 観測が多くの型と両立して型を絞れないため。未検証。

### 8. 限界(いまは受け入れる)

- **特性を探索しない**。未知側の `Ability` はゼロ値固定。しんかのきせき相当を持ち物候補で代用できるが、
  ふしぎなうろこ・あついしぼう等は表現できない。格子に特性候補の次元を足せば拡張できる形にしておく。
- **複数観測は同じ技・同じ場・同じ既知側に限る**(API も `moveId` と `attacker` を1つしか持たない)。
  同じ分布から2回引くだけなので情報の増え方は小さく、2回観測の Recall が 1回観測から
  1〜2ポイントしか伸びないのはこのため。**技を変えた観測を混ぜられるようにするのが最も効く改善**だが、
  API 契約の変更を伴うので P3-1 以降で検討する。
- **事前順位が結果に効く**。同着の候補は「現実的な調整ほど上」という事前分布で並ぶ。
  Recall テストの真値も現実的な調整から引くので、テストは事前順位に有利に働く。
  これは「相手は普通の調整をしている」という実用上妥当な仮定を測っているのであって、
  「任意の SP を当てられる」ことは測っていない。数値を読むときはこの前提込みで読む。
  — **P1-12 で置き換え**: 型(Archetype)と事前順位そのものを廃止した(§R6)。新しい順序は
  `Mismatch` → `Support` → `SPCount` → 定義順(§R4)で、float の `MatchScore` も使わない。
  「区別できない候補は決め打ちしない」設計に変わったため、この限界は §R7 の限界に置き換わる。
- **観測 100% は「表示がちょうど 100%」として照合する**。「100% 以上(瀕死)」としては扱わない。
  相手が瀕死になる攻撃でも表示は 100% に頭打ちされ、そのときの真のダメージは分からないため、
  100% 観測は情報量が小さく候補が絞れにくい(§7 の attacker の実測低下)。
  — **P1-12 で置き換え**: 100% 観測の上側を開区間にした(`Matches` で `v == S ∧ x ≥ 0` なら
  100% 超のダメージとも両立する。§R2)。旧仕様は 100% 超の真のダメージを取りこぼしており、
  それが attacker の実測低下の原因と考えられていたもの(§R2 の該当段落)。
- **表示 % の丸めが仮定**(§3)。実機が切り捨てだった場合、1 ポイントずれて完全一致が消える観測が出る。
  — **P1-12 で置き換え**: 観測%の丸め規則(切り捨て/四捨五入/切り上げ)がどれであっても真値を
  落とさない開区間 (v−1, v+1) で照合するようにした(§R2)。したがって**表示%の丸めが何であっても
  この限界自体が解消**している。丸め規則が人間の確認で確定したら `Matches` の1か所を狭めるだけでよい
  (§R2 末尾の段落、および 2026-09-21 の追記を参照)。
- **急所・状態異常・ランクは観測側で指定する**(全観測共通)。相手のランク変化を推定はしない。
- **ダブル固有補正は未対応**(ADR-0005 と同じ範囲)。`Format` は `CalcDamage` に渡すだけ。

### 9. API 契約(`api/openapi.yaml`)との差分 — P1-8 では API を変更しない

今回は engine だけを作り、`api/openapi.yaml` は触らない。契約とのズレを以下に記録し、
**P3-1(calc-svc の実装)で解消する**。

| 契約 | engine | P3-1 での解消 |
|---|---|---|
| `Observation.observedPercent: number` | `Observation.Percent int`(観測%。§3.1) | calc-svc が整数でなければ 400。engine に float を渡さない |
| `Observation` に実点数の観測が無い | `Observation.Damage int` | `side=attacker` は自分の HP 減少を点数で知れるので契約に `observedDamage` を足す |
| `ReverseRequest.attacker: Individual` 固定 | `Known Individual`(`Side` により攻撃側/防御側) | `side=attacker` のとき `attacker` フィールドが「自分=防御側」を指す読み替えが必要。`known` へ改名するか `defender` を足す |
| `ReverseRequest.defenderSpeciesKey` 固定 | `UnknownSpecies Species` | 同上。`side` によって未知側が変わるので `unknownSpeciesKey` に寄せる |
| `ReverseRequest` に持ち物候補が無い | `ItemCandidates []*Item` | `itemCandidates: [ItemId]` を足す。解決は calc-svc(engine に持ち物一覧を持ち込まない) |

| `ReverseCandidate.rangePercent: [number,number]` | `MinPercentTenths` / `MaxPercentTenths`(0.1% 単位の int。§3.3) | calc-svc が 10 で割って小数第1位の number にする |
| 一致度の意味が未定義 | `MatchScore`(1.0 = 完全一致)+ `Exact` | `matchScore` の意味を description に書き、`exact` を足すか検討 |
| `ReverseResult` に候補数の上限が無い | `MaxCandidates`(0 = 無制限) | ページングは不要。`limit` を足すかは画面を見て決める |

## 却下・保留

- **逆算を calc-svc 側(engine の外)に置く**: WASM オフラインで逆算できなくなる。要件の
  「ブラウザ版はWASMでバックエンドなしでも計算可能」に反するので却下。
- **格子を現実的な調整だけに絞る(8型だけ探索する)**: 速いが「H に 12 振り」のような
  中間調整をまったく提示できなくなる。要件は「候補の提示を優先」なので全格子を残し、
  中間調整は `mid` バケットの型として下位に出す。
- **`CalcDamage` からロールだけを取り出す内部関数を切り出す**: `koProbability` が
  低ダメージ時に 86µs かかり、逆算の実行時間のほとんどを占める。切り出せば1桁速くなるが、
  `engine/damage.go` の変更はゴールデンへの影響を作らないと言い切れる形でレビューしたいので
  P1-8 では触らない。逆算の実行時間が問題になったら、ゴールデン全件一致を条件に別タスクで行う。
- **1回の逆算で技違いの観測を混ぜる**: 最も精度が上がるが API 契約の変更が要る(§8)。P3-1 以降。
- **特性候補の探索**: 格子が特性数倍になる。持ち物候補と同じ「引数で候補を受け取る」形にすれば
  足せるので、必要になってから足す。

## §R. P1-12 改訂: H32 前提の SP 範囲推定(§3.1・§4〜§7 を置き換える)

- 日付: 2026-09-21 / 関連: plan.md P1-12、requirements.md §2「調整の推定(逆算)」、DECISIONS.md 2026-09-21 (5)(6)
- 変わらないもの: §1(`CalcDamage` の合成・純粋関数)、§2(`Side` と関連ステータス)、§3.2・§3.4(表示%)、
  §8 のうち特性・技・場の限界、§9 の P3-1 への持ち越し(ただし中身は §R8 のとおり変わる)。
  **§3.3 は変わる**: P1-11 時点は「代表点の `DisplayPercentRangeTenths()`」「照合は観測%のまま
  (`ObservedPercent`)」だったが、P1-12 で候補が SP の範囲(`Ranges`)を返す形になったため、
  想定ダメージ幅は「代表点の幅」ではなく「`Ranges` 全体の幅」になり(§R3)、照合も `ObservedPercent`
  ではなく §R2 の区間モデルに置き換わった。

### 背景(ユーザー決定。未確定に戻さない)

1. 固定プリセット/型からの選択をやめる。防御側は **H32(HP SP=32)を前提**に B(D) の SP を 0..32 探索、
   性格は「B(D) 補正なし」「B(D) 上昇」の2通り。攻撃側も A(C) の SP 0..32 × 「補正なし」「A(C) 上昇」。
2. 結果は「性格補正あり/なし × 持ち物」ごとに、観測を説明できる **SP の範囲**。区別できない候補は決め打ちせず残す。
3. 「無振り」「HB特化」などの名前は目安として併記してよい(必須ではない)。
4. 同じ相手の観測を複数入力すると絞り込める。
5. 実機画面の観測%の丸め規則は表示%とは別概念で、**未確認**(plan.md ブロッカー)。
6. Recall を再設計し、基準(1観測 ≥80%・2観測 ≥95%)は緩めない。

### R1. 探索空間と候補

| `Side` | 未知側の SP | 性格クラス(定義順) | 候補の数 |
|---|---|---|---|
| `defender` | H = 32 固定、B(D) = 0..32 | `neutral`, `plus` | 2 × 持ち物候補数 |
| `attacker` | A(C) = 0..32(H は計算に使わない) | `neutral`, `plus` | 2 × 持ち物候補数 |

- 候補 = (性格クラス, 持ち物)。**全候補を必ず返す**(説明できない候補も §R3 の近い SP 付きで残す)。
- 代表 `Nature`: `neutral` = 無補正、`plus` = `{Plus: 関連, Minus: atk}`(関連が atk のときだけ `Minus: spa`)。
  下降補正(旧 `minus`)は探索しない(ユーザー決定)。`NatureClassMinus` は削除。
- `ReverseResult.AssumedHPSP` に仮定した H の SP を返す(defender = 32、attacker = 0)。
  画面が「H32 を仮定した結果」であることを明示できるようにするため。
- 持ち物候補は従来どおり引数(`nil` / 空は「持ち物なし」の1通り)。特性は探索しない(§8)。
- 1候補あたり `CalcDamage` を 33 回。格子は 33 × 2 × 持ち物(旧 3,267 × 3 × 持ち物の約 1/150)。

### R2. 観測の区間モデル(丸め規則に依存しない照合)

**観測は「精度付きの値」**として受ける。float は使わない。

```go
type Observation struct {
    Percent       int    // 整数%の観測(1..100)。精度 1%
    PercentTenths int    // 小数第1位の観測(1..1000。0.1% 単位の整数)。精度 0.1%
    Damage        int    // HP の実点数(> 0)。精度 1 点
    Note          string
}
func (o Observation) Matches(damage, maxHP int) bool   // 観測を説明できるか
func (o Observation) Distance(damage, maxHP int) int   // 説明できないときの距離(0 ⇔ Matches)
```

3つのうち**ちょうど1つ**を指定する(0 は未指定。それ以外・範囲外・負は `ErrInvalidObservation`)。

**照合の定義**(S = 100(Percent)/ 1000(PercentTenths)、v = 観測値、x = S·damage − v·maxHP):

```
Matches ⇔ |x| < maxHP                    // 真の値 p(同じ単位)が開区間 (v−1, v+1) に入る
       ∨ (v == S ∧ x ≥ 0)                // HP バーは 100% で頭打ち: 100% 観測は「99% 超」すべてと両立
Damage 観測: Matches ⇔ damage == D       // 実点数は完全一致(従来どおり)
maxHP <= 0: Matches = false(panic しない)
```

- **なぜ開区間 (v−1, v+1) か**: 切り捨て(v ≤ p < v+1)・四捨五入(v−½ ≤ p < v+½)・切り上げ(v−1 < p ≤ v)の
  どれで作られた観測でも真値が入る最小の区間が、この3つの和集合 = 開区間 (v−1, v+1) だから。
  「どれかの丸め規則で v になりうる」と**同値**(`TestObservationMatchesAnyRounding` が被覆と最小性の両方を固定)。
  広げすぎると情報を捨て、狭めるとどれかの規則で真値を落とす。
- **100% の頭打ち**: 実機では相手が瀕死になるとダメージは残り HP で止まり、表示も 100% を超えない。
  したがって 100%(100.0%)の観測の上側は開いている。旧 §8「観測 100% は表示がちょうど 100% として照合する」を改める
  (旧仕様は 100% を超える真のダメージを取りこぼした。§7 の attacker の実測低下の原因と考えられていたもの)。
- **規則が確定したら**: `Matches` の1か所(と `Distance` の両立判定)を差し替えるだけで区間を狭められる
  (例 切り捨てなら 0 ≤ x < maxHP)。テストは `oracleMatches`(3規則の和)を確定した規則に替えて同じ構造で検証できる。
- **精度の選択**: 精度はフィールドで表す(`Percent` か `PercentTenths`)。精度を別の enum にしないのは、
  値と精度の組み合わせ不整合(「0.1% 精度で 45」が 45% か 4.5% か)を型で起こせなくするため。
- **2026-09-21 のユーザー回答**: 実機の HP 減少は整数%で表示される(ユーザー確認)。丸め方
  (切り捨て/四捨五入/切り上げ)は未確認のため、上記のとおり区間は3規則の和のまま。
  確認できたら `Matches` の1か所で狭める(上記「規則が確定したら」)。

**距離**(説明できない候補の「近さ」。単位は 0.1%(最大 HP 比)の整数):

```
Percent       : 両立なら 0、それ以外 (|x| / maxHP) × 10
PercentTenths : 両立なら 0、それ以外 (|x| / maxHP)
Damage        : 一致なら 0、それ以外 max(1, 1000·|damage − D| / maxHP)
maxHP <= 0    : 1 以上(照合できないものを完全一致にしない)
```

- 両立しないとき |x| ≥ maxHP なので Percent/PercentTenths の距離は自動的に 1 以上。Damage は下限 1 を置く
  (HP が大きいと整数除算で 0 に落ち、「0 ⇔ 説明できる」が壊れるため。旧 §3.1 と同じ理由)。
- 単位を 0.1% に揃えるのは、観測の種類が混在しても距離を足せるようにするため。

### R3. 候補の範囲(結果の形)

```go
type SPRange struct{ Min, Max int }   // 両端を含む
type ReverseCandidate struct {
    NatureClass NatureClass // neutral / plus
    Nature      Nature      // 代表性格(構造値)
    Item        *Item       // 渡されたものをそのまま
    ItemID      string
    Ranges      []SPRange   // 昇順・互いに素・隣接しない(極大連続区間)。空にならない
    SPCount     int         // Ranges に含まれる SP の数
    Exact       bool        // Mismatch == 0
    Mismatch    int         // min_SP Σ_観測 min_ロール Distance(0.1% 単位)
    Support     int         // Ranges の各 SP で、各観測を説明できるロールの延べ数
    MinPercentTenths, MaxPercentTenths int // Ranges 全体での想定ダメージ幅(表示%。§3.3)
}
type ReverseResult struct {
    Side ReverseSide; Stat StatKey; AssumedHPSP int
    Candidates []ReverseCandidate; ExactCount int
}
```

- SP ごとの距離 `dist(sp) = Σ_観測 min_ロール Distance`(観測ごとに別のロールでよい。§6.1 と同じ)。
  `Mismatch = min dist`、`Ranges = {sp : dist(sp) == Mismatch}`。
  - `Exact`(Mismatch = 0)なら Ranges は「**全観測を説明できる SP の集合そのもの**」。広すぎも狭すぎもしない(厳密性)。
  - 説明できる SP が無ければ、距離最小の SP を返す(要件「正確さより候補の提示を優先」)。`Exact = false` で区別できる。
- **非連続は複数区間で返す**(1区間に畳まない)。ダメージは SP に単調だが、ロールが 2 点以上飛ぶ高ダメージでは
  「ある実点数を出せる SP」が飛び飛びになる(例: 威力150・A32上昇 → Damage 136 は B {17, 19..32})。
  1区間 [17,32] に畳むと、説明できない SP=18 を「候補」と偽って表示することになる。情報を捨てない方を選ぶ。
  画面が1区間で見せたいなら、`Ranges[0].Min`〜`Ranges[len-1].Max` を表示層で使えばよい(逆は復元できない)。
- `MinPercentTenths` / `MaxPercentTenths` は Ranges の全 SP について `DisplayPercentRangeTenths()` の
  最小/最大(代表点1つではなく範囲全体の幅。範囲を返すようになったので幅も範囲に合わせる)。
- 目安の名前(「無振り」「HB特化」)は **engine では付けない**(要件上任意)。範囲の端(0 / 32)と性格クラスから
  表示層(P4-4)が付けられる。engine に名前の規則を持つと、範囲が 0..32 に跨るときの命名という
  答えの無い規則を抱えることになるため。

### R4. 順序(決定的な全順序)

1. `Mismatch` 昇順(説明できる候補が先)
2. `Support` 降順(説明できるロールが多い = 一様事前分布の下で観測が出やすい候補が先)
3. `SPCount` 降順
4. 定義順: 性格クラス(`neutral` → `plus`)→ `ItemCandidates` の添字

- 4 で必ず一意に決まる。float を使わない(旧 `MatchScore` を廃止)ので、ネイティブと WASM で並びが食い違う余地が無い。
- 観測上**まったく区別できない候補**(例: 等倍技に対する半減きのみ と 持ち物なし)は 1〜3 が同値になり、定義順で並ぶ。
  どちらかに決め打ちせず両方を残す(要件)。
- `MaxCandidates` は並べた後に上から切る。`ExactCount` は切る前の値。

### R5. Recall の再定義(基準の数値は変えない)

**旧 Recall@5 の「上位5件」は新仕様では条件として成り立たない。** 理由(計測。固定シード `0x50314238`・全種族 1,000 ケース・
Bayes 最適に近い順序 = §R4 でも):

| 持ち物候補 | 候補数 | 真値の候補が5位以内 | 性質 |
|---|---|---|---|
| 旧テストと同じ2種 | 4 | 常に 100% | 自明(5件に全部入る) |
| 要件の分類どおり(攻撃側5種) | 10 | 76〜80% | 上限。説明可能な候補が平均 8.6 件あり、区別できないものの**決め打ち**を強いる |

一方「真値の SP が範囲に入る」だけなら、正しい区間モデルでは**構成上 100%**(全範囲 0..32 を返しても 100%)で、何も測らない。
1回の整数%観測で説明可能な SP は真値の候補で平均 23/33 あり(情報がそもそも無い)、幅にしきい値を置くと到達不能になる。

そこで、**厳しさを「広すぎない」ことの厳密一致で担保する**:

- **Recall の「正解に入る」**: 真値の (性格クラス, 持ち物) の候補が `Exact` で、真値の SP がその `Ranges` に入り、
  **かつその `Ranges` が総当たりの正解(観測を説明できる SP の集合。テスト側で CalcDamage と
  「いずれかの丸め規則で作れる」から独立に計算)と完全に一致する**。
  全範囲を返す実装・観測を無視する実装・1区間に畳む実装はここで落ちる。
- **基準**: 1回観測 ≥80%、2回観測 ≥95%(変えない)。加えて、次の3つは決定的な性質なので **100%(違反0件)** を要求する:
  - 被覆: 真値を落とさない(丸め規則3通りのすべてで)
  - 厳密性: **全候補**の Ranges・Exact が総当たりの正解と一致する
  - 絞り込み: 2回観測では、1回目だけの結果より説明可能な SP が増えない
- 順位(1位率・5位以内率)と情報量(真値の範囲の平均 SP 数、説明可能な候補の平均数)は**参考値としてログに出す**。

**母集団**(§7 からの変更点。変えないもの: 種族集合・シード `0x50314238`・1,000 ケース・技の作り方・既知側・引き直し規則):

- 真値の SP: 関連ステータス **0..32 から一様**(旧: 0 か 32)。防御側の H は 32(前提どおり)。
  新しい結果は「任意の SP で範囲が真値を含む」と主張するので、端点だけでなく中間値で検証する。
- 真値の性格クラス: {補正なし, 上昇} から一様(旧と同じ2通り)。
- 持ち物: **requirements.md「逆算の持ち物候補」の分類ごとに1つ**(旧: M-C に無いしんかのきせき・チョッキ・こだわり系)。
  防御側 = なし / 防御・特防を上げる / 半減きのみ(技のタイプ)、攻撃側 = なし / 最終ダメージ / 分類の威力 /
  タイプ強化(技のタイプ)/ 抜群時のみ。倍率が近く区別しにくいものを**あえて**入れる(決め打ちしないことの検証)。
- 観測: 整数%。**切り捨て・四捨五入・切り上げの3通りすべて**で作り、それぞれ独立に判定する(規則が未確認のため)。
  100% 超は 100 に丸める(§7 item 6 と同じ)。0% は引き直す。
- 実行時間: 12 構成(側2 × 観測数2 × 丸め3)× 1,000 ケースで約 33 秒(旧 55 秒)。`allspecies` タグのまま。

`TestReverseRecallSmoke`(`make test`)は同じ手順を 12 種族・60 ケースで回し、被覆・厳密性・絞り込み・Recall をすべて 100% で見る
(決定的な性質なので標本誤差の余地は無い。旧 Smoke の緩い下限 75/88 は順位の標本誤差用だったので不要になった)。

### R7. 限界(受け入れる)

Recall の新しい定義(§R5。「上位5件」を「Ranges の厳密一致」に置き換えたこと)はユーザー承認済み
(2026-09-21)。

- **H32 前提の外は表現できない**(H を振らない型、無振り = ADR-0009 の `none` など)。ユーザー決定の前提。
  H0 の相手の観測は、B(D) を低く見積もった範囲として出る(`Exact` のこともある)。`AssumedHPSP` で画面に前提を明示する。
- 下降補正の性格は探索しない(ユーザー決定)。
- 1回の整数%観測の情報量は小さい(真値の候補で平均 23/33 の SP が残る)。技を変えた観測を混ぜられるようにするのが
  最も効く改善だが、API 契約の変更を伴う(§8 のとおり P3-1 以降)。
- 攻撃側は持ち物の倍率(×1.1〜×1.3)と SP・性格が観測上ほぼ区別できない。候補が多く残るのは仕様どおり。

### R8. 境界(`engine/wasmapi`)と API 契約

  結果 DTO に `assumedHpSp`。`percent` / `percentTenths` に小数を渡したら入力検証で落とす(表示%の取り違え防止)。
