# ADR-0137: サービスの分け方の現在の方針とマイルストーンの優先順(ADR-0012 を補う)

- 状態: 採用(ユーザー決定 2026-10-03「既定案で OK」。issue #283 の推奨案 (b))
- 日付: 2026-10-03
- 補う ADR: ADR-0012(damage-calc / balance のサービス境界と共通マスタ)。決定 1〜3 のうち「主要な実行単位は2つ」を本 ADR が置き換え、決定 4〜8(共通マスタの正本・read model・provider 境界)は ADR-0012 のまま有効

## 背景

ADR-0012 は「主要な実行単位は damage-calc と balance の2つ。pokedex-svc が本当に必要か再評価する」と決めた。
その後、実行単位は gateway・pokedex・calc・balance・speed・judge・record・team の8つに増えた(Go サービス。ほかに MySQL・TiDB・NATS)。
一方で `docs/requirements.md` の「必須」のうち、計算結果の自動保存・よく使うポケモン・Web の構築ビルダー(Showdown 形式の入出力)は未完了のままだった(issue #283)。

## 決定

1. **サービスの現在の構成**: gateway(唯一の入口)・pokedex(マスタ参照)・calc(計算)・balance(タイプバランス)・speed(素早さ)・judge(判定)・record(計算イベント・お気に入り)・team(構築)の8つ。
   pokedex-svc は balance・speed・judge・calc の read model の供給元として必要と再評価した(ADR-0105・ADR-0135)。ADR-0012 の「再評価」はこれで済みとする。
2. **サービスを増やす・まとめる基準**(今後の判断):
   - 増やす: 保存先(DB)・障害の影響範囲・リリースの頻度のいずれかが既存と明確に分かれるとき。計算は保存に依存させない(CLAUDE.md 絶対ルール5)。
   - まとめる: 同じレーンが同じ頻度で変え、同じ DB・同じ障害で止まるとき。
   - 既存のサービスの統合・廃止は、完成済みの作り直しになるため、必要が出てから別タスクで決める。今回は統合しない(issue #283 の (c) は採らない)。
3. **マイルストーンの優先順**: 新しい機能(サービス・画面)を増やさず、**M2 の必須**(計算結果の自動保存・よく使うポケモン・Web の構築ビルダー・Showdown 形式のインポート/エクスポート)を先に終える。
   タイプバランス・素早さ・判定は「要件に追加した機能(実装済み)」として `docs/requirements.md` に位置づけ、必須ではない。
   新規の機能要望は、M2 の必須が終わるまで受け付けても着手を後ろに回す(バグ修正・運用の安全に関わるものを除く)。
4. 構成を変えるのは判断を伴う変更なので、本 ADR を置き換える ADR を新しく書く。

## 結果

- `docs/requirements.md` に「要件に追加した機能(実装済み)」節、`docs/plan.md` の冒頭とマイルストーン表に優先順を反映した。
- 運用の持ち主(M2 は API レーン、M4 と到達経路・運用はデータレーン)は `docs/ai-shared/decisions/2026-10-03-data-ops-ownership-lanes.md` と COORDINATION.md に記録した。
