# ADR-0329: 計算画面の攻撃側に SP の数値入力と性格補正を足し、「技 → 攻撃/特攻」の順にする(I-web-1・I-web-3)

- 状態: 採用(Web レーン、2026-10-04。実装済み)
- 日付: 2026-10-04
- レーン: Web
- 関連: ADR-0300 §5(攻撃側プリセット)、ADR-0010 §R1(代表性格)、ADR-0301 §2(natureId の解決)、
  ADR-0312(計算条件と条件の寿命)、ADR-0315(防御側ランクの def/spd 別保持)、ADR-0316 §4(構築の SP 欄の検査)、
  ADR-0311(特性セレクト)、ADR-0320(メガの持ち物固定)、docs/plan/improvements/web.md I-web-1・I-web-3

## 背景

利用者の要望(2026-10-04、データレーン 01 経由): 「この努力値ならどれくらいか」が分からない。攻撃側の能力ポイント(SP)を、
今の「無振り・特化・全振り」に加えて自分で数値(0〜32)で入れたい。性格補正(上昇・補正なし・下降)も選びたい。
丸め(4096 基準・五捨五超入)は今のまま。入力の順は「技を選ぶ → その技の分類の攻撃/特攻を決める → 計算」。
物理と特殊の両方を使うポケモンで手間にならないよう、攻撃・特攻の両方の入力を常に出し、選んだ技が使う方を強調する。

今の画面は攻撃側カードの中に1つのラジオグループ「攻撃側の調整」(無振り / X特化 / X振り(無補正))を持ち、X は技の分類で
決まる(Key を1つだけ保持し、技を物理 ⇄ 特殊に替えると A特化 ⇄ C特化 に読み替わる)。

engine は既に任意の SP(`Individual.sp`、各 0〜32・合計 66 以下)と性格(`{plus, minus}`)を受け付ける
(`engine/model.go` の `Validate`、`engine/wasmapi/dto.go` の `natureDTO`)。ダメージ式が攻撃側から読むのは
技の分類の A(物理)か C(特殊)だけ(`engine/damage.go` の `attackDefenseStats`)。engine・API 契約は変えない。

## 決定

### 1. 画面の形(I-web-3)

- 攻撃側の種族を選ぶと、**「技」セレクタの直後**(持ち物の候補の比較より前。攻撃側カードの外)に「攻撃」「特攻」の
  2ブロックを**常に**出す。旧「攻撃側の調整」(攻撃側カードの中のラジオグループ)は取り除く。
- 各ブロックは `<fieldset>`(role=group)。`<legend>` は「攻撃」「特攻」。選択中の技の分類が使う側
  (物理・変化 = 攻撃、特殊 = 特攻。`attackStatFor`)の legend に「(この技で使用)」を足し、`aria-current="true"`
  を付ける。視覚の強調はトークンの色・枠に加えて見出しの文字でも示す(色だけに頼らない)。技が未選択なら強調しない。
- 各ブロックの中身(上から):
  1. プリセットのラジオグループ「攻撃の調整」/「特攻の調整」: 無振り・A特化・A振り(無補正)(特攻は C 表記)。
     文言は既存の `attackerPresetText` を踏襲。並びは `ATTACKER_PRESET_KEYS`。
  2. SP の入力欄「攻撃のSP」/「特攻のSP」: `type="text" inputMode="numeric"`(ADR-0316 の構築の SP 欄と同じ)。
  3. 性格補正のラジオグループ「攻撃の性格補正」/「特攻の性格補正」: 上昇・補正なし・下降(アクセシブルネームは
     この3語。↑↓ を添えるなら `aria-hidden` の装飾にする)。攻撃は A、特攻は C に掛かる。
- 文言は `i18n/ja.ts` に置く(ハードコードしない)。色・余白はデザイントークンのみ。演出は操作時のみ。
- design.md「入力はタップで選ぶ。数値の直接入力は『詳細』を開いたときだけ」の例外として、攻撃側の SP 欄は常に出す
  (利用者の要望。プリセットのタップで従来どおり数値を打たずに済む)。design.md の計算画面の図と箇条書きを実装と同じ
  PR で更新する。

### 2. プリセットと数値入力の関係

- 状態はブロックごとに `{ spText: string, modifier: "up" | "neutral" | "down" }`(`AttackStatInput`)。
  SP は入力途中を保てるよう文字列で持つ(ADR-0316 §2 と同じ)。既定は両方 `{ "0", "neutral" }`。
- プリセットを選ぶと、そのブロックの値に `presetInput(key)` を入れる: 無振り = `0`・補正なし、特化 = `32`・上昇、
  振り(無補正) = `32`・補正なし。`attackerPresets`(engine/presets/attacker.json の契約)の関連ステータスの値と一致させる
  (テストで固定)。
- プリセットの選択状態は保持せず、ブロックの値から毎レンダー導く(`matchingPreset`)。どのプリセットとも一致しなければ
  どのラジオも選ばれず、ブロックに「カスタム」と出す。数値を手で 32 に戻す等で一致すれば再びそのプリセットが選ばれた
  表示になる。数値を変えても補正は変わらず、補正を変えても数値は変わらない。

### 3. 他のステータスと要求の形

- H・B・D・S の SP は 0 のまま(従来の攻撃側プリセットの挙動)。攻撃と特攻の SP は**両方とも**要求の
  `attacker.sp` に載せる(技が使わない側の値もそのまま。お気に入りに入る個体と同じにするため)。
- この形では合計は最大 32 + 32 = 64 で、合計 66 の上限は構造上超えない。合計超過のエラー表示は作らない
  (到達できない分岐を持たない)。上限との関係はテストで固定する。
- 要求の組み立ては WASM・API で同じ(`buildIndividual` に `sp`・`nature` を渡すだけ)。API は `resolveNatureId` で
  natureId に写す。丸めは engine のまま(Web は値を渡すだけ。ゴールデンは変わらない)。

### 4. 性格の解決(A 補正と C 補正 → 性格)

A 補正と C 補正を別々に持ち、要求の `nature` は **マスタの性格一覧から**純粋関数 `resolveAttackerNature(natures, {atk, spa}, category)`
で解決する(オンラインの natureId 解決と必ず一致させるため。解決できた性格は必ず `resolveNatureId` で ID に戻せる)。

1. 両方補正なし → `NEUTRAL_NATURE`(`{plus:"", minus:""}`。既定の要求を従来とバイト同一にする)。
2. A・C の両方に合う性格(上昇の側は plus、下降の側は minus、補正なしの側は plus でも minus でもない)を **ID の昇順**で
   最初に選ぶ。例: A↑・C補正なし・特殊技 → plus=atk、minus ∈ {def, spd, spe} のうち ID が最小のもの。
   **ただし**、技が使う側が上昇でもう一方の攻撃系が補正なしなら、マイナスをもう一方の攻撃系に置く性格を優先する
   (物理 = +A/−C、特殊 = +C/−A。従来のプリセット〈ADR-0010 §R1 の代表性格・engine/presets/attacker.json の契約〉と
   同じ性格。実データの25性格でも「A特化」がいじっぱり相当になり、素早さに効くお気に入りの個体が変わらない)。
   その性格がマスタに無ければ ID の昇順に戻る。
3. 2 が無ければ、選択中の技の分類が使う側だけを合わせる(使わない側はこの技のダメージに効かない)。使う側が補正なしなら
   `NEUTRAL_NATURE`。例データ(性格6種)の A↑・C補正なし・物理技 → 例データの +A/−C(従来の A特化と同じ要求)。
4. それでも無ければ `null`。画面は `role="alert"` で「この性格補正の組み合わせに当たる性格がマスタにありません」と出し、
   計算しない。
- A と C を同じ向き(上昇と上昇・下降と下降)にする組み合わせは実在する性格にならないので、**入力時に制約する**:
  もう一方が上昇なら、こちらの「上昇」と「特化」プリセットを `disabled` にする(下降も同様)。理由の一文を
  `aria-describedby` で添える。黙ってもう一方の値を書き換えることはしない(「両方の値が残る」に反するため)。
  関数としては同じ向きの組み合わせに `null` を返す(防御的)。

### 5. 範囲外・不正な入力

- SP は 10 進の整数 0〜32(前後の空白は無視、先頭の 0 は可)。空欄は 0(ADR-0316 §4 と同じ。1文字ずつ消す途中を
  弾かない)。符号・小数点・指数・全角数字・33 以上は不正。
- 不正な欄は入力を拒否せず、`aria-invalid="true"` と `role="alert"`(「攻撃のSPは0〜32の整数で入力してください」)で
  明示し、**計算しない**(技が使わない側の欄が不正でも同じ。要求に両方の SP を載せるため)。古い結果の行も出さない。
  直せばエラーは消えて計算し直す。

### 6. 古い結果と値の寿命

- `CompletedCalc` に攻撃側の入力(`attackerStatInputs` の参照)を持たせ、今の入力と違えば loading にする
  (旧 `attackerPresetKey` の置き換え)。数値・補正を変えた直後に古い行を出さない。
- 値の寿命は ADR-0312 §6 の条件と同じ: **技の変更・攻撃側/防御側の種族の変更・攻守入れ替えで消さない**
  (旧プリセットの Key も攻守入れ替えで保っていた。攻撃側の調整は「自分側」の設定で、入れ替え後も自分が攻撃側のため)。
  技を物理 ⇄ 特殊と切り替えても両方のブロックの値はそのまま残り、強調だけが移る。

### 7. お気に入り・メガ・特性との共存

- お気に入りに入れる攻撃側(ADR-0327 §2)の SP・性格は、この入力から解決したものにする(`resolveAttackerStats`)。
  入力が不正・性格が解決できないときは追加できない(`favoriteInput` を null)。性格は技の分類で解決が変わりうる
  (例: A↑・C補正なしで特殊技にすると §4 の 3 のフォールバックになる)。
- メガの持ち物固定(ADR-0320)・特性セレクト(ADR-0311)・「詳細」の攻撃側ランク(ADR-0312)は独立に働く
  (互いの値を書き換えない)。

### 8. 対象外

- 逆算画面(自分側の調整)・調整画面・判定画面は対象外(同様の入力が要るなら別 PR・別 ADR)。
- iOS は同じ仕様を iOS レーンが横展開する(データレーンが連絡)。
- engine・`api/openapi.yaml`・services は変えない。

## 実装メモ(採用時)

- 純粋関数は `web/src/domain/attackerStatInputs.ts`。SP の1欄の読み方は `domain/spInput.ts` の `parseSpText` に置き、
  構築の `checkSpDraft`(ADR-0316 §4)と整数の判定(`SP_DIGITS`)を共有した。`checkSpDraft` の合計の数え方
  (範囲外の値も合計に入れる)は変えていない。
- 同じ向きにできない理由の一文(「攻撃と特攻の両方を上昇、または両方を下降にすることはできません」)は、
  無効な選択肢があるブロックにだけ出し、プリセット・性格補正の両ラジオグループの `aria-describedby` で結ぶ。
- 性格補正のピルに ↑↓ は付けず、語(上昇・補正なし・下降)だけで示す(読み上げ・文字検索と同じ名前にするため)。
- 入力が不正なときの結果欄は何も出さない(idle)。理由は入力のすぐ下の `role="alert"` に出す。
- 無効な選択肢は薄く表示する。強調は太い枠と見出しの文字の両方で示す。
- `docs/design.md` の計算画面の図と「数値の直接入力は詳細を開いたときだけ」の例外を同じ PR で更新した。
- iOS 向けの決定: `docs/ai-shared/decisions/2026-10-04-web-calc-attacker-input-flow.md`。

## 結果

- 利用者は攻撃・特攻の SP を 0〜32 の任意の値で、性格補正つきで試せる。物理・特殊の両刀でも技を切り替えるだけで済む。
- 既定のままなら要求は従来とバイト同一(テストで固定)。engine・API・ゴールデンは変わらない。
- 性格はマスタから解決するので、オンライン(natureId)でもオフライン(WASM)でも同じ要求になる。

## 検討した代替案

- **技の分類に応じて1ブロックだけ出す(旧 UI の延長)**: 両刀で技を替えるたびに入れ直しになる。要望の既定案 A に反する。
- **A↑C↑ のような組み合わせを「最も近い性格」に丸める**: 画面の表示と送る性格がずれ、利用者が気づけない。入力時の制約にした。
- **性格をマスタを使わず `{plus, minus:""}` で送る**: WASM は受理するが実在しない性格で、オンラインは natureId に
  写せず `unknown_nature` になる。WASM と API で要求がずれるので採らない。
- **H・B・D・S も入力させる**: 攻撃側のダメージに効かず、要望の範囲外。合計 66 の検査が要るようになる。
