# ADR-0308: Web のタブ切り替えで入力を消さない — 訪れたタブだけ mount して保持する

- 状態: 採用(Web レーン、2026-09-25。issue #218 の受け入れ条件とテストの正)
- 日付: 2026-09-25
- 関連: issue #218、ADR-0300(Web の構成。§1「ルーターのライブラリは入れない」・「状態管理ライブラリは入れない」)、
  ADR-0301 §4(計算モードの切り替え。自動フォールバックをしない)、ADR-0304 §追記 A-6(モードを切り替えたら
  前のモードのマスタで画面を出さない)、ADR-0304 追記6 / issue #308(マスタの読み込みに失敗してもタブ一覧は残す)、
  ADR-0604 §2(素早さの画面はマウント時に speed API を2本呼ぶ)、
  docs/requirements.md §2「設計原則: 入力の手間を最小にする」

## 背景

`web/src/App.tsx` は `const ActiveScreen = SCREEN_COMPONENTS[tab];` で、選択中のタブの画面**だけ**を
1つの `role="tabpanel"` の中に描いている。タブを切り替えると前の画面のコンポーネント型が変わるため、
React は前の画面を unmount する。画面の入力はすべて画面内の `useState`(`localStorage` を使うのは
`app/calcMode.ts` と `api/clientIds.ts` だけ)なので、計算 → 逆算 → 計算 と往復しただけで、
選んだ種族・技・持ち物・プリセット・観測がすべて初期値に戻る。ブラウザの戻る/進む(popstate)でも同じ。

要件(requirements.md §2)の「入力の手間を最小にする」に正面から反する。

issue #218 の既定案は「5画面すべてを mount したまま、非選択のパネルを `hidden` にする」。
ここで2つの設計判断が要る。

## 決定

### 1. 「訪れたタブだけ mount し、以後 unmount しない」(lazy mount → keep alive)

5画面を最初から全部 mount する案は**採らない**。`web/src/speed/SpeedScreen.tsx` はマウント時に
無条件で `speedClient.pokemon()` と `speedClient.table()` を呼ぶ(ADR-0604 §2 の設計。コメントに明記がある)。
全画面を起動時に mount すると、素早さのタブを一度も開かない利用者でも毎回この2本のリクエストが飛ぶ。
`CalcScreen`・`ReverseScreen`・`BalanceScreen` は入力が揃うまで呼ばないガードを持ち、`JudgeScreen` は
`useEffect` を持たないので、実害が出るのは素早さだけだが、「開いていない画面の通信を起こさない」
という現在の性質は保つ価値がある(ADR-0604 §2 のコメントの前提でもある)。

そこで App は「一度でも選ばれたタブ」を覚え、その画面だけを mount する。以後そのタブを離れても
unmount しない(非選択のパネルは隠すだけ)。これで issue #218 の受け入れ条件(往復・戻る/進むでの保持)を
満たしつつ、未訪問の画面の副作用は起きない。

### 2. 隠し方は**ネイティブの `hidden` 属性**。`role="tabpanel"` は1つのまま

非選択の画面を包む要素に `hidden` を付ける。CSS のクラスだけで隠す案は採らない。jsdom は CSS の
cascade を評価しないため、Testing Library の `getByRole`/`queryByRole` から見ると非選択の画面が
「見えている」ままになり、`App.test.tsx` の既存アサーション
(`expect(screen.queryByRole("combobox", { name: "攻撃側のポケモン" })).toBeNull()` など)が
壊れる。`hidden` 属性なら dom-testing-library の `isInaccessible` が祖先までたどって除外するので、
既存アサーションはそのまま成立し続ける(= テストを緩めずに済む。CLAUDE.md 絶対ルール6)。

`role="tabpanel"` は**今までどおり1つ**にし、全タブの `aria-controls` がその1つを指す形を保つ。
画面ごとに `role="tabpanel"` を分ける方が WAI-ARIA Authoring Practices の Tabs パターンには近いが、
そうすると既存の
`expect(reverseTab).toHaveAttribute("aria-controls", panel.id)`(App.test.tsx)を書き換えることになる。
issue #218 は入力の保持の話で、ARIA 構造の作り替えは目的ではない。「1つの tabpanel の中身を差し替える」
形は APG も認める変種で、`aria-labelledby` が選択中のタブを指す配線も今のまま正しい。
隠す `hidden` はパネルの**内側**の包み要素に付ける(パネル自体は常に見える)。

### 3. マスタが入れ替わったら、マスタを使う画面は作り直す(入力は初期化される)

計算モードをオフライン⇄オンラインに切り替えると `MasterData` ごと入れ替わる(ADR-0304 §追記 A-6)。
このとき、保持していた画面をそのまま生かして新しいマスタを流し込む案は**採らない**。作り直す。

理由:

- `CalcScreen` は直近の計算結果(`completed`)を state に持つ。画面を生かしたまま新しいマスタを渡すと、
  種族の select は「新しいマスタに無い key」を指して空欄になる一方、**古いマスタで計算した結果の行が
  そのまま残る**。空欄の種族の下に前のマスタのダメージが並ぶのは、消えるより悪い。これを直すには
  各画面の内部ロジック(マスタが入れ替わったときの state の作り直し)に手を入れる必要があり、
  issue #218 が「対象外」と明記した範囲に入る。
- ADR-0304 §追記 A-6 と issue #308 の既存テストは「切り替え後のマスタを読み込むまでは前のモードの
  マスタで画面を出さない」「失敗中はマスタを使う画面を出さず案内を出す(黙って古いマスタで描かない)」を
  要求している。マスタが無い/入れ替わった状態を画面の中で扱わせない、というこれまでの線を動かさない。

したがって issue #218 の異常系の受け入れ条件は、**「保持していた選択がマスタに無いまま残らないこと」**
として満たす。具体的には、マスタが入れ替わったらマスタを使う画面(計算・逆算・タイプバランス・判定)は
作り直され、種族も技も持ち物も結果も初期状態に戻る。issue の文言のうち「他の入力(技・持ち物など)は
保持する」は、上の理由で**採らない**(保持すると古いマスタ由来の表示が残るため)。保持の範囲は
「同じマスタで開いている間のタブの往復」と定める。

**実現手段(critic指摘で2026-09-25に修正)**: 当初の実装は、マスタを使う画面の React `key` に
`masterEpoch`(モードごとに別マスタを持つときだけ `mode` の値、単一マスタなら常に `"single"`)を
混ぜて、マスタが実際に入れ替わったときだけ React に作り直させる形にしていた。しかしこれはデッドコード
だった: `masterEpoch` を固定値にしても全テストが green のまま(検知できない)。理由は、計算モードの
切り替えで取得口(`activeMasterSource`)が変わると、`masterLoad.source !== activeMasterSource` になり
`currentMasterLoad` が一旦 `null` になる(ADR-0304 §追記 A-6)。`App.tsx` は
`{currentMasterLoad !== null && (<div className="app-tabs">…</div>)}` という分岐でタブ関連の
サブツリーごと描いているため、`currentMasterLoad` が `null` を経由するたびにこのサブツリー全体が
unmount → 新しいマスタが読めた時点で mount し直される。マスタが入れ替わって *かつ* サブツリーが
残り続けるケースは存在しない(「再試行」は取得口〈`activeMasterSource`〉が変わらないので
`currentMasterLoad` は `null` を経由せず、サブツリーは残ったままになるが、これは望ましい: 同じ
マスタの読み直しでは画面を作り直さない)。したがって `key` に epoch を混ぜる仕掛けは不要で、
マスタを使う画面の `key` は `id` 単体でよい。

この性質(サブツリーがマスタの取得口が変わるたびに作り直される)を、決定1の「訪れたタブの集合
(`visitedTabs`)」のリセットにもそのまま利用する。`visitedTabs` を App の state ではなく、
上記のサブツリーの中に置いた子コンポーネント(`AppTabPanel`)自身の state に持たせることで、
取得口が変わって一旦 `currentMasterLoad` が `null` になるたびに `AppTabPanel` ごと作り直され、
`visitedTabs` も選択中のタブだけへ自動的にリセットされる(React の `useState` の初期化に頼るだけで、
明示的な `key` の作り込みは不要)。`visitedTabs` が App 直下の state のままだと、マスタの
再読み込みでサブツリーが作り直されても `visitedTabs`(App 側)は生き残ってしまい、訪問済みの
非選択タブ(素早さなど)まで一斉に再マウントされ、hidden のまま speed API を呼び直す実害が
あった(critic が計測: 2件→4件)。

### 4. 保持はセッション内だけ。入力は永続化しない

リロードすると入力は初期状態に戻る(issue #218 の既定案どおり)。`sessionStorage`・`localStorage` に
入力を書かない。ADR-0300 の「状態管理ライブラリを入れない」方針も変えない(訪れたタブの集合を持つのは
`useState` 1つだけ。決定3の実現手段のとおり、置き場は App 直下ではなく `App.tsx` 内の子コンポーネント
`AppTabPanel` だが、依然としてこの1つのコンポーネントツリーの中に閉じている)。

## 影響

- 変更するのは `web/src/App.tsx` のレンダー部だけ(訪れたタブの記録と、パネル内の包み要素 + `hidden`)。
  各画面(`CalcScreen`・`ReverseScreen`・`BalanceScreen`・`SpeedScreen`・`JudgeScreen`)と
  `app/screens.tsx`・`app/routes.ts` は変更しない。
- メモリ: 訪れた画面の数だけ DOM とコンポーネントが残る(最大5)。計算結果の行も残るが、
  いずれも1画面分の入力と数行の結果なので問題にならない。
- CSS: 隠した包み要素は `hidden` で `display: none` になるので、`.app-tabs__panel` のレイアウトには
  影響しない(`hidden` を打ち消す `display` を `App.css` に書かないこと)。
- 常時動くアニメーションは増やさない(CLAUDE.md ドメイン規約)。隠れている画面でも
  `useHoloCard` などの演出は操作時のみ。

## 却下・保留

- **5画面を起動時に全部 mount する**(issue の既定案): 素早さの画面がマウント時に speed API を
  2本呼ぶため、開いていない画面の通信が毎回起きる(決定1)。
- **状態を App に持ち上げる**(issue の代替案): 画面ごとの入力の型が App に流れ込み、画面を足すたびに
  App が太る。ADR-0300 §1 の「App は配線だけ」を崩す。
- **`sessionStorage` に入力を保存する**: リロードをまたぐ保持は issue の既定案が要らないとしている。
  保存すると、マスタが入れ替わったときに「存在しない種族の key」がストレージに残る後始末が増える。
- **CSS クラスだけで隠す / `aria-hidden="true"` だけを付ける**: 決定2のとおり、jsdom 上の
  アクセシビリティツリーの扱いが曖昧になり、既存テストの意味(別タブの入力欄は取得できない)が揺れる。
- **画面ごとに `role="tabpanel"` を分ける**: 決定2のとおり、既存の `aria-controls` のテストを
  書き換えることになる。将来 ARIA 構造を見直すなら、それ自体を1タスクにする。
