# ADR-0331: 調整画面のメガ固定(F-10)と、「相手を選んで目標を選ぶ」調整(F-11)

- 状態: 採用(2026-10-04。spec 段階。実装は段階 A = Web、段階 B = engine・calc-svc)
- 日付: 2026-10-04
- レーン: ダメージ計算(ec)・Web(Web 帯 `0300〜`。`0330` は PR #625 が使うため `0331`)
- 関連: docs/usability-round2.md F-10・F-11(ユーザー決定 2026-10-04)、ADR-0150(調整の探索・配分)、ADR-0250(調整 API の契約)、
  ADR-0319(Web の調整画面)、ADR-0320・ADR-0326・ADR-0328(メガ固定・持ち物の役割・ストーンの名前)、ADR-0509(iOS のメガ固定)、
  ADR-0107(技の追加効果のランク変化)、ADR-0700 §6-5・docs/judge-design.md §4-5(判定の素早さ)、docs/speed-design.md §5(素早さのプリセット)、
  ADR-0300 §5・ADR-0009(攻撃側・防御側のプリセット)

## 背景

2026-10-04 の動作確認でユーザーから2点の要望が出た(docs/usability-round2.md 原文 15・16)。

- **F-10**: 調整でメガ種族を選んでも持ち物を選べる。計算・逆算・構築・判定は固定済み(ADR-0320・0326)だが、調整は
  ADR-0326「対象外・追跡」のとおり固定が無く、ストーンを選択肢から外して**持ち物なしで計算**している。iOS の調整は固定し、
  ストーンを要求に送っている(ADR-0509)。
- **F-11**: 目標を数値で入れるのは手間。「このポケモンのこの技を耐えたい」「このポケモンの素早さを上回りたい」を
  **相手と目標の種類を選ぶ**形にしたい。ユーザー決定: 種類は「素早さを上回る」「この技を耐える」「この技で倒す」の3つ、
  相手の振り方はプリセットから選ぶ(数値は内部で決める)、目標は複数追加できる、今の「素早さの目標(実数値)」は詳細設定に残す。
  判定レーンの元の要望「ニトチャ+メイン技で素早さ抜ける+そのポケモンを倒せるか」を1回で、も同じ画面の目標で満たす。

今の契約(ADR-0250)で足りるかを確かめた。

| 必要なこと | 今の契約 | 足りるか |
|---|---|---|
| 相手の素早さの実数値 | どこにも無い(Web は式を持たない。ADR-0319 §1) | 足りない |
| 素早さだけの目標で「最小の S」 | `allocation`(offense)は `goal` が無いと `minSp` が null。`maxIndex` は S を最大にする | 足りない |
| 「倒す」と「素早さ」を同時に | `allocation`(offense)の `goal` + `minSpeed` | 1つずつなら足りる |
| 「耐える」を2つ(物理と特殊など) | `goal` は1つ。H を共有するので別々の結果を足せない | 足りない |
| 「耐える」と「倒す」を同時に | bulk と offense の2回に分かれ、合計 66 の配分が分かれる | 足りない |
| ニトロチャージで上がった後の素早さ | 技の追加効果(ADR-0107)は calc-svc のマスタにだけある。公開 `Move` に無い | 足りない |

## 決定

### 1. F-10: 調整画面のメガ固定(iOS ADR-0509 と同じ挙動)

- 自分のポケモンにメガ種族を選ぶと、持ち物を `megaItemLock`(`domain/mega.ts`)でストーンに固定する。持ち物欄は `disabled`、
  値はストーンの ID、表示はストーンの名前(`megaStoneDisplayName`。ADR-0328)。理由 `megaItemText.lockedReason` を見える文で出し、
  `aria-describedby` で欄に結び付ける(計算・判定と同じ作法)。ストーンを引けない(`missing`)ときは空で `disabled`、理由は `missingReason`。
- メガ以外・未選択に変えたら固定を外して**未選択に戻す**(`itemIdAfterSpeciesChange`)。メガどうしの切り替えは新しいストーン。
- 要求: 自分の `Individual.itemId` に**ストーンを送る**(`missing` は送らない)。indices・min-sp-to-ko・min-sp-to-survive・allocation・goals のすべて。
  calc-svc は調整でもメガの持ち物を受け付ける(`Individual.itemId` の契約: requiredItemId か省略)。iOS と同じ要求になる。
- 相手(持ち物欄を持たない)がメガ種族なら、相手の `Individual.itemId` にもストーンを送る(`missing` は送らない)。
  相手の欄は持ち物を選ばせないので文は出さない(結果の名前にだけ出る)。
- 種族を検索で解決するマスタ(`speciesList` が false)でも、解決した種族(`MasterSpeciesResolution.species`)の `isMega`・`requiredItemId` で固定する。
  ストーンの実体はマスタの持ち物の全件(`master.items`)から引く(ADR-0326 §4。絞り込んだ選択肢からは引かない)。
- ADR-0326「対象外・追跡」の「調整画面にはメガの固定が無い」は本 ADR で解消する。

### 2. F-11 の進め方: 新しい操作 `adjustGoals` と、2段階の実装

目標をすべて満たす最小の振り方は、今の4操作の組み合わせでは作れない(背景の表)。Web で4操作を順に呼んで合成する案は、
「耐える」を2つ持つと最小にならず(H を共有する)、素早さだけの目標では最小の S が出ず、相手の素早さを出すために
Web が式を持つことになる。よって **1操作1エンドポイント**(ADR-0250 §1)の流儀で、新しい操作を足す。

| 操作 | HTTP | 段階 |
|---|---|---|
| `adjustGoals` | `POST /api/calc/adjust/goals` | 契約は本 ADR で決め `api/openapi.yaml` に入れた。calc-svc は 404 のスタブ(段階 B で実装) |

- **段階 A(Web。本 ADR §5〜§8)**: 画面・要求の組み立て・結果の表示。fake のクライアントでテストし、段階 B の前でもマージできる。
  ただし calc-svc が 404 を返す間は「目標から振り方を決める」が使えないので、**段階 B が main に入るまでモードの radio を出さない**
  (出す条件は 1 か所の定数 `ADJUST_GOALS_ENABLED`(`adjust/adjustGoals.ts`)。段階 B のマージで true にする。
  画面の props `goalsEnabled`(省略時はこの定数)でテストから有効にする)。
- **段階 B(engine・calc-svc。別 ADR)**: engine に複数目標の探索を足し、calc-svc の `AdjustGoals` を実装する。engine の
  探索の定義は engine 帯の ADR(`0151` 以降の空き)で決める。本 ADR §4 はその前提と提案。WASM への登録は Web が API 専用(ADR-0319 §1)なので段階 B では行わない。

### 3. 相手の素早さはサーバーが求める(案②)

| 案 | 内容 | 判断 |
|---|---|---|
| ① クライアントが種族値とプリセットから実数値を計算 | Web と iOS が `floor((種族値+20+SP)×性格)` とランク補正を持つ | **却下**。式の二重実装(engine の `RealStats`・`EffectiveStat` が正)。ADR-0319 §結果「Web は計算をしない」 |
| ② 契約に相手の個体を渡し、calc-svc が engine で求める | `AdjustGoal.opponent` から `RealStats` + `ranks` の `EffectiveStat` | **採用**。式は engine の1か所。Web・iOS は同じ契約を呼ぶだけ |
| ③ Web が WASM の engine を呼ぶ | `CalcEngine` に関数を足す | **却下**。調整は API 専用(ADR-0319 §1)。iOS は WASM を持たない |
| 素早さレーン(speed-svc)の position を呼ぶ | speed-svc の preset・スカーフ計算を再利用 | **却下**。別サービスの別 ID(`pokemonId`)で、gitops に未配備(docs/speed-design.md §7)。調整が speed-svc の稼働に依存する |
| 判定(judge)の `outspeeds` | judge-svc の判定 | **却下**。判定は非表示(F-07)で目的を作り直す。調整の計算を判定に依存させない |

- 「上回る」は**素早さが相手より大きい**(同速は満たさない。ADR-0150 §8 の「相手の S + 1」と同じ)。
- 相手の持ち物・特性・場による素早さの補正は段階 B では含めない(こだわりスカーフの ×1.5 は engine に無く speed-svc のコアにだけある。
  docs/speed-design.md §2)。必要になったら engine に素早さの補正を足す別 ADR で扱う。相手のランクは `opponent.ranks` で渡せる。
- **ニトロチャージ**: 目標「素早さを上回る」に任意の「先に使う技」(`moveId`)を持たせ、calc-svc がマスタの技の追加効果
  (ADR-0107 の `Move.Effect`。**確率 100% の、使用者自身の素早さのランク変化**)を自分に掛けて比べる。公開 `Move` に追加効果が無いので
  (ADR-0107 決定8)、Web は技を絞れない。効果の無い技でもエラーにせず、応答の `selfSpeedRank` が 0 になり、画面がそれを文で伝える。
  確率 100% でない追加効果(発動しないことがある)は掛けない(「必ず先に動ける」を約束できないため)。

### 4. engine の拡張(段階 B の前提と提案。決定は engine の ADR)

`api/openapi.yaml` の `adjustGoals` の意味: 下限 `self.sp`・上限 `ceiling`(省略は 32)の中で、**すべての目標を満たす組のうち合計 SP が最小**の組。
同点は ADR-0150 §6 の規則。すべては満たせないときも 200 で `feasible: false` と最も近い組、目標ごとの `met`。

提案する探索(engine ADR で確かめる):

- 目標ごとに効く能力が分かれる: 素早さ → S、倒す → A か C(技の分類)、耐える → H と B・D。**能力の組が重ならないので**、
  S・A・C は単調性から1次元の最小(S は「最も速い相手 + 1」を自分のランクで割り戻した最小の SP、A・C は同じ分類のすべての「倒す」を満たす最小の SP)、
  H・B・D は「耐える」をすべて満たす最小の組を 33³ の総当たり(`CalcDamage` は目標ごとに (H, B) / (H, D) の 33² で使い回す)で求め、合計する。
  合計が 66 を超える・上限で届かないときが `feasible: false`。
- 例外: 自分の別の能力でダメージが変わる技(ボディプレスのように防御で攻撃する技など)は分けられない。engine の ADR で、
  その技を含む目標を拒否する(`invalid_input`)か、合わせて探索するかを決める。
- 計算量: 目標 6 件(上限)・耐える目標 6 件でも `CalcDamage` は最大 6 × 1,089 回 + 候補 35,937 × 6 の確率の参照で、
  allocation(ADR-0250 §5)の数倍。上限ちょうどのベンチマークを足す。
- 規模の見積もり: engine に `SuggestSPForGoals`(1 ファイル + 独立の総当たりとの一致を見る性質テスト)、calc-svc の境界(検査順・ID 解決・
  素早さのランク変化の読み出し)とテスト、engine ADR 1 件。ゴールデン(ダメージ式)は変えない。

### 5. Web: 画面の構成(段階 A)

- モードに **「目標から振り方を決める」(`goals`)** を足し、radio group の**先頭**に置く。既定のモードは今のまま「指数と 16n を見る」
  (F-12 の作り直しで既定と「詳細設定」への格納を見直す。今の5つのモードと「素早さの目標(実数値)」はそのまま残す = ユーザー決定の「詳細設定に残す」)。
- `goals` のときは、領域「相手」「目標」(発数・確率)の代わりに、領域 **「目標」**(h2)を出す。中身:
  - 目標のカード(`fieldset`、legend「目標 n」= group の名前)を追加順に並べる。n は 1 からの位置(外すと詰める)。
  - 「目標を追加」ボタン。目標は最大 `MAX_ADJUST_GOALS` = 6 件(契約の `maxItems`)。6 件で `disabled` にし、理由
    「目標は 6 つまでです」を `aria-describedby` で結ぶ。目標が無いときは「目標を追加してください」の文。
  - 追加したら新しいカードの「種類」にフォーカスを移す。外したら「目標を追加」にフォーカスを移す。
- カードの欄(見えるラベルは短い語、accessible name は「目標 n の<ラベル>」。SC 2.5.3):

| 欄 | 見えるラベル | 種類 | 中身 |
|---|---|---|---|
| 種類 | 種類 | すべて | 「素早さを上回る」(既定)・「この技を耐える」・「この技で倒す」 |
| 相手のポケモン | 相手のポケモン | すべて | 一覧(select)または検索欄(SpeciesSearchField) |
| 相手の振り方 | 相手の振り方 | すべて | 素早さ: 最速(既定)・準速・無振り / 耐える: 攻撃側プリセット(無振り・A(C)特化(既定)・A(C)振り。相手の技の分類で A/C)/ 倒す: 防御側プリセット(`defenderPresetKeysFor(自分の技の分類)`。既定は無振り) |
| 相手の技 | 相手の技 | 耐える | 相手の learnset のダメージ技 |
| 自分の技 | 自分の技 | 倒す | 自分の learnset のダメージ技 |
| 先に使う技 | 先に使う技 | 素早さ | 任意。「使わない」(既定)+ 自分の learnset のダメージ技。説明「ニトロチャージのように自分の素早さが上がる技を選ぶと、上がったあとの素早さで比べます」を `aria-describedby` |
| 発数・確率 | 発数・確率 | 耐える・倒す | 既存と同じ選択肢(1〜10 発、確定・90%・75%・50%) |
| 外す | 外す | すべて | ボタン。accessible name「目標 n を外す」 |

- **素早さのプリセット**(`adjust/adjustGoals.ts` の `SPEED_PRESETS`。入力の作り方の型でマスタではない。docs/speed-design.md §5 の語にそろえる):

| key | 表示 | S の SP | 性格 |
|---|---|---|---|
| `fastest` | 最速 | 32 | 素早さ上昇(下降は攻撃。相手の素早さだけを比べるので下降の置き先は結果に影響しない) |
| `neutral_max` | 準速 | 32 | 補正なし |
| `none` | 無振り | 0 | 補正なし |

  ほかの能力の SP は 0。性格の ID はマスタから引く(`natureIdForPreset`。見つからなければ送らずに理由)。スカーフ・+1 などの行は段階 B 以降
  (スカーフは §3 のとおり engine に無い。+1 は `ranks` で送れるので、要望が出たら足す)。
- 種類を変えたら、相手のポケモンは保ち、振り方・技は新しい種類の既定に戻す。自分のポケモンを変えたら、選べなくなった自分の技
  (倒す・先に使う技)は未選択に戻す。モードを切り替えても目標は消さない。

### 6. Web: 要求・検査・送信

- 「調整する」で `indices`(今の振り方。従来どおり)と `goals` を**並行して**呼び、両方そろってから出す(ADR-0319 §4 と同じ)。
- `AdjustGoalsRequest`: `format: "single"`、`self`(今の `Individual`。固定 SP が下限。メガはストーン)、`goals`(カードの順)。`ceiling` は送らない(全能力 32)。
- `AdjustGoal`: 共通で `kind`・`opponent`(`{ speciesKey, level: 50, natureId, sp }`。メガはストーンの `itemId`)。
  素早さ = 先に使う技を選んだときだけ `moveId`(`hits`・`thresholdPercent` は送らない)。
  耐える = `moveId`(相手の技)・`hits`、しきい値は 100 以外のときだけ。倒す = `moveId`(自分の技)・`hits`、しきい値は同じ。
  組み立ては純粋関数 `buildGoalRequest`・`goalOpponentIndividual`(`adjust/adjustGoals.ts`)。
- 送信前の検査(違反なら API を呼ばず role=alert。最初の違反だけ): 自分のポケモン・性格、固定 SP(既存)、目標が 0 件「目標を追加してください」、
  目標ごとに順に「目標 n: 相手のポケモンを選んでください」「目標 n: 相手の技を選んでください」(耐える)「目標 n: 自分の技を選んでください」(倒す)
  「目標 n: 相手の振り方に合う性格がマスタにありません」。
- 取り消し・古い応答・画面を閉じたときの abort は既存(ADR-0319 §4)と同じで、`goals` の呼び出しにも signal を渡す。

### 7. Web: 結果の表示

- 先頭に未対応の印(既存)、次に今の振り方の指数(既存の h3)。
- 振り方(h3 の region): すべて満たすなら「目標をすべて満たす振り方」、満たせないなら「目標に一番近い振り方」と
  「すべての目標は満たせませんでした」。能力ポイント・合計・実数値・「残りの能力ポイント n」(既存の文言)。
- 目標ごとの結果(`ul`、名前「目標ごとの結果」)を目標の順に1行ずつ。名前は**送信した時点**の相手・技・振り方から作る:
  - 素早さ: 「目標 n: {相手}({振り方})より先に動けます(自分 a / 相手 b)」/「…より先には動けません(自分 a / 相手 b)」。
    先に使う技を選んだときは前に「{技}で素早さが k 段階上がったあと、」、上がらない技なら「{技}では素早さは上がりません。」を付ける。
  - 耐える: 「目標 n: {相手}({振り方})の{技}を m発耐えます(耐える確率 p)」/「…を m発は耐えられません(耐える確率 p)」
  - 倒す: 「目標 n: {技}で{相手}({振り方})を m発で倒せます(倒す確率 p)」/「…を m発では倒せません(倒す確率 p)」
  - p は既存の `formatChancePercent`(0.1% 単位の切り捨て)。
- エラーは既存の写像(code から日本語、サーバーの message は出さない)。入力・目標は消さない。

### 8. 見た目・iOS・文言

- 本 ADR は**構造・挙動・文言**だけを決める。色・カード・アイコンの全面変更は F-12(デザイン基盤。Web レーン)の後に行い、本 ADR の
  accessible name・見出し・文言を変えない範囲で載せ替える。アニメーションは入れない。
- 文言は `i18n/adjust.ts` の `adjustScreenText` に置く。iOS は同じ語にそろえる(docs/usability-round2.md §5)。
- **iOS の追従**: 仕様の正は本 ADR §1(メガ固定。iOS は ADR-0509 で実装済み。要求に相手のストーンを載せる点だけ確認)と §3・§5〜§7、
  契約は `api/openapi.yaml` の `adjustGoals`。iOS は段階 B の後に同じ契約を HTTP で呼ぶ。

## 却下した案

- **Web で既存の4操作を組み合わせる(段階 A だけで完結させる)**: 背景の表のとおり、素早さだけの目標で最小の S が出ず、「耐える」2つで最小にならず、
  相手の素早さに式が要る。満たすが最小でない振り方を「最小」と見せることになる。
- **`allocation` に `goals[]` を足す**: `mode`(bulk / offense)で回す能力が分かれる前提と合わず、応答の `maxIndex`(指数最大)は目標の調整では使わない。
  別の意味の操作を1本に混ぜない(ADR-0250 §1)。
- **相手の振り方を数値で入れさせる**: ユーザー決定(プリセットから選ぶ)と requirements.md「プリセットを選ぶだけ」に反する。
- **目標の数を無制限にする**: 探索量が目標数に比例する(§4)。6 は構築の 6 匹と同じで、要望の範囲を覆う。

## 結果

- 既存のモードと契約は変えない(足すだけ)。`AdjustModeKey` に `goals` が増える。無効のとき(既定)の radio は今の5つのまま(既存テストは変えない)。
  段階 B で有効にするときは、radio の数を固定する既存テストの期待値を 6(先頭に `goals`)へ改める(仕様の変更)。
- 段階 B が main に入るまで `ADJUST_GOALS_ENABLED` は false で、利用者には今の画面のまま見える。
- ADR-0250 §1 の表に `adjustGoals`(HTTP のみ)が加わる。ADR-0326 の「調整にメガ固定が無い」は解消する。
