# ADR-0422: おすすめタイプの改善 — 偏りを悪化させる候補の除外・該当ポケモンのタイル・相性の色

- 状態: 採用(ユーザー要望 2026-10-11。案はタイプバランスレーン。Web・iOS と分担)
- 関連: ADR-0401(おすすめタイプ。§3 候補の並び・§8 該当ポケモン)、ADR-0421(構築の中の「バランス」)、ADR-0303 §7(判定は API の値だけ)、
  ADR-0339(見た目の作り直し G-05)、ADR-0334(ポップ配色)、ADR-0810(画像の取り込み)、docs/design.md

## 背景
構築内の「バランス」(ADR-0421)で、おすすめタイプを選びやすくしたい。(1) 補うタイプの該当ポケモンをその場で見て、タップで空き枠に入れたい。
(2) おすすめは 1 つに限らず、効果の高い順に 3〜5 個。ただし「明らかにおかしい」候補(すでに偏っている弱点をさらに増やす)は出さない。
(3) 弱点は赤、耐性は水色系(今は緑)、無効は灰で、Web と iOS で同じ意味の色にする。

## 決定

### 1. 評価の理屈(サーバー。テストで固定する)
ADR-0401 §3 の候補(171 通りの防御タイプ)・並び(`defenseCovered + offenseCovered` の多い順 → `weaknesses` の少ない順 → 正準順)は変えない。そこに**除外**を足す。

- **偏りのある攻撃タイプ**(`skewedAttackTypes`): チームの集計(TB1。特性反映済み)で `weak - (resist + immune) >= 2` の攻撃タイプ
  (`weak` は ×2 と ×4 を含む人数。`resist` は ×1/2 と ×1/4、`immune` は無効)。穴(耐性・無効が 0 人)のうち 2 人以上が弱いものも含む。
- **除外**: 候補の防御タイプが、偏りのある攻撃タイプのどれかに対して ×2 以上(弱点)になる候補は、`candidates` に入れない。
  (すでに偏っている弱点をさらに増やす候補を勧めない。)
- 除外しても穴をふさぐ数・並びは変えない(除外した後の並びのまま上位 `limit` 件)。穴が無い・すべて除外されたときは `candidates: []`。
- 件数: サーバーの既定 10・上限 20 は変えない。**クライアントは `limit: 5` で呼ぶ**(構築内の「バランス」は上位 5 個。ユーザー要望の 3〜5 個)。
- 応答に `skewedAttackTypes`(攻撃タイプの正準順。偏りが無ければ空配列)を足す。画面は偏りの表示とテストに使える。契約は `services/balance/api/openapi.yaml` を 0.9.0 → 0.10.0(項目の追加のみ。古いクライアントはそのまま動く)。
- 数えるのは防御タイプの組み合わせの相性だけ(候補の特性は考えない。ADR-0401 §3)。レギュレーション・使用可能の判定は read model の側(ADR-0401 §4)。

### 2. 該当ポケモンのタイル(Web・iOS)
- 候補ごとの該当ポケモンは**今の応答の `pokemon`**(ADR-0401 §8。`exactMatch` が先 → `pokemonId` 昇順。read model 由来でハードコードしない)をそのまま使う。新しい API は要らない。
- 表示: 候補(タイプのバッジ + 「穴を n 個ふさぐ」の数)の下に、小さなタイル(画像 + 名前。画像が無ければタイプ色のエンブレム。G-06/ADR-0808)を並べる。
  1 候補で最初の 8 件まで表示し、残りは「もっと見る」(押して全件)。
- タップ: 構築編集の**最初の空き枠**にそのポケモン(`pokemonId` = speciesKey)を入れる。6 枠が埋まっているときはタイルを押せない状態にして「空き枠なし」を一言出す。
  入れたら結果は ADR-0421 のとおり自動で更新される。
- 境界: `BalancePanel` は `onPickPokemon?: (speciesKey: string) => void` と `canPick: boolean` を受け取り、構築側(TeamMemberEditor / TeamEditView)が実際の枠への入れ方を持つ。
  バランス側は枠の構造を知らない(ADR-0421 §3 の境界を保つ)。`onPickPokemon` が無ければタイルは押せない(旧画面と同じ)。

### 3. 相性の色(Web・iOS で同じ意味。docs/design.md のトークン)
| 意味 | 倍率 | トークン | ライト(文字 / 塗り) | ダーク(文字 / 塗り) |
|---|---|---|---|---|
| 弱点・抜群 | ×2 以上 | danger / danger.soft(今のまま・赤) | 既存 | 既存 |
| 耐性・いまひとつ | ×1/2 以下(無効を除く) | **matchup.resist** / **matchup.resist.soft**(水色系。今の緑から変える) | #0A5E8E / #D7F0FB | #6CCBF5 / #0E2F40 |
| 無効 | ×0 | **matchup.immune** / **matchup.immune.soft**(灰) | #4A5568 / #E6E9EE | #AEB8C6 / #222B38 |
- 値は案。コントラスト 4.5:1(文字と塗り)を満たすように、Web レーンがトークンの検査で確かめ、足りなければ明度だけを調整する(色相は水色系・灰のまま)。
- 記号と文字(「×2 弱点」など)は ADR-0303 §7 のとおり API の値だけから作り、色だけに頼らない(今のまま)。緑(success)は相性に使わない。
- iOS は同じ名前(`matchupResist`・`matchupResistSoft`・`matchupImmune`・`matchupImmuneSoft`)を `PokeCalcDesign` の `ColorToken` に置く。

### 4. 分担

| 段階 | 内容 | 担当 |
|---|---|---|
| A | 偏りの除外・`skewedAttackTypes`・契約 0.10.0・テスト(Go) | タイプバランス |
| B | Web: クライアントの型(gen)・`BalancePanel` のおすすめにタイルと `onPickPokemon`・`limit: 5`・トークンと色の差し替え | Web(段階 2 の組み込みと同じ PR 群) |
| C | iOS: `APIBalanceService` の `limit: 5`・`skewedAttackTypes` の読み取り・`BalanceRecommendationsView` のタイル・`ColorToken` の追加 | iOS(契約の読み取りはタイプバランス) |

### 5. 受け入れ条件
- 偏り(例: みず 2 人が弱い・耐性ゼロの攻撃タイプ)があるとき、その攻撃タイプに弱点を持つ候補が `candidates` に出ない。偏りが無ければ従来と同じ。
- `skewedAttackTypes` が正準順で返る。除外の前後で並びの規則(§1)が保たれる。
- タイルのタップで空き枠に入る・満杯なら押せない。
- 弱点が赤、耐性が水色、無効が灰で、Web と iOS で同じ(緑を相性に使わない)。

## 代替案と不採用の理由
- 候補を入れたときのチーム全体の穴の数で最適化する: 入れ替える 1 体の前提が要り、仕様が膨らむ(ADR-0401 の却下案と同じ)。単純な除外 1 規則で「明らかにおかしい」を防ぐ。
- 弱点を 1 つでも増やす候補を全部除く: どの候補も何かには弱いので、候補が残らない。「すでに偏っている」ものだけに限る。
- 新しい「タイプで絞ったポケモン検索」API を呼ぶ: 応答の `pokemon` がすでに read model の該当ポケモンを返しているので不要。
