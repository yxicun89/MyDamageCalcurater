# ADR-0607: 素早さ比較に追い風・まひ・トリックルームを足す

- 状態: 採用(2026-10-02。ユーザー決定「追い風・まひ・トリックルームを足す。特性(すいすい等)は対象外のまま」)
- 日付: 2026-10-02
- 関連: ADR-0600 §3(素早さの式・スカーフ)、ADR-0601(表・同速の段)、ADR-0602(自分の位置)、ADR-0604(Web 画面)、
  ADR-0702(判定サービスの追い風・トリックルーム。同じ出典・同じ丸め)、ADR-0002(@smogon/calc 0.12.0 の完全固定)、
  CLAUDE.md ドメイン規約(4096 基準の固定小数と五捨五超入。float で近似しない)

## 背景

素早さ比較(docs/speed-design.md)は「ランク・こだわりスカーフ」までしか扱っておらず、追い風・まひ・トリックルームの
状況で自分がどこに入るかを見られない。判定サービスは JD2(ADR-0702)で追い風・トリックルームを入れ済みなので、
式と丸めはそれに揃える。まひは判定サービスにはまだ無い(ADR-0702 却下案の末尾)ので、ここで初めて決める。

表の 6 行(ADR-0601 §2)は「相手側の想定値」で、自分のポケモン(ADR-0602)とは別の側にある。場の効果が
どちらの側に掛かるかを明確にする必要がある。

## 決定

### 1. 効果の適用範囲(どちらの側に掛かるか)

| 効果 | 表(相手側) | 自分 | 入力 |
|---|---|---|---|
| 追い風 | 掛けられる | 掛けられる | 別々に切り替える(表: `tailwind` クエリ / `tableTailwind`、自分: `tailwind`) |
| まひ | 掛けない | 掛けられる | 自分の `paralysis` だけ |
| トリックルーム | 場全体 | 場全体 | 表: `trickRoom` クエリ。位置の入力には持たない(§4) |

- 追い風はゲームでは片側の場の効果なので、表側と自分側を**別々の欄**にする(ADR-0702 の `attackerTailwind` /
  `defenderTailwind` と同じ考え方)。両方 on も許す(両側に追い風が吹いている状況)。
- まひを表の全行に掛けるのは「相手全員がまひ」という現実味の無い想定になるので、自分だけにする。
- 自分の `tailwind` / `paralysis` は `preset` / `custom` だけ。`raw` は「戦闘中の実数値そのもの」を入れるモードなので、
  自分側の補正を重ねない。`raw` に `tailwind` / `paralysis` があれば(false でも)400 `invalid_request`
  (ADR-0602 §2「mode に要らない項目は 400」と同じ規則。JSON `null` は省略と同じ)。`tableTailwind` は全モードで使える。
- すべて省略可・既定 false。**省略した request の応答は 0.4.0 と 1 バイトも変わらない**(後方互換)。

### 2. 追い風 ×2 / スカーフと連結して 1 回だけ丸める

出典は ADR-0702 §2 と同じ `@smogon/calc` 0.12.0 の `dist/mechanics/util.js` の `getFinalSpeed`
(Champions 世代 `Generations.get(0)` も同じ関数を通る)。

```
実数値(engine.RealStats)
  → ランク補正(engine.EffectiveStat)
  → 素早さ補正を 4096 基準で連結(追い風 8192 → こだわりスカーフ 6144 の順に積む)
       1 ステップ: M = (M × mod + 2048) / 4096(切り上げ寄り。4096 から始める)
  → 連結した M を 1 回だけ適用: floor((v × M + 2047) / 4096)(五捨五超入)
  → まひ(§3)
```

- 定数は `tailwindSpeedModifier = 8192`、既存の `scarfSpeedModifier = 6144`、基準は `engine.Modifier4096`。4096 を直書きしない。
- 既存の `applyScarf` はスカーフ単独の連結(M = 6144)と同じ値なので、連結の関数に置き換えても既存の期待値は変わらない。
- 表の `max-scarf` 行に追い風が掛かるときも同じ連結で、**各補正ごとに丸めない**。例(手計算・原典で確認済み):
  - 実数値 91: 追い風 + スカーフ = 91 × 3 = **273**(逐次なら 136 × 2 = 272)
  - 実数値 167: **501**(逐次なら 250 × 2 = 500)。追い風なしでは同速だった「最速スカーフ」と「最速+1」が、
    追い風では 501 と 500 に分かれる(表の段が変わる)。

### 3. まひ ×1/2 は連結の後に別枠で切り捨て

原典(同じ `getFinalSpeed`):

```js
speed = OF32(pokeRound((speed * chainMods(speedMods, 410, 131172)) / 4096));
if (pokemon.hasStatus('par') && !pokemon.hasAbility('Quick Feet')) {
  speed = Math.floor(OF32(speed * (gen.num >= 7 || gen.num === 0 ? 50 : 25)) / 100);
}
```

- Champions 世代(`gen.num === 0`)は 50/100。式は **`floor(v × 50 / 100)`**。4096 基準の補正ではなく、
  連結・五捨五超入の**後**に整数で切り捨てる(依頼の「×0.5・4096 基準・五捨五超入」は、原典ではこの形になる)。
- 定数は `paralysisSpeedPercent = 50` と百分率の分母(名前付き定数)で持ち、0.5 を float で掛けない。
- 順序が値に出る例: 実数値 91 にスカーフ + まひ → 136 → **68**(まひを先にすると 45 → 67)。
  追い風 + スカーフ + まひ → 273 → **136**(まひを先にすると 45 → 90 → 135)。
- はやあし(Quick Feet)の例外は特性なので対象外(ユーザー決定)。

### 4. トリックルームは実数値を変えず、表の段の順だけを反転する

- `GET /api/speed/v1/table?trickRoom=true` は各段の `speed` を変えず、**段の並びだけを昇順(= 行動順)**にする。
- 同速は 1 つの段のまま(同速はトリックルームでも行動順がランダムで、どちらが先か決まらない。ADR-0702 §3 と同じ)。
- **段の中の並び(pokemonId の昇順 → プリセットの順)は反転しない**。段の中は「同じ速さの行の一覧」で、
  行動順の意味を持たないため。反転すると同じ段の表示がトリックルームの有無で入れ替わり、見比べにくい。
- 「自分の位置」の意味の反転:
  - `faster` / `slower` / `tie`(位置の応答)は**素早さの比較のまま**で、トリックルームで入れ替えない
    (ADR-0702 §3 が `attackerSpeed` を加工しないのと同じく、値の意味を 1 つに保つ)。したがって位置の request には
    `trickRoom` を持たない(持っても応答が変わらない欄になる)。未知の欄として 400。
  - トリックルーム中に「自分より先に動く行」は `slower`、「後に動く行」は `faster`。この読み替えは契約
    (`faster` / `slower` の description)に明記し、画面は 1 つの規則で表示する(Web・iOS で割れない)。
  - 画面の境界線は、表示中の段(昇順)に対して「自分より遅い最後の段の後・自分より速い最初の段の前」に引く。

### 5. 検証と、原典との既知の差

- 期待値は手計算し、`@smogon/calc` 0.12.0 の `getFinalSpeed` に種族値を差し替えた個体(`overrides.baseStats`)を
  Champions 世代で通して一致を確かめた(種族値 1 / 71 / 73 / 100 / 255、SP 0 / 32、性格 補正なし / 上昇、
  追い風・まひ・スカーフ・ランクの組み合わせ)。テストは架空データのみ(ADR-0002)。
- **原典との既知の差(今回は変えない)**: 原典の最後の `Math.min(gen.num <= 2 ? 999 : 10000, speed)` は
  Champions(`gen.num === 0`)で 999 の上限になる。speed サービスは既存の値(種族値 255・最速・+6・スカーフ = 2022)から
  この上限を入れておらず、今回もそのまま(追い風を足した最大は 4044)。この上限が Champions のゲーム仕様か
  原典の世代判定の副作用かは未確認で、入れると既存の応答が変わるため、人間の判断に回す(plan.md のブロッカーに記載する)。
- `RawSpeedRange`(mode=raw の受け付け範囲。ADR-0602 §3)は**広げない**。式の入力に追い風・まひを含めると
  範囲が 2〜4044 に広がるが、既存の範囲(4〜2022)と既存テストの総当たりを保つ。raw で 2022 を超える値・4 未満の値を
  入れたい場合は、preset / custom の自分の追い風・まひを使う。

### 6. コアの形(`internal/speed` は純粋なまま)

- `Input` に `Tailwind bool`・`Paralysis bool` を足す(`Scarf` と同じ「その個体の素早さに乗る補正」)。
- 表の場の効果は `TableField{Tailwind, TrickRoom bool}` にし、`BuildTable(roster, presets, field TableField)` の
  第 3 引数で渡す。ADR-0702 §4 と同じく**関数は 1 本のまま**(場の効果なし版を別に残すと、呼び出し側が古い方を呼んで
  効果を黙って落とす)。既存テストは呼び出しに `TableField{}` を足しただけで、期待値は 1 つも変えていない。
- `PositionRequest` に `Tailwind`・`Paralysis`・`TableTailwind bool` を足す。位置の表は
  `TableField{Tailwind: TableTailwind}` で組む。raw は `Value` をそのまま使い、`Tailwind` / `Paralysis` を掛けない
  (余計な項目の検査は HTTP 層。ADR-0602 §2 の分担のまま)。

## 受け入れ条件

1. `services/speed/api/openapi.yaml`(0.5.0)の `GET /api/speed/v1/table` に省略可の `tailwind` / `trickRoom`(boolean、既定 false)、
   `PositionRequest` に省略可の `tailwind` / `paralysis` / `tableTailwind`(boolean)がある。応答のスキーマは変えない。
   `make speed-gen` と `web/src/speed/speed.gen.ts` の生成物が最新。
2. 追い風は実数値を ×2 し、こだわりスカーフと 4096 基準で連結して 1 回だけ五捨五超入する(91 → 273、167 → 501)。
3. まひは連結の後に `floor(v × 50 / 100)`(91 → 45、91 + スカーフ → 68、91 + 追い風 + スカーフ → 136、下限の組み合わせ → 2)。
4. 表の `tailwind=true` は全行に掛かり、`trickRoom=true` は段の順だけを逆にする(実数値・段の中の並び・同速のまとめは変えない)。
5. 位置の `tailwind` / `paralysis` は自分だけ、`tableTailwind` は表の全行に掛かる。`faster` / `slower` / `tie` は素早さの比較のまま。
6. 省略・false・null は従来と同じ応答。`raw` に `tailwind` / `paralysis`、真偽値でない値、表のクエリの不正値・空・重複は 400
   `invalid_request`(判定順はヘッダー → クエリ/body → 503 のまま)。
7. Web: 左に「場の状態」(追い風(相手側)・トリックルーム)、右の preset / custom に追い風(自分側)・まひ。
   トリックルーム中は遅い順の表・反転した境界・「先に動く/後に動く」の表示。すべて off なら従来と同じ呼び出し。
8. `make speed-test` / `speed-lint` / `speed-build` と Web の test / lint / typecheck が通る。`internal/speed` は I/O を持たない。

## 却下した案

- **追い風を 1 つのスイッチで表と自分の両方に掛ける**: ゲームでは片側の効果で、両側同時は特殊な状況。片側だけの
  比較(自分だけ追い風)が主な使い方なので、別々の欄にする。
- **トリックルームで `faster` / `slower` を入れ替える、または `movesBefore` / `movesAfter` を足す**: 前者は同じ名前の欄が
  状況で別の意味になる。後者は応答の破壊的でない追加だが、`faster` / `slower` と常に同じ値の組み替えで情報が増えず、
  既存の応答の完全一致テストの期待値をすべて書き換えることになる。契約の description に読み替えを明記する形にした。
- **段の中の並びも反転する**: §4 のとおり。段の中は行動順の意味を持たない。
- **まひを 4096 基準の補正(2048)として連結に入れる**: 原典は連結の後に別枠の整数切り捨てで、91 + スカーフで 68 と 67 に割れる。
- **`RawSpeedRange` を追い風・まひ込みに広げる**: §5。既存の範囲と総当たりのテストを変えることになり、raw の意味
  (補正済みの値を自分で入れる)に対して得るものが小さい。
- **原典の 999 上限を入れる**: §5。既存の応答が変わるうえ、ゲーム仕様か未確認。
