# ADR-0209: M2 保存データの保持・削除・端末 ID 境界

- 状態: 提案(2026-09-23。issue #103 の設計。受け入れ条件は spec-writer が先に書き、critic の独立レビュー待ち。record-svc / team-svc の実装は P5-3 / P5-4 で、この ADR に従う)
- 日付: 2026-09-23
- 関連: issue #103(監査ベース `264ae5963bb7e867a88ff5c79fade257a10edeb4`)、
  ADR-0012(サービス境界)、ADR-0200(API 契約とエラー語彙)、ADR-0202(gateway のルーティングとヘッダ検証)、
  ADR-0208(契約に上限を書く前例)、docs/ai-shared/DECISIONS.md 2026-09-23「issue #103・#111 の needs-decision をユーザーが決定」、
  docs/requirements.md §3(認証なし)・§4(アーキテクチャ)・§6(データモデル骨格)・§8(構築データは team-svc)、
  plan.md P5-1〜P5-4・P5-5・P7-4

## 背景

`record-svc` / `team-svc`(P5-3 / P5-4)は、認証のない端末 ID で分けたデータを TiDB に持つ。
要件は自動保存・履歴由来の推薦・構築保存を求めているが(requirements.md §2・§6)、保持期間・利用者による削除・
端末 ID を失ったときの扱いが決まっていない。Codex の監査で次が指摘された。

- 端末 ID を「所有権の証明」として扱うのか「単なる分割キー」として扱うのかが契約に書いていない
  (`api/openapi.yaml` の `DeviceId` / `SessionId` は形式と gateway の検証だけを定めていた)。
- 端末 ID は Web では localStorage、iOS では UserDefaults に平文で持ち、失われたら新しい値を作る
  (`web/src/api/clientIds.ts`、`ios/PokeCalcKit/Sources/PokeCalcCore/ClientIdentity.swift`)。
  つまり「秘密として守れない値」であり、同時に「失うと元のデータに戻れない値」である。
- 生の計算イベントを無期限に持つのか、推薦の集計後に捨てるのかが未決。
- 削除の範囲(record DB / team DB / NATS JetStream / バックアップ)が未決。

ユーザー決定(DECISIONS.md 2026-09-23): **一定期間で自動失効させる**(例: 未使用90日。具体的な日数は実装レーンに委任)。
**無期限保持はしない**。

この ADR は、その決定を具体的な分類・日数・API 契約・受け入れテストにする。実装(スキーマ・ハンドラ・ジョブ)は含まない。

## 決定

### 1. v1 の公開範囲

v1 は**個人利用 + Tailscale 内**に固定する(requirements.md §3「可用性」。issue の既定案どおり)。
インターネットに公開する前に、**認証方式を別 ADR で必須決定**とする。この ADR は認証を導入しない。

理由: 以下 §2 のとおり端末 ID は秘密として守れない。公開網に出すなら、この ADR の境界(端末 ID による分割)は
アクセス制御として不十分で、認証が前提条件になる。「今は公開しない」と決めておくことで、
分割キー方式が「認証の代わり」に見えないようにする。

### 2. 端末 ID / セッション ID の位置づけ(`api/openapi.yaml` に明記済み)

| 値 | 位置づけ | 明示的に**そうではない**もの |
|---|---|---|
| `X-Device-Id` | 保存データの**分割キー**(このキーでデータを分け、削除・保持期間を判定する) | 秘密、認証、所有権の証明、ベアラトークン |
| `X-Session-Id` | 計算イベントに「どの一連の操作か」として**記録するだけ** | 分割キー(分離・削除・保持期間の判定に使わない) |

- 端末 ID は**リクエストヘッダだけを正**とする。ボディ・クエリ・パスで端末 ID を受け取らない
  (受け口を二重にすると、どちらが正かの分岐と偽装口が生まれる)。ボディに `deviceId` を入れた要求は
  400 `unknown_field`(既存語彙。ADR-0200)。
- 端末 ID は秘密ではないので、漏えい時の失効・再発行という概念を持たない。**ローテーションの仕組みは作らない**
  (新しい端末 ID は「別の端末」であり、前のデータには繋がらない)。
- この決定は `components/parameters/DeviceId` / `SessionId` の description に書き、
  `services/internal/api/client_id_semantics_test.go` が契約から消えていないことを検査する。

### 3. データ分類と保持期間

「日」は UTC の日付境界ではなく、経過時間(24h × 日数)で判定する(タイムゾーンの扱いを持ち込まない)。
`last_seen_at` の書き込み抑止(§4「1日1回に抑える」)も同じ規則で、「24時間以内なら書かない」と読む
(UTC の日付が変わったかどうかではない)。

| # | データ分類 | 目的 | 保存場所 | 分割キー | 保持期間 | 削除契機 | バックアップからの消去 | ログに残してよい項目 |
|---|---|---|---|---|---|---|---|---|
| 1 | `calc_events`(生の計算イベント) | 履歴表示・推薦の集計 | TiDB record DB | `device_id` | **作成から90日**(§4) | 日次の失効ジョブ / 端末単位の全削除(§5) | バックアップ世代の失効(30日)+ 復元手順での再適用(§9) | 端末 ID・セッション ID・操作名・件数・所要時間・エラーコード |
| 2 | 推薦の集計(「よく使う相手」。頻度×時間減衰) | 推薦の提示 | TiDB record DB | `device_id` | **独自の保持期間を持たない**。生イベント(#1)から再計算できる派生データとして扱い、#1 と同時に失効する | #1 の削除後の再計算 / 端末単位の全削除 | 同上 | 同上(集計の中身は出さない) |
| 3 | `favorites`(お気に入り) | 手動ピン留め | TiDB record DB | `device_id` | **`max(devices.last_seen_at, 行.updated_at)` から540日**(§4) | 失効ジョブ / 利用者の個別削除 / 端末単位の全削除 | 同上 | 同上(ピン留めの中身は出さない) |
| 4 | `teams` / `team_members`(構築) | 構築ビルダー | TiDB team DB | `device_id` | **`max(devices.last_seen_at, 行.updated_at)` から540日**(§4。team-svc も計算イベントを購読して自分の `devices.last_seen_at` を更新する) | 失効ジョブ / 利用者の個別削除 / 端末単位の全削除 | 同上 | 同上(構築名・ニックネーム・個体の中身は出さない) |
| 5 | `devices`(端末ごとの `last_seen_at` と削除の墓石 `purged_at`。record DB と team DB がそれぞれ自分の分を持つ) | 失効判定・削除後のイベント再出現の抑止(§7) | TiDB record DB / team DB | `device_id` | **行自体**はその端末のデータ(#1〜#4)が全て無くなってから30日で失効ジョブが消す(使われ続ける端末の行は消えない)。**`purged_at` の値**は削除のたびに更新され(§5.2)、30日経過後もクリアしない(§7 の「30日」は判定に使う猶予の長さであり、値の寿命ではない) | 失効ジョブ(行自体) | 同上。**バックアップに必ず含める**(§9) | 端末 ID・`last_seen_at`・`purged_at` |
| 5b | **purge journal**(削除要求を受け付けた端末 ID と時刻だけの追記専用ログ。record DB / team DB がそれぞれ持つ**うえ**で、DB のバックアップ世代とは独立の場所〈P7-4 が決める。§9-2〉にも同時に追記する) | バックアップ復元時に、復元世代より後に来た削除要求を再適用するため(§9) | TiDB record DB / team DB + P7-4 が決める独立の保存先 | `device_id` | **90日**(#7 のバックアップ復元の想定範囲より長く取る) | 期限切れの行の削除(データを含まないので保持コストは小さい) | **DB のバックアップとは別に、独立の保存先で必ず保持する**(DB 側の世代が全損しても journal だけは残る想定。§9-2) | 端末 ID・削除要求の受付時刻 |
| 6 | NATS JetStream の計算イベント(calc-svc → record-svc **と team-svc**〈§4〉の中継) | 非同期保存(requirements.md §4)・record は保存本体、team は `devices.last_seen_at` の更新だけ | JetStream のストリーム | subject に `device_id` を含む | **`max_age` 7日**、**両方の consumer が ack したら破棄**(record と team は別々の durable consumer を持つので、片方の ack ではストリームから消えない。P5-2) | ack / `max_age` | **バックアップの対象にしない**(復元で再生しない) | ストリーム名・シーケンス番号・consumer 名 |
| 7 | バックアップ(MySQL / TiDB。P7-4) | 障害復旧 | P7-4 で決める保存先 | ― | **30日(世代の上限)** | 世代の失効 | ― | 世代 ID・取得時刻・対象 DB |

**ログに残さない**(どの分類でも共通。coding-rules §1): 個体の中身(種族・技・持ち物・特性・性格・SP)、ダメージの数値、
構築名・ポケモンのニックネーム、お気に入りの中身、リクエスト / レスポンスの本文そのもの。
理由: 端末 ID・セッション ID はクライアントが作るランダム UUID で、それ自体は個人を特定せず秘密でもないので全体を出してよい。
一方、構築名・ニックネームは利用者の自由入力で、個人を特定しうる文字列が入りうる。

**#3 の設計上の制約(データレーンへ)**: `favorites` は `calc_events` を参照しない。
ピン留めした時点の**個体スナップショットを自分で持つ**(record-svc は個体を参照せず計算時点のスナップショットを保存する。
requirements.md §8)。#1 が90日で消えても #3 が壊れないための条件で、外部キーで繋ぐと保持期間の差が矛盾する。

### 4. 日数の根拠と「未使用90日」の定義

#### 生の計算イベント: 作成から90日

ユーザー決定の「例: 未使用90日」を、**イベントの作成日時から90日**と定義する(最終アクセス日時からにしない)。

- 集計は「頻度×時間減衰」(requirements.md §2)なので、古いイベントはもともと寄与しない。
  時間減衰の半減期を仮に2週間とすれば、90日前のイベントの重みは 2^(−90/14) ≒ 0.8% で、実質ゼロ。
  つまり「減衰で無視できるほど古くなった分は持たない」だけであり、推薦の質を落とさない
  (半減期そのものは P5-3 で決める。保持期間より短いこと、が満たすべき関係)。
- 90日はおおよそ1シーズン分で、「最近よく計算する相手」という機能の体感と一致する。
- **イベント単位の最終アクセスは採らない**: `calc_events` は追記専用にしたい表で、
  行ごとに `last_accessed_at` を持つと履歴を1画面開くたびに数十行の UPDATE が出る(TiDB では分散トランザクションのコスト)。
- 「未使用」はイベント単位ではなく**端末単位**で意味を持つ。端末が90日使われなければ、
  作成から90日の規則でその端末のイベントは自然に全部消える(= ユーザー決定の「未使用90日」と一致する)。
  使い続けている端末では古いイベントだけが落ちる(ローリング90日)。

代替案: 30日(月1回程度の利用者で履歴が空になり、推薦が育たない)、365日(行数が約4倍。個人利用では意味のない蓄積)。

#### 構築・お気に入り: 端末の最終アクセスから540日(18か月)

「無期限保持はしない」(ユーザー決定)と「利用者の意思がある限りは保持する」を両立させる形として、
**基準を端末の最終アクセス(`devices.last_seen_at`)に置く**。使い続けている端末のデータは消えない。

- 構築は作るのに手間がかかるデータで、90日で消えると実害が大きい。
  ユーザー決定は「無期限にしない」であって「短命にせよ」ではない。
- 540日まったく接続しない端末は、離脱(端末の紛失・アンインストール・ストレージ消去)と見なせる。
  iOS は無料 Apple ID 配布で7日ごとの再署名が必要(requirements.md §3)なので、1年半の無接続は継続利用と両立しない。
- したがって540日で消えるのは実質「§8 の孤児データ」だけになり、期限削除の主目的と一致する。

代替案: 365日(1シーズン空けただけで消える恐れがある)、730日(2年。実質「無期限に近い」でユーザー決定の趣旨に反する)。

#### `last_seen_at` の更新(書き込み増幅を避ける。かつ「使い続けている利用者のデータが消える」経路を作らない)

**失効の判定は `devices.last_seen_at` 単独ではなく、`max(devices.last_seen_at, 対象行の updated_at)` から540日で行う**
(#3・#4 の失効ジョブはこの式で判定する)。理由: `devices.last_seen_at` は「HTTP 要求を受けた」ときにしか更新されないが、
自動保存される計算イベント(#1)は calc-svc → JetStream → record-svc の**非同期イベント経路**で、要求を経由しない。
「ダメージ計算だけを使い続け、履歴・構築の画面を一度も開かない端末」では `devices.last_seen_at` が更新されないまま
`favorites`・`teams` の行だけが古いままの状態が起こりうるので、`last_seen_at` 単独で判定すると
アクティブな利用者のデータが540日で消える(構築を守るという §4 の目的に反する)。`対象行の updated_at` を式に含めることで、
利用者がその行(お気に入り・構築)自体を最後に触った時刻も加味する。

- record-svc / team-svc は、**端末 ID を含む HTTP 要求を受けたとき**に自分の DB の `devices.last_seen_at` を upsert する
  (サービスは自分の DB にだけ触る。CLAUDE.md 絶対ルール4)。更新は**日単位**で行い、
  保存済みの `last_seen_at` から24時間経っていなければ書かない(§3の「日」の定義どおり。1日1回程度に抑える)。
- **record-svc は、JetStream からのイベント消費時にも `devices.last_seen_at` を同じ規則で更新する**
  (自動保存だけを使い続ける端末を「未使用」と誤判定しないため)。
- **team-svc も同じイベント(#6)を購読し、自分の DB の `devices.last_seen_at` だけを同じ規則で更新する**
  (計算 API だけを使い続け、構築画面を一度も開かない端末で `teams`/`team_members` が誤って失効しないため)。
  team-svc はイベントの中身〈計算結果・個体〉を保存せず、購読の目的は自分の `devices.last_seen_at` の更新だけ
  (他サービスのデータには触らない。CLAUDE.md 絶対ルール4)。これにより record・team のどちらも、
  「HTTP 要求を経由しない自動保存の継続」だけで `last_seen_at` が新しく保たれる。
- `favorites`・`teams`・`team_members` の各行は、行自体の `updated_at`(作成・更新時に書く通常のカラム)を持つ。
  失効ジョブは行ごとに `max(devices.last_seen_at, 行.updated_at)` を計算し、そこから540日経過していれば消す
  (`devices.last_seen_at` が上記のとおり record・team それぞれで独立に新しく保たれるので、`max()` は
  「行自体を最後に触った操作」と「端末が使われ続けているという事実」の両方を拾う)。

#### 失効ジョブ

- 日次の CronJob(record 用・team 用をそれぞれのサービスが持つ)。
- **冪等**(何度走らせても結果が同じ)で、途中で落ちても次回が続きを消す。
- 1回の実行で消す行数に上限を持ち、上限に達したら「残りあり」で終了して次回に回す(長いトランザクションを作らない)。
- **失効ジョブが止まっても計算 API は成功する**(CLAUDE.md 絶対ルール5)。ジョブの失敗はメトリクスとログで見る。

### 5. 端末単位の全削除 API(契約。P5-3 / P5-4 で `api/openapi.yaml` へ入れる)

#### 5.1 サービスごとに1つ置き、gateway では束ねない

- `DELETE /api/record/device-data` — operationId `deleteRecordDeviceData`、タグ `record`
- `DELETE /api/team/device-data` — operationId `deleteTeamDeviceData`、タグ `team`

クライアント(Web / iOS)の「この端末のデータを削除」は、この2つを順に呼ぶ。
片方が失敗したら「一部が残っている」と伝えて再試行させる(§8 の文言)。

gateway に `DELETE /api/me/data` のような1本を置いて fan-out させる案は却下した(§却下した案)。
パス名に `me` を使わないのは、§2 で否定した「本人性・所有権」の語感を契約に持ち込まないため。

この API は **JetStream のメッセージ本体は消さない**(#6。最長7日で自然に ack/`max_age` により消える)。
削除の即時性が必要なのは DB 側(record/team DB)で、JetStream は墓石(§7)がイベントの再出現を防ぐので、
メッセージ自体を能動的に消す必要が無い。

#### 5.2 冪等性と繰り返し(ジョブ ID を発行しない)

- 削除は**同期**で行い、1回の呼び出しで消す行数に上限(実装の設定値)を置く。
- 上限に達したら `status: partial` を返す。クライアントは**同じ要求をもう一度送る**。
  要求は端末 ID だけで決まるので、何回送っても安全(冪等)で、サーバー側に進行状態を持たない。
- すでに何も無い端末への削除も **200 `completed`**(`deleted` は全て 0)。404 は返さない。
- 削除の順序は record-svc 内で (1) 墓石 `purged_at` を立てる・purge journal に追記(#5b) → (2) `calc_events` → (3) 集計 → (4) `favorites`。
  先に墓石を立てるのは、削除中に JetStream から届くイベントを捨てられるようにするため(§7)。
  `calc_events` を集計より先に消すのは、`partial` で処理が中断しても「集計だけが `calc_events` から再生成されて残る」
  (削除の途中経過が逆走して見える)ことを避けるため。失効ジョブ・集計の再計算ジョブは、`purged_at` が立っている
  端末の行には触らない(削除処理と競合させない)。
- `occurred_at`(calc-svc の時計)と `purged_at`(record-svc の時計)はサーバー間で完全には一致しない。
  この ADR は同一 Mac 上の k3d(クラスタ内の時計は事実上同期)を前提にし、クロックスキューの補正猶予は設けない。
  クラウド分散環境に移すときは NTP 同期の精度を確認し、必要なら猶予(数秒)を検討する。
- **`purged_at` の再発行**: `DELETE` が呼ばれるたびに、**`purged_at` を現在時刻に更新する**(`partial` の繰り返しも含め、
  毎回)。トレードオフとして、`partial` を繰り返している最中に発生した計算イベントは、次の呼び出しで `purged_at` が
  進むたびに「削除後」の基準から外れうる(捨てられる可能性がある)。これは個人利用規模(§5.2。1回の削除操作は
  数秒〜十数秒で `completed` に達する)では実害がほぼ無い一方、**「保持しない」実装だと、削除完了後に利用者が
  もう一度「この端末のデータを削除」を押しても、その間に溜まった新しいイベントを消せない**(利用者の「削除して」
  という意図に反する)ため、更新する方を選ぶ。AC-P4「削除後の計算は残る」は、**削除操作の呼び出しが終わってから**
  発生したイベントに限って保証する(削除処理の実行中に発生したイベントの扱いは保証しない)。

理由(同期 + 繰り返しにした): 個人利用1端末の90日分は多くても数千行で、1回で終わる規模。
非同期ジョブにするとジョブ ID・進行状態・結果の保持期間という別のライフサイクルが増える。
一方、gateway の上流タイムアウトは10秒(ADR-0202)なので、無制限の同期削除も許さない。
`partial` の繰り返しは、その両方を満たす最小の形。

### 6. 端末 ID によるデータ分離(record / team の全操作に共通の規則)

1. すべての読み書きは `WHERE device_id = <X-Device-Id の値>` を必ず持つ。端末 ID の絞り込みを省く経路を作らない。
2. リソース ID をパスに受ける操作(`/api/team/teams/{teamId}` など)は、**先に端末 ID で絞ってから ID を照合**する。
   他の端末のリソースを指した場合は **404 `not_found`**(403 にしない)。
   理由: 403 は「あるが見せない」= 所有権の概念を作ってしまい、§2 の決定に反する。存在の有無も漏らさない。
3. 一覧・検索・集計は端末内だけを見る。集計に他端末のイベントを混ぜない(推薦の学習も端末内で閉じる)。
4. 端末 ID をボディ・クエリで受け取らない(§2)。送られた場合は 400 `unknown_field`。
5. レスポンスに他端末の情報(件数・存在の有無を含む)を出さない。

### 7. NATS JetStream の未処理イベントと削除の競合

全削除の後に、削除前に発行された計算イベントが JetStream から届いてデータが復活しうる。これを**墓石**で防ぐ。

- record-svc は `devices.purged_at`(削除を受け付けた時刻)を持つ。
- イベントの消費側は、`occurred_at <= purged_at` のイベントを**保存せずに ack して捨てる**(再配送させない)。
- `occurred_at > purged_at` のイベントは通常どおり保存する(削除の後に行った計算は残る。利用者の期待どおり)。
- `occurred_at <= purged_at` の判定に使う猶予は**30日**(#5。`purged_at` の値自体はクリアしない。#5 の注記)。
  JetStream の `max_age` は7日(#6)なので、30日は「未処理のまま残りうる最長の期間」より十分に長い。
  この関係(判定の猶予30日 > `max_age`7日)を壊さないこと。
- `occurred_at` は calc-svc がイベントに載せる発生時刻を使う(record-svc の受信時刻ではない)。
  受信時刻で判定すると、削除直前に発生したイベントが削除後に受信されて生き残る。
- 墓石は端末 ID と時刻だけで、利用者のデータを含まない(だから削除要求の後も持てる)。
- 墓石とは別に、**purge journal**(#5b)へも同じ削除要求を追記する。理由は §9 の復元時の再適用のため
  (`devices.purged_at` はバックアップ世代の内容がそのまま戻るので、世代取得**後**に来た削除要求を復元後に知る手段が要る。
  journal は追記専用でバックアップ復元でも消えず、`purged_at` を書き込む代わりに「そのまま再生する」ログとして使う)。

### 8. 端末 ID を失ったときの扱い(Web / iOS への依頼)

**回復手段は用意しない**。端末 ID が変わると前のデータには戻れない(§2: 秘密でない値を認証に使わないことの裏返し)。
残された孤児データは §3 の保持期間(イベント90日 / 構築・お気に入り540日)で自動的に消える。

Web / iOS レーンへ渡す文言案(そのままの文でなくてよい。趣旨を満たすこと。実装は各レーン):

設定画面の説明:
- 「アカウントはありません。履歴・お気に入り・構築は、この端末に割り当てた ID でサーバーに保存しています。」
- 「ID が変わると(Web: ブラウザのサイトデータを消したとき / iOS: アプリを削除して入れ直したとき)、
  前のデータは開けなくなります。元に戻す方法はありません。」
- 「開けなくなったデータは自動的に消えます。計算の履歴は記録から90日、お気に入りと構築は最後に使った日から18か月です。」

削除の操作:
- ボタン: 「この端末のデータを削除」
- 確認: 「履歴・お気に入り・構築をサーバーから削除します。元に戻せません。」
- 実行中: 「削除しています…」
- `partial` のとき: 「まだ残っています。続けて削除します。」(自動で再送するか、再試行ボタンを出す)
- 失敗(503 / 通信不能)のとき: 「サーバーに届きませんでした。通信を確認してもう一度お試しください。」
- 完了: 「削除しました。」(record / team の両方が `completed` になってから出す)

### 9. バックアップ / 復元との整合(P7-4)

復元はバックアップ時点の状態を戻すので、**期限切れ・削除済みのデータが復活しうる**。次を P7-4 の要件とする。

**重要な区別**: `devices.purged_at`(墓石)はバックアップ世代の中身としてそのまま戻るので、**世代を取得した時点より前**の削除要求にしか効かない。
世代取得の**後**に来た削除要求(例: 世代を取った直後に利用者が削除し、その後で障害が起きて世代から復元する場合)には、
墓石は世代に含まれておらず、再適用しても何も消えない。これを防ぐのが #5b の **purge journal**(バックアップ復元でも消えない
追記専用ログ)で、journal 自体は世代を跨いで別の場所(または世代の対象外)に保持する。

1. バックアップには **`devices`(墓石 `purged_at` を含む)を必ず含める**。含まないバックアップは復元に使えない
   (削除要求を再適用できないため)。
2. **purge journal(#5b)は、DB のバックアップ世代とは独立に保持する**(journal 自体の保持期間は90日。#5b)。
   耐久性の担保: 削除要求を受け付けた時点で、DB のテーブルへの追記と**同時に**、DB 外の独立した保存先
   (P7-4 が決める。追記専用)へも書く。**復元時に参照する journal の正はこちらの独立した保存先**であり、
   DB 側の世代が(クラスタ全損等で)丸ごと失われても journal だけは残る前提にする。
   復元手順は journal をバックアップ世代と別に取得し、世代の取得時刻以降に記録された削除要求も対象にする。
3. 復元の手順は、**サービスを Ready にする前に**次の3つを終える:
   a. 墓石の再適用 — `purged_at` がある端末のデータを、その時刻を基準にもう一度削除する。
   b. **purge journal の再適用** — journal に記録された全端末について、削除を(すでに済んでいても冪等なので)もう一度実行する。
      これが世代取得後に来た削除要求を復元後に反映する唯一の経路。
   c. 失効ジョブの強制1回実行 — §3 の保持期間を現在時刻で再判定して消す。
4. JetStream はバックアップの対象にしない。復元時にイベントを再生しない(再生すると削除済みデータが戻る)。
5. バックアップ世代は30日で失効させる。したがって**削除要求から30日以内にバックアップからも物理的に消える**
   (これが issue の言う「バックアップからの期限付き消去」)。purge journal の保持(90日)はバックアップ世代の失効(30日)より
   長く取り、「世代を取得してから複数世代分の時間が経って初めて復元する」場合でも journal が残っていることを保証する。
6. 復元の検証(P7-4 の復元テスト)には、「**世代取得より前**に削除済みの端末のデータが復元後に出てこない」(墓石の再適用)と、
   「**世代取得より後**に削除された端末のデータが復元後に出てこない」(journal の再適用)の両方のケースを含める(AC-B2・AC-B2b)。

### 10. `api/openapi.yaml` に今入れるもの / 入れないもの

**今入れた**: `components/parameters/DeviceId` / `SessionId` の description に §2 の位置づけ。
`make gen`(Go / TypeScript)と `make ios-gen`(Swift)を実行済み。

**今は入れない**: §5 のパス・スキーマ・`store_unavailable`。P5-3 / P5-4 の実装と同じ変更で入れる。理由:

1. 生成物は**単一の `api.ServerInterface`**(oapi-codegen の echo5-server + strict-server、`skip-prune: true`)で、
   各サービスが全操作のメソッドを持つ必要がある。既存の前例は calc-svc の `GetMasterExport`
   (`services/calc/internal/httpapi/readiness.go`: 「ルートに登録しない。呼ばれたら 404 not_found」)。
   record / team の操作を今足すと、calc-svc と pokedex-svc に「常に 404 を返すだけの空メソッド」が増え、
   実装の無い契約のためだけに他サービスの本体コードを触ることになる。
2. gateway のルーティング表(ADR-0202 §3)に `/api/record` / `/api/team` が無いので、
   契約に載せても実際の応答は常に 404 `not_found` になる。「契約にあるのに必ず 404」は契約を嘘にする。
3. Web / iOS の生成クライアントに、呼べない操作の型が生える(P4 / P6 のレーンに無駄な追従を強いる)。

§5 の本文をこの ADR に置く間は、**契約の正はこの ADR §5.3** とする。
openapi.yaml に移した時点で §5.3 を「移動済み(正は `api/openapi.yaml`)」に書き換える(coding-rules §2「単一の正」)。

**P5-3 / P5-4 の成果物には gateway(ADR-0202)の変更を含む**(クライアントの唯一の入口は gateway。requirements.md §4)。
契約を openapi.yaml に移すのと同じ区切りで、以下も行う:

1. gateway のルーティング表(ADR-0202 §3)に `/api/record/*` → record-svc、`/api/team/*` → team-svc を追加する
   (calc・pokedex と同じ形。ヘッダ検証あり)。
2. `services/gateway/internal/httpapi/cors.go` の `corsAllowMethods`(現状 `"GET, POST, OPTIONS"`)に
   **`DELETE`**(§5 の全削除 API)と、team の CRUD(AC-D2 が前提にする PUT・必要なら PATCH)を追加する。
   これを忘れると、別オリジン(Vite 開発サーバ等)のブラウザからのプリフライトが DELETE を許可されず、
   Web から全削除 API を呼べない。
3. ADR-0202 に、上記1・2の追記を行う(ルーティング表とCORSの許可メソッドの更新)。

## 受け入れ条件(P5-3 / P5-4 の完了条件。実装が無いので今はテストの仕様)

分離(record / team の両方に同じ形で置く。AC-D5 は record のみ):

- **AC-D1** 端末 A が作ったデータは、端末 B の一覧・検索に出ない(同じデータを A で作り、B で一覧して 0 件)。
- **AC-D2** 端末 B が、端末 A のリソース ID を指して GET / PUT / DELETE すると **404 `not_found`**。
  403 を返さない。応答本文に A の情報(名前・存在の有無・件数)を含まない。
- **AC-D3** ボディ・クエリに `deviceId` を入れた要求は 400 `unknown_field`。ヘッダの端末 ID を上書きできない。
- **AC-D4** ヘッダの欠落・不正は gateway で 400 `missing_header` / `invalid_header`(ADR-0202 §4 の再確認)。
- **AC-D5** 「よく使う相手」の集計に他端末のイベントが混ざらない(A で 10 件、B で 1 件作り、B の集計が 1 件分だけを反映)。

全削除(§5):

- **AC-P1** 冪等: 削除を2回呼ぶと2回目も 200 `completed` で、`deleted` は全て 0。
- **AC-P2** 繰り返し: 1回の上限を小さく設定した状態で、1回目が `partial`、繰り返すと `completed` になり、
  最終的に行が残らない。途中で別の要求が割り込んでも壊れない。
- **AC-P3** 墓石: 削除後に `occurred_at <= purgedAt` のイベントを JetStream から流しても保存されず、ack される
  (再配送のループにならない)。
- **AC-P4** 墓石の境界: `occurred_at > purgedAt` のイベントは保存される(削除の呼び出しが終わった後の計算は残る)。
- **AC-P1b** `purged_at` の再発行: 削除が `completed` になった端末にもう一度 `DELETE` を呼ぶと、`purgedAt` は
  1回目より新しい時刻になる(§5.2「呼ばれるたびに現在時刻へ更新する」の確認)。
- **AC-P5** 削除は他端末のデータを消さない(A を削除して B のデータが全て残る)。
- **AC-P6** 部分障害: 削除の途中で DB が落ちたら 503 `store_unavailable`。墓石は立っており、
  再送すると残りが消えて `completed` になる。
- **AC-P7** 境界: `DELETE /api/record/device-data` は team DB を消さず、その逆も同じ(サービスは自分の DB だけ。絶対ルール4)。
- **AC-P8** gateway: `OPTIONS /api/record/device-data`(と `/api/team/device-data`)に
  `Access-Control-Request-Method: DELETE` を付けたプリフライトが、許可オリジンに対して DELETE を許可して返る
  (§10 の gateway 変更の確認)。

保持期間(§3・§4):

- **AC-R1** 作成から91日のイベントは失効ジョブで消え、89日のものは残る(境界を両側から見る)。
  **ちょうど90日(2160時間)のイベントは残る**(保持期間は「以内は残す」の意味。削除条件は `経過時間 > 90日`。
  2160時間を1秒でも超えたら次回の失効ジョブで消える)。
- **AC-R2** `max(devices.last_seen_at, 行.updated_at)` から541日経過した構築・お気に入りは消え、539日のものは残る。
  **ちょうど540日のものは残る**(AC-R1 と同じ規則。削除条件は `経過時間 > 540日`)。
- **AC-R2b** `devices.last_seen_at` は540日以上前(要求を受けていない)だが、対象行の `updated_at` が540日以内(利用者が
  最近その行を作成・更新した)の場合、その行は消えない(§4「最終アクセス単独ではなく行の更新も見る」の確認)。
- **AC-R2c** 自動保存イベント(#1)だけを継続的に受けている端末(HTTP 要求は無い)で、record-svc の `devices.last_seen_at`
  がイベント消費のたびに更新され、540日以内に保たれる(§4)。
- **AC-R2d** 同じ条件(計算 API だけを使い続け、構築画面を一度も開かない端末)で、**team-svc の `devices.last_seen_at`
  も**同じイベントの消費で540日以内に保たれ、`teams`/`team_members` が消えない(§4「team-svc も同じイベントを購読する」の確認。
  record 側だけでなく team 側の失効判定式に実効性があることを直接検査する)。
- **AC-R3** 失効ジョブは冪等で、同じ入力に対して2回走らせても結果が同じ。上限に達したら「残りあり」で終わる。
- **AC-R4** 失効ジョブ・record-svc・TiDB・NATS が落ちていても、計算 API(`/api/calc/*`)は成功を返す(絶対ルール5)。
- **AC-R5** `last_seen_at` は直近の更新から24時間以内の2回目の要求では更新されない(書き込み増幅の抑止)。
- **AC-R6** 集計(#2)は生イベント(#1)から再計算でき、生イベントを消したあとに集計だけが残らない。

バックアップ / 復元(§9。P7-4 の完了条件):

- **AC-B1** バックアップに `devices`(墓石を含む)が含まれる。含まないバックアップは復元手順が拒否する。
- **AC-B2** 復元テスト(世代取得**前**の削除): 削除済みの端末と期限切れのイベントを含むバックアップから復元し、
  サービスが Ready になった後にどちらも API から見えない(墓石の再適用 + 失効ジョブの強制実行が済んでいる)。
- **AC-B2b** 復元テスト(世代取得**後**の削除): バックアップ世代を取得した後に別の端末を削除し、
  その世代から復元してもその端末のデータが API から見えない(purge journal の再適用が済んでいる。§9-3b)。
- **AC-B3** 復元で JetStream のイベントを再生しない。

ログ(§3):

- **AC-L1** record / team のログに、個体の中身・ダメージの数値・構築名・ニックネーム・要求本文が出ない。
  端末 ID・セッション ID・操作名・件数・所要時間・エラーコードは出る。

契約(§10):

- **AC-C1** `services/internal/api/client_id_semantics_test.go` が緑(端末 ID / セッション ID の位置づけが契約にある)。
- **AC-C2** §5.3 を openapi.yaml に移したら、`make gen` の差分がコミットに含まれ、再生成しても差分が出ない。

## 却下した案

- **gateway に `DELETE /api/me/data` を1本置いて record / team に fan-out する**: gateway が操作の意味と部分失敗の状態を
  持つことになり、ADR-0202 §3(gateway は `/api/calc` の中の操作を知らない = 転送だけ)を壊す。
  クライアントが2つ呼ぶほうが、再試行が「同じ要求をもう一度」で済む。
- **端末 ID を所有権の証明(事実上のベアラトークン)として扱う**: localStorage / UserDefaults に平文で置き、
  失われたら作り直す値を秘密として扱うことになる。失効・再発行の境界も作れない。公開するなら認証を入れる(§1)。
- **端末 ID のローテーション機能を作る**: 秘密でない値に失効の概念を持ち込むだけで、守れるものが増えない。
- **生の計算イベントを無期限保持**: ユーザー決定に反する。集計の時間減衰から見ても価値がない。
- **構築も90日で失効**: 手間をかけたデータが短命になる実害が大きい。ユーザー決定は「短命にせよ」ではない。
- **イベントごとに `last_accessed_at` を持ち「未使用」を行単位で判定する**: 追記専用の表に更新を持ち込み、
  履歴を開くたびに書き込みが出る(§4)。
- **非同期ジョブ(ジョブ ID + ポーリング)で削除する**: 個人利用の規模に対して状態を持ちすぎる。
  `partial` の繰り返しで同じ結果が得られる(§5.2)。
- **削除を論理削除(`deleted_at`)にする**: 「消して」と言った利用者の期待に反し、バックアップからの消去も達成できない。
- **`api/openapi.yaml` に record / team のパスを今すぐ全部入れる**: §10 の3つの理由。
- **保持期間をコードに定数で埋める**: 環境変数(設定)として渡す。ローカルとクラウドで変えられるようにする
  (coding-rules §2「変更されうる設定」)。既定値はこの ADR の日数で、起動時に検証する(0 以下・未設定は起動エラー)。
