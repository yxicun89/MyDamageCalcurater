## 1. ユーザーが決めたこと(2026-10-04)

| 論点 | 決定 |
|---|---|
| 判定レーン | 今の機能(対戦でどちらが勝つかの判定)はいらない。**目的を作り直す(別途ユーザーが指示)**。それまで Web のタブ・iOS の入口は**非表示**にする(サービス・コードは残す) |
| 調整の目標の選び方 | **相手ポケモンを選び、目標の種類を選ぶ**。種類は「素早さを上回る」「この技を耐える」「この技で倒す」。相手の振りはプリセット(素早さは最速・準速・無振りなど。耐久・火力は無振り・特化など)から選び、数値は内部で決める。目標は複数追加できる。今の「目標の素早さ」の数値入力は詳細設定に残す |
| 見た目 | **ポケモンらしいポップ・カラフル**(タイプ色のカード・丸いボタン・アイコン・やさしい言葉)。使っていて楽しいこと |

### 判定レーンの元の要望(参考。2026-09-22。docs/judge-design.md・docs/ai-shared/decisions/2026-09-22-104-entry.md に記録された1文)

> 「ニトチャ+メイン技で素早さ抜ける+そのポケモンを倒せるか」を1回の入力で確認したい

素早さ比較とダメージ計算が別々の画面だったので、「相手より先に動けて、かつ倒せるか」を1回の入力で確認することが目的だった(ニトロチャージのように、技を使うと自分の素早さが上がる追加効果も踏まえる)。ユーザーのプロンプトの原文そのものは残っておらず、記録は上の1文だけ。

この目的は、調整の目標(F-11 の「素早さを上回る」「この技で倒す」)とほぼ重なる。判定の画面を非表示にしたうえで、**「相手を抜けて、倒せる」を調整の画面の目標として一度に確認できるようにする**ことで、元の要望を満たせる可能性が高い(判定の再設計は、ユーザーの指示を待つ)。

## 2. フィードバックの原文(要約。番号は表で参照)

1. ダメージ計算の使用感・桁の丸め方はよい。
2. メガストーンの表示名が違和感。正式名称(メガリザードンX を選んだらリザードナイトX)で表示してほしい。
3. 攻撃側の SP は、無振り・特化・全振りに加えて、数値入力と性格補正の選択がほしい(入力できないと、その努力値でどれくらいか分からない)。
4. 変化技ではダメージを与えられないので、技の選択肢はダメージを与える技に絞る。
5. 順番は「技を選ぶ → その技に応じた攻撃/特攻を選ぶ(または数値入力と補正選択)→ ダメージ計算」。物理も特殊も使うポケモンで、選んだ技のみの入力だと手間になる。
6. 技の選択肢は五十音順(またはタイプ順)にソートできるとよい。
7. 「この結果は正確でない可能性があります(未対応: 攻撃側の特性「punkrock」)」。未対応の特性に対応する。効果は検索してよい。
8. ニンフィアを選んだら特性が「未選択」しか選べなかった。パンクロックも未対応。特性がまだ完全でない。
9. 素早さ表: 左に素早さ・右にポケモンの形はよい。右のポケモンの素早さは、左の一覧と同じ高さに置いてほしい(選んだポケモンが表のどの位置か視覚的に分かる)。
10. 素早さ表の左側の一覧は、全部を出すと長いので、スクロールに合わせて周辺だけ表示するほうがよい。
11. 判定レーンの今の機能はいらない(目的が違うと思う)。
12. 構築: 構築名はいらない。
13. 構築: Showdown 形式に何を入力すればよいか一目で分からず UX がよくない。6 匹のポケモンを選べて、それぞれが技を選べる形で構築を作れるようにする。使い方が全く分からないので修正。
14. お気に入り: 登録しただけで何もできないなら無駄。クリックするとそのときのダメージ計算がすぐ出せる、などにする。
15. 調整: メガ進化ポケモンを選んだのに、持ち物を選べるのはおかしい。
16. 調整: 自分のポケモンが撃つ技の威力と、残りの耐久調整の配分を最大化するのはよい。ただし「このポケモンのこの技を耐えたい」「このポケモンの素早さまで上回りたい」を数値だけで入れるのは手間。努力値振りを「どのポケモンの何を超えるか」で選べるようにする。
17. verify-m3: Xcode でビルドして Mac で動かすやり方を知らない。手順を教えてほしい。`ios-test` を実行したら、Xcode の iOS で動作確認できる状態までしてほしい。
18. ios-test-ui が長すぎて終わらない(ループしている?)。おおよその時間を知りたい。ずっと「判定(judgement)」の何かをテストしている。`ios-test-ui: 全 76 件 / 成功 75 / 失敗 1`、`TEST INTERRUPTED`、xcodebuild の終了コード 75。
19. 全体の UI・UX が簡素すぎる。ボタンや文字や表に見た目の装飾が無く、機械的で使っていて楽しくない。ビジュアルをよくしたい。
20. 表示する文言が機械的(「〇〇のメガストーン」「観測する」など)。やさしい言葉にしたい。

## 4. 進める順番(推奨)

1. **F-07(判定の非表示)**: すぐできて、iOS の UI テストの時間も減る。
2. **F-12(ビジュアルの基盤)** を先に決め、その上に F-08・F-09・F-02 を載せる(同じ画面を別々に作り直さないため)。
3. **F-04・F-05(特性)と F-10・F-11(調整)** はダメージ計算(ec)レーンが進める。エンジン・データ・契約に関わるので critic を通す。
4. **F-06(素早さ表)**・**F-14・F-15(iOS の導線とテスト)** は並行してよい。
5. **F-13(文言)** は F-12 の後に、画面ごとの作り直しと一緒に行う。

## 5. 共通の規則

- 画面の文言・用語は Web の `i18n/<レーン>.ts` と iOS の Text で**同じ語**にする。
- 見た目の変更で既存のテストの期待値を弱めない。変えるときは理由をコミットメッセージに書く。
- 常時動くアニメーションは入れない(CLAUDE.md)。演出は操作時のみ。「視差効果を減らす」で無効化する。
- 画像は必須にしない(無ければタイプ色エンブレム)。
- 実データ名・公式画像を Git にコミットしない。テストは架空データ。
- 共有ファイルの編集は ADR-0172(plan の区画)・ADR-0805(state・decisions)・ADR-0323(Web の画面レジストリ)・ADR-0507(iOS の機能レジストリ)の規約に従う。
