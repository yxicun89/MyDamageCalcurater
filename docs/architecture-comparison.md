# ソフトウェアアーキテクチャの比較(このプロジェクトでの利点と欠点)

- 更新日: 2026-10-11
- 状態: **ユーザーの判断材料**。採用の決定は ADR に書く。調査の詳細と段階計画は [plan/architecture-adoption.md](plan/architecture-adoption.md)
- 読む人: 「どの形で作るのが、このプロジェクトに合うか」を判断する人間

## このプロジェクトの特徴(比較の前提)

| 特徴 | 内容 |
|---|---|
| 複雑さの場所 | ダメージ計算のルール(`engine/`)。サービスの周りは入出力が中心で薄い |
| 核の性質 | `engine/` は純粋(DB・HTTP・時刻・乱数なし)。ブラウザの WASM でも同じコードを使う |
| 作る人 | AI(Claude Code・Codex)が実装し、人間が確認する。規則は機械で検査できる形が望ましい |
| 並行作業 | 複数のレーンが同時に PR を出す。一斉の構造変更は競合の原因になる |
| 目的 | 学習目的のマイクロサービス構成。個人利用 |

## 比較表

評価は ◎(合う)/ ○(まあ合う)/ △(条件つき)/ ✕(合わない)。

| 方式 | 一言で | 利点(このプロジェクトで) | 欠点(このプロジェクトで) | 適性 |
|---|---|---|---|---|
| **現状維持+明文化** | 今の形を変えず、決まりを書く | 費用ほぼゼロ。競合なし | 名前がなく、人間が確認する基準が弱い | △ |
| **ヘキサゴナル**(ポートとアダプタ) | 核を中心に置き、HTTP や DB は外側の付け替え可能な部品 | 核を守る目的に合う。現状のコード(balance・speed)に近い。向きの検査が単純(外→内のみ)。WASM と相性が良い。AI が規則を守りやすい | ユースケース層の置き方を決める必要がある。小さなサービスでは層が薄くなる | ◎ |
| **クリーンアーキテクチャ** | 同心円の層。依存は内向きだけ。ユースケース層が必須 | 層の役割が最も明確。人間が読みやすい | 層とファイルが増える。小さなサービスには過剰。層ごとの変換コードが増え、AI が手間取りやすい。全レーンの PR が競合しやすい | △ |
| **オニオン** | 同心円でドメインを中心に置く(クリーンに近い) | ドメインを中心に置く考え方が明確 | クリーンと同じ。層の数と決まりが多く、AI が手間取りやすい | △ |
| **レイヤード**(handler / service / repository) | 上から下へ呼ぶ三層 | 馴染みがあり、わかりやすい | 依存が DB 側に向きやすく、核を守る目的とは逆。核が DB の形に引きずられる | ✕ |
| **縦割り**(機能ごとのフォルダ) | 機能単位で全部を持つ | 機能の追加が速い | 計算ルールを共有しにくい。engine が複数機能にまたがる | ✕ |
| **モジュラーモノリス** | 1 つのアプリを内部で分ける | 運用が軽い | 学習目的のマイクロサービスから外れる | ✕ |

## DDD(ドメイン駆動設計)について

- DDD は「ドメインの言葉でモデルを作る」考え方で、**上のどのアーキテクチャの上でも再現できる**。方式の選択と独立している。
- このプロジェクトでは、ドメインの言葉(種族・技・特性・実数値・確定数)がすでに `engine/` と `docs/glossary.md` にそろっている。
- 戦術パターン(集約・リポジトリなど)まで導入するのは過剰。複雑さの場所が engine の計算ルールにあり、永続化の業務ルールが薄いため。

## 判断(ユーザーの理解 2026-10-11)

- ヘキサゴナルを基本にする方向。クリーンとオニオンは、層とルールが多く、AI が実装で手間取りやすい。その分、ヘキサゴナルのほうが開発しやすい。
- この「AI が手間取りやすい」は、層が増えるほど変換コードと決まりが増えるという理由からの判断であり、計測した値ではない。
- ユースケース層は、ヘキサゴナルの中で大きなサービスから段階的に足す(条件や順序は [plan/architecture-adoption.md](plan/architecture-adoption.md))。

## 用語

| 語 | 意味 |
|---|---|
| ポート | 核が外に求める窓口(インターフェース)。例: マスタを取得する |
| アダプタ | ポートの実体。例: HTTP の受け口、DB の読み書き、他のサービスの呼び出し |
| ユースケース層 | 「何をするか」の流れ(検証 → 計算 → 保存 → 通知)を置く層 |
