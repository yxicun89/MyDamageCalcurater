# 判定(素早さ×ダメージ連動) 設計書(判定レーン)

- 更新日: 2026-09-22
- 状態: 起草(ユーザー要望を受けてタイプバランスレーンのセッションが起草。設計の正はこの文書と `docs/adr/0700〜`(判定レーンの帯))
- ユーザーの要望: 「ニトチャ+メイン技で素早さ抜ける+そのポケモンを倒せるか」を1回の入力で確認したい

## 1. 目的

素早さ比較とダメージ計算は別々のサイト・別々の画面で確認する必要があり、「このポケモン(道具・調整込み)は、想定した相手を素早さで抜けて、かつ技で倒せるか」を
一度に確認できない。1回の入力で **抜けるか(素早さ)** と **倒せるか(ダメージ)** を同時に判定する。

**技の追加効果で自分の素早さが上がる場合を考慮する**(ユーザー要望 2026-09-22)。攻撃技には、命中時に追加効果として使用者自身の能力ランクを
変化させるものがある(素早さを1段階上げる等)。これを別々に2回計算(効果発動前の速度判定 → 効果込みの速度判定)しなくて済むように、
1回の request で「技の追加効果を適用した後の実数値」も踏まえた `outspeeds` を返せるようにする(詳細は §4-5)。

## 2. 位置づけ(ユーザー決定: 新しいレーンを作る)

- ダメージ計算(damage-calc)・タイプバランス(balance)・素早さ(speed)と並ぶ4つ目の独立サービス `services/judge/`(ADR-0012 のサービス境界に従う)。
- **判定に必要な計算はどちらも既存の資産で足りる**。判定サービス自身は新しい計算式を持たない(素早さの実数値も、ダメージも、engine が既に持つ)。
  - 実数値(素早さ含む)は `engine.RealStats` を直接呼ぶ(speed-svc・calc-svc と同じやり方。ADR-0600 §3 のこだわりスカーフ ×1.5 の小さな追加ロジックも同様に持つ)。
  - ダメージ・確定数は **calc-svc の公開 API(`POST /api/calc`)をそのまま呼ぶ**(計算式を再実装しない。calc-svc が返す `KOChance` をそのまま使う)。
  - 種族の base stats(素早さ実数値の計算に要る)は **pokedex-svc の公開 API(`GET /api/pokedex/species/{key}`)から引く**(calc-svc が pokedex-svc を呼ぶのと同じ依存の向き。ADR-0012 の「兄弟サービスは互いを呼ばない」に対する例外は、既存の calc→pokedex と同じ前例に倣う)。
  - speed-svc への依存は**作らない**(SP2 がまだ無く、判定レーンが待たされるため。素早さの実数値は自分で計算する)。
- 判定レーン自身が持つのは「抜けるか・倒せるか」を1回の request で返す薄いオーケストレーション層と、その結果の型だけ。

```text
Client (Web/iOS)
  └─ POST /api/judge/v1/outspeed-and-ko
        judge-svc
          ├─ engine.RealStats を直接呼ぶ(自分・相手の実数値。スカーフ ×1.5 は judge が持つ)
          ├─ pokedex-svc の /api/pokedex/species/{key}(自分・相手の種族値)
          └─ calc-svc の /api/calc(技のダメージ・確定数)
```

## 3. 段階実装(既定案。判定レーンの最初のセッションが確定する)

### JD0: 基盤
- ディレクトリ構成(`services/judge/`。balance/speed と同じ形: `api/openapi.yaml`・`cmd/api`・`internal/api`(生成)・`internal/judge`(純粋 Go)・`internal/httpapi`・Kustomize・Argo CD)。
- pokedex-svc・calc-svc への HTTP クライアント(タイムアウト・エラーの正規化)。
- ヘルスチェックのみで疎通を確認する。

### JD1: 抜けるか + 倒せるか(最小構成)
- request: 自分の `Individual`(既存の `api/openapi.yaml` の `Individual` と同じ形を再利用: speciesKey・natureId・sp・abilityId・itemId・ranks)+ 相手の `Individual`(**相手も具体的な調整を入力できる形**。ユーザー回答)+ 使用する技の moveId + field(天候等、任意)。
- response: `outspeeds`(自分が相手より速いか。同速は false 扱いか要検討)、相手への `ko`(calc-svc の `KOChance` をそのまま転記)。
- 「抜ける」の判定は実数値の比較(ランク補正・こだわりスカーフを含む。麻痺などの状態変化は既存の `StatusCondition` を使うなら含めてよいが最初は見送り候補)。

### JD2 以降(未定。着手時にユーザーに確認)
- 複数の相手候補を一度に判定する(TB4 の仮想敵診断のような複数体入力)。
- 素早さ操作技(でんこうそうげき等)・トリックルーム・追い風などの場の効果。
- Web/iOS の画面。
- JD1 では「使用した技自身の追加効果によるランク変化」までを対象にする(§4-5)。相手の技・場の状態変化によるランク変化は JD2 以降。

## 4. 未決事項(判定レーンの最初のセッションが着手前に確認する)

1. 同速(実数値が同じ)の扱い(`outspeeds` を false にするか、`speedTie: true` の3値にするか)。
2. 相手の技(こちらが先制されて落とされる可能性)を判定に含めるか、まずは自分が殴る側だけに絞るか。
3. gateway 経由(`/api/judge/*` を gateway に足す。API レーンへの依頼が要る)か、Web/iOS が直接 judge-svc の Ingress を叩くか(balance と同じやり方)。
4. ADR 番号の帯は `0700〜`(COORDINATION.md に登録済み)。
5. **技の追加効果によるランク変化の扱い**(ユーザー要望 2026-09-22)。エンジンの `DamageInput`/`CalcResult` が追加効果によるランク変化を
   どう表現しているか(現状 calc-svc の公開 API `CalcResult` に追加効果後のランクを返す項目があるか)を確認する。無ければ次のどちらかになる。
   (a) request 側で「技を撃った後の自分のランク」をあらかじめ指定させる(単純だが「一発で計算」の体験が弱まる)。
   (b) engine 側に技の追加効果(自分のランク変化)を返す入力/出力があるか調べ、無ければ ADR-0005(データ駆動の効果定義)に沿ってデータレーンに
       「追加効果の情報(対象・確率・ランク変化量)をマスタに持たせてほしい」と提案する。
   確率的な追加効果(命中率100%でない場合)の扱い(発動時/不発時の両方を返すか、発動前提で計算するか)も合わせて決める。

## 却下した案
- speed-svc を判定レーンが呼ぶ: SP2(自分の実数値算出)がまだ無く、判定レーンが素早さレーンの完了待ちになる。engine を直接呼べば待たずに済む。
- calc-svc に「素早さも一緒に返す」拡張をする: calc-svc の責務(1vs1 ダメージ)を超える。判定レーンが engine を直接呼べば calc-svc の変更は不要。
- Web 画面だけで合成する(新レーンを作らない): ユーザー決定により不採用(新しいレーンを作る)。
