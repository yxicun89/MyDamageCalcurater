# 判定(素早さ×ダメージ連動) 設計書(判定レーン)

- 更新日: 2026-09-23
- 状態: 起草(ユーザー要望を受けてタイプバランスレーンのセッションが起草。設計の正はこの文書と `docs/adr/0700〜`(判定レーンの帯))
- ユーザーの要望: 「ニトチャ+メイン技で素早さ抜ける+そのポケモンを倒せるか」を1回の入力で確認したい

## 1. 目的

素早さ比較とダメージ計算は別々のサイト・別々の画面で確認する必要があり、「このポケモン(道具・調整込み)は、想定した相手を素早さで抜けて、かつ技で倒せるか」を
一度に確認できない。1回の入力で **抜けるか(素早さ)** と **倒せるか(ダメージ)** を同時に判定する。

**技の追加効果で自分の素早さが上がる場合を考慮する**(ユーザー要望 2026-09-22)。攻撃技には、命中時に追加効果として使用者自身の能力ランクを
変化させるものがある(素早さを1段階上げる等)。これを別々に2回計算(効果発動前の速度判定 → 効果込みの速度判定)しなくて済むように、
1回の request で「技の追加効果を適用した後の実数値」も踏まえた `outspeeds` を返せるようにする(詳細は §4-5)。

## 2. 位置づけ(ユーザー決定: 新しいレーンを作る)

- ダメージ計算(damage-calc)・タイプバランス(balance)・素早さ(speed)と並ぶ4つ目の独立サービス `services/judge/`(ADR-0012 のサービス境界に従う)。
- **判定に必要な計算はどちらも既存の資産で足りる**。判定サービス自身は新しい計算式を持たない(素早さの実数値も、ダメージも、engine が既に持つ)。
  - 実数値(素早さ含む)は `engine.RealStats` を直接呼ぶ(speed-svc・calc-svc と同じやり方。ADR-0600 §3 のこだわりスカーフ ×1.5 の小さな追加ロジックも同様に持つ)。
  - ダメージ・確定数は **calc-svc の公開 API(`POST /api/calc`)をそのまま呼ぶ**(計算式を再実装しない。calc-svc が返す `KOChance` をそのまま使う)。
  - 種族の base stats(素早さ実数値の計算に要る)は **pokedex-svc の公開 API(`GET /api/pokedex/species/{key}`)から引く**(calc-svc が pokedex-svc を呼ぶのと同じ依存の向き。ADR-0012 の「兄弟サービスは互いを呼ばない」に対する例外は、既存の calc→pokedex と同じ前例に倣う)。
  - speed-svc への依存は**作らない**(SP2 がまだ無く、判定レーンが待たされるため。素早さの実数値は自分で計算する)。
- 判定レーン自身が持つのは「抜けるか・倒せるか」を1回の request で返す薄いオーケストレーション層と、その結果の型だけ。

```text
Client (Web/iOS)
  └─ POST /api/judge/v1/outspeed-and-ko
        judge-svc
          ├─ engine.RealStats を直接呼ぶ(自分・相手の実数値。スカーフ ×1.5 は judge が持つ)
          ├─ pokedex-svc の /api/pokedex/species/{key}(自分・相手の種族値)
          └─ calc-svc の /api/calc(技のダメージ・確定数)
```

## 3. 段階実装(既定案。判定レーンの最初のセッションが確定する)

### JD0: 基盤
- ディレクトリ構成(`services/judge/`。balance/speed と同じ形: `api/openapi.yaml`・`cmd/api`・`internal/api`(生成)・`internal/judge`(純粋 Go)・`internal/httpapi`・Kustomize・Argo CD)。
- pokedex-svc・calc-svc への HTTP クライアント(タイムアウト・エラーの正規化)。
- ヘルスチェックのみで疎通を確認する。

### JD1: 抜けるか + 倒せるか(最小構成)

決定の正は **ADR-0701**(`POST /api/judge/v1/outspeed-and-ko`。契約は `services/judge/api/openapi.yaml`)。

- request: 自分の `Individual`(speciesKey・natureId・sp・ranks・abilityId・itemId)+ 相手の `Individual`
  (**相手も具体的な調整を入力できる形**。ユーザー回答)+ 使用する技の moveId + format + field(天候等、任意)。
  `status`・`teraType`・`options.critical` は JD1 では受け取らない(ADR-0701 §2・却下した案)。
- response: `outspeeds`(自分が相手より**厳密に**速いか)、`speedTie`(実数値が同じか。§4-1 の決定)、
  `attackerSpeed` / `defenderSpeed`(judge が使った戦闘中の素早さ。ADR-0701 §1)、
  相手への `ko`(calc-svc の `KOChance` をそのまま転記)。
- 「抜ける」の判定は実数値の比較。順序は 実数値(`engine.EffectiveStat`)→ ランク → こだわりスカーフ(×1.5・五捨五超入)
  で、こだわりスカーフの持ち物 ID は既定 `choicescarf`(環境変数 `JUDGE_CHOICE_SCARF_ITEM_ID` で上書き可。ADR-0701 §3)。
  **麻痺などの状態変化は見送り**(ADR-0701 §2 で確定。JD2 で `status` ごと扱う)。
- 性格は `GET /api/pokedex/natures` を 1 リクエストにつき 1 回だけ引いて、自分と相手の両方を解決する(ADR-0701 §4)。
- 上流(natures → attacker の種族 → defender の種族 → calc)は**逐次**で呼ぶ。検査順とエラーの対応表は ADR-0701 §5・§6。

### JD2 以降: 段階と順序(2026-09-22 ユーザー回答で4項目すべてが対象と確定。順序は判定レーンが技術的な依存関係から決めた)

ユーザーは次の4つすべてを対象とすると回答した: (1) 複数の相手候補を一度に判定、(2) 相手の技を含めた返り討ち判定、
(3) 場の効果(トリックルーム・追い風等)、(4) Web/iOS の画面。技の追加効果によるランク変化の自動反映(§4-5 で先送りにした案(b))は、
このユーザー回答で**明示的に対象外**(引き続き request の `ranks` を呼び出し側が指定する形のまま)。

段階分けの根拠: (2) は pokedex-svc に「技を ID 1件で引く」endpoint が無く(`GET /api/pokedex/moves` は日本語名の前方一致検索のみ。
`/api/pokedex/moves/{key}` のような detail endpoint が無い)、技の優先度(`priority`)を judge が取得できない。技の優先度が無いと
「先に動くのはどちらか」を正しく決められないため、(2) は API レーンへの依頼(下記)が要る。(1)(3) は今の1体対1体の endpoint を
拡張するだけで新しい上流依存が無いため、先に進められる。(4) は API の形が (1)〜(3) で変わるので最後にする。

- **JD2: 場の効果(トリックルーム・追い風)。完了(正は ADR-0702。critic PASS)**。
  今の `POST /api/judge/v1/outspeed-and-ko` に、judge だけが解釈する `speedField`
  (`trickRoom`・`attackerTailwind`・`defenderTailwind`。すべて省略可・既定 false)を足す。
  calc-svc は場の効果として weather/terrain/screens しか知らず、トリックルーム・追い風はダメージに関与しない
  (素早さのみ)ため、既存の `field`(calc-svc へ転送する)とは別の欄にし、`speedField` は calc-svc に送らない。
  - **追い風は実数値を ×2 する**(対象側だけ)。`attackerSpeed` / `defenderSpeed` にも現れる。
  - **トリックルームは実数値を変えず、`outspeeds` の比較の向きだけを反転する**(遅い方が先に動く)。
    `outspeeds` の意味は「自分が先に動くか」のまま保つ。`speedTie`(同速)は反転しない。
  - **素早さ補正は 4096 基準で 1 つに連結してから 1 回だけ五捨五超入する**(補正ごとに丸めない)。
    追い風 8192・こだわりスカーフ 6144。出典は @smogon/calc 0.12.0(ADR-0002 が固定した版)の
    `getFinalSpeed`(`chainMods` → `pokeRound` を 1 回)。実数値 91 にスカーフと追い風が両方乗ると 273
    (補正ごとに丸めると 272 になる)。
  - `speedField` を省略した request の応答は JD1 と同一(後方互換)。麻痺(`status`)は JD2 に含めない
    (連結の後に別枠で掛かり、ダメージ側にも効くため。ADR-0702「却下した案」)。
- **JD3: 複数の相手候補を一度に判定。設計確定(正は ADR-0703)**。攻撃側(自分・技)は1つに固定し、
  相手候補(`Individual` の配列)を受け取って候補ごとに JD1+JD2 の判定を配列で返す
  (TB4 の仮想敵診断と同じ「1つに対し複数」の形)。
  - request の `defender`(単数)を **`defenders`(1〜6件の配列)**に置き換える。上限6件は balance の
    `members`/`threats` と同じ「手持ちの数」の慣習で、1リクエストの逐次の上流呼び出し数(2+2N)を読める範囲に抑える。
  - response の単数の5欄を **`matchups`(`defenders` と同じ順序・同じ件数)**に置き換える。各行は
    `defenderIndex`・`outspeeds`・`speedTie`・`attackerSpeed`・`defenderSpeed`・`ko` を持ち、
    `attackerSpeed` が全行で同じでも行を自己完結にする(ルートの `BulkCalcRow` と同じ形)。
  - **既存契約の破壊的変更**だが、JD5(Web/iOS のクライアント)が未着手でクライアントが1つも無いため今は安全
    (ADR-0703 §7。段階分けが意図したとおりの動き)。
  - natures の解決は候補が増えても1リクエスト1回のまま。種族と calc は候補ごとに **index 昇順の逐次**で、
    **最初に失敗した候補で全体を打ち切る**(部分成功は返さない)。message にはどの候補かを `defenders[<index>]` で示す。
  - `field`・`speedField` は1リクエストに1つで、すべての候補に同じように適用される。同じ `speciesKey` の重複除去はしない。
- **JD4: 相手の技を含めた返り討ち判定**。相手の moveId も受け取り、優先度(`priority`)と素早さから先に動く側を決め、
  相手が先に動くなら相手→自分の順で `KOChance` を評価する。**技の優先度を pokedex-svc から個別に引く endpoint が今は無い**
  ため、データ/API レーンへの依頼(`GET /api/pokedex/moves/{key}` のような detail endpoint。DECISIONS.md に既定案を記録する)を
  先に出し、依頼が通るまでは「両者の技は優先度0」という限定つきで進めるか、依頼が通ってから着手するかは、JD3 完了時点で改めて決める。
- **JD5: Web/iOS の画面**。judge-svc を呼ぶ画面。(1)〜(3)(可能なら(4)も)の API が固まってから着手する
  (先に画面を作ると API 変更のたびに作り直しになるため)。担当(判定レーン内で作るか、Web/iOS レーンに依頼するか)は着手時に判断する。

## 4. 決定事項(1〜5 は JD0 で確定。正は ADR-0700。JD1 の決定は ADR-0701、JD2 は ADR-0702、JD3 は ADR-0703)

1. **同速(実数値が同じ)の扱い: 決定** — `outspeeds`(自分が相手より**厳密に**速いか)と `speedTie`(実数値が同じか)を別のフィールドで返す。
   根拠: 同速は「抜けている」でも「抜けられている」でもなく、真偽値1つに丸めると画面で区別できない。同速を真偽に丸めない ADR-0602 の `tie` に倣う。
2. **相手の技を判定に含めるか: 決定** — JD1 は自分が攻撃する側だけを扱う(plan.md の JD1 の記述どおり)。
   根拠: 返り討ち判定には相手の技構成(複数)と行動選択の仮定が要り、JD1 の「1回の入力」を大きくする。JD2 以降で扱う。
3. **gateway 経由か: 決定** — judge も `/api/judge` prefix の自分の Ingress を持つ(balance・speed と同じ)。gateway は変更しない。
   根拠: gateway への追加は API レーンへの依頼になり判定レーンが待たされる。前例が2つあり、クライアントから見た形も変わらない。
4. **ADR 番号の帯: 決定** — `0700〜`(COORDINATION.md に登録済み)。JD0 の基盤は ADR-0700。
5. **技の追加効果によるランク変化の扱い: 決定** — JD1 は request の `Individual.ranks`(既存の型)をそのまま使い、
   呼び出し側が「技を撃った後のランク」を指定する(§3 JD1 の選択肢(a))。
   根拠: engine の `Move`、pokedex-svc・calc-svc の公開 API のいずれにも「技の追加効果(使用者自身のランク変化)」を表すデータが無いことを確認した。
   データ駆動で持たせるにはマスタの新しい欄が要り、データレーンへの新規依頼になる。判定レーンはそれを待たずに JD1 を出せる形を選ぶ。
   「技 ID から自動でランク変化を出す」と、確率的な追加効果(命中率100%でない場合)の扱いは JD2 以降の課題とし、
   マスタへの追加は DECISIONS.md にデータレーンへの提案として記録した(2026-09-22)。

## 却下した案
- speed-svc を判定レーンが呼ぶ: SP2(自分の実数値算出)がまだ無く、判定レーンが素早さレーンの完了待ちになる。engine を直接呼べば待たずに済む。
- calc-svc に「素早さも一緒に返す」拡張をする: calc-svc の責務(1vs1 ダメージ)を超える。判定レーンが engine を直接呼べば calc-svc の変更は不要。
- Web 画面だけで合成する(新レーンを作らない): ユーザー決定により不採用(新しいレーンを作る)。
