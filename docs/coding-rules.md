# コーディング規約(Claude Code / Codex 共通)

Claude Code と Codex は、コードを書く・直す・レビューするときにこの規約に従う。

- 状態: v2(Claude Code が起草。Codex の1回目レビュー「要修正」を反映し、2回目レビューは「条件付き承認」。その条件2点を反映済みで、反映後の Codex の再確認は行っていない。経緯は `docs/ai-shared/DECISIONS.md`)
- 目的は3つ: (1) **いつでも GitHub に公開できる状態を保つ** (2) **人が読みやすいコードにする** (3) **データや設定をコードに埋め込まない**

## 0. 文書の優先順位

| 文書 | 担当 |
|---|---|
| [CLAUDE.md](../CLAUDE.md) | 絶対ルール・ドメイン規約・技術規約(プロジェクトの正) |
| [AGENTS.md](../AGENTS.md) | Git・役割分担・共有状態・検証の共通運用 |
| 採用済みの `docs/adr/` | 個別の設計判断(この規約の一般則より優先する、限定的な例外) |
| この文書 | コードの書き方の一般作法 |

採用済みの ADR が**明示している例外**は、矛盾ではない(この規約の一般則に対する限定的な例外として従う)。
同じ事柄について文書間で異なる定めがあり、上の優先順位でも決まらないときは、作業を止めて文書を同期する(どちらが正かを `docs/ai-shared/DECISIONS.md` に書く)。
運用(ブランチ・検証範囲・ログ)は AGENTS.md を参照し、ここでは繰り返さない。レビューだけ・書き込み禁止の依頼では、ログ更新は不要。

## 1. 公開できる状態を常に保つ

リポジトリは、今この瞬間に公開しても問題がない状態にしておく。「あとで消す」は許さない。

- **コミットしない**: 秘密情報(トークン・パスワード・鍵)、個人情報(メールアドレス・端末名・ローカルの絶対パス)、`.env`(サンプルは `.env.example` だけ)、個人用メモ(`docs/local/` は .gitignore)、生成物・バイナリ(`engine.wasm` など)。
- **第三者由来のデータ・画像はコミットしない**(実マスタ・生成済みスナップショット・公式画像。ADR-0002)。テストの fixture は架空データか、数値と識別子だけの最小限にする。
  例外は ADR に理由を書く(現在は `testdata/golden` だけ。ADR-0002 §追加の回答)。適法性の判断はコードを書く側が断定しない。迷ったらコミットしない。
- 生成コード(`*.gen.go` など)は仕様(`api/openapi.yaml`)から作り、手で編集しない。再生成して差分が出ない状態を保つ。
- コメント・ログ・コミットメッセージ・ドキュメントに、個人情報や内輪の事情を書かない。
- 依存を足すときは、ライセンスが公開に問題ないことを確認し、理由を書く。バージョンは固定する(例: oracle の `@smogon/calc` は完全固定)。
- **Go の module path に GitHub のアカウント名などの個人を特定する名前を入れない**。公開用のプレースホルダ(`example.com/pokecalc/...`)を使う(ユーザー決定。実装は plan.md の R-2-8)。
- Git の作者名・メールも公開用の名前を使う(履歴の書き換えは plan.md の R-2-9)。以後のコミットは、このリポジトリのローカル設定の公開用 identity で行う。
- 公開前に確認する: README の記載、Git の作者情報、第三者コンテンツの出所の記録。**LICENSE は現時点で置かない**(個人で使う前提。法的に面倒なものを含む状態では公開しない。公開するときに、含めないと確認できた範囲で決める)。
- **`make check-publishable`**(絶対パス・個人情報・秘密らしき文字列・追跡禁止ファイル・第三者データの検査。`make lint` から呼ばれる)を通す。公開・push の前は `make check-publishable-full`(Git の作者情報・生成コードの差分も検査)。検査を変えたら `make check-publishable-selftest`。検査は値を出力せず、ファイル:行と種類だけを表示する。
- 秘密が漏れたら、まず失効(ローテーション)し、その後に履歴の除去を検討する。

## 2. ハードコードしない

- **マスタ(ポケモン・技・持ち物・特性)とレギュレーション(v1 は M-C)をコードに埋め込まない**。データ(マスタ・設定・ファイル)から引く。
- 「変更されうる設定」(URL・ポート・DB 接続先・認証情報・レギュレーション)と「プロトコル・ドメインの定数」(Lv50・個体値31・SP 上限32・合計66・4096 基準)を区別する。
  - 設定は環境変数などで渡し、型付きの設定として**1か所で読み込み**、必須値は起動時に検証する。ローカルとクラウドの差は Kustomize overlay で吸収する。
  - ドメイン定数は、**所有するモジュールの1か所**に名前を付けて集約し、出典(ADR)を書く。散在させない。
- マジックナンバー・マジック文字列は名前付き定数にし、**なぜその値か**を示す。表示文言は各クライアントの文言資源に、エラーコードは OpenAPI を正として1か所に定義する。
- 同じ定義を複数箇所に書かない。**単一の正(1か所)を決め、他はそれを参照する**。
  - 例外: 独立した検証(テストの期待値、外部 oracle との照合、ADR で認めた意図的な重複)は、実装の写しにせず独立に書く。その場合は根拠を示し、同期を検査するテストを置く(例: ADR-0009 のカタログとゴールデンの名前一致)。
- 「入力の作り方の型」(防御プリセットの SP 配分など)はマスタではないので engine が持ってよい。定義は1か所に集め、ADR に理由を書く(ADR-0009)。
- **ゲームの版やレギュレーションで変わりうる「表・一覧」(タイプ相性表を含む)はデータとして渡し、計算の「手順・式」はコードに置く**(ADR-0012)。迷ったら変数化(データ化)する。

## 3. 人が読みやすいコードにする

- **名前で意図を伝える**。略語を避け、ゲーム用語は `docs/requirements.md` と同じ言葉を使う。1文字の変数は、ごく狭いスコープの添字だけ。
- **関数は1つの責務**。長さ(目安 50 行)・ネスト(目安 3 段)・ファイル(目安 500 行)は**失敗条件ではなく、見直しのきっかけ**。
  超えたら分けられないか考える。生成コード・テストの表・宣言的なデータは対象外。
- **コメントは「なぜ」を書く**。何をしているかはコードで読めるようにする。設計判断・丸め順の根拠は ADR を参照する。
  コメントアウトしたコード・意味のない TODO を残さない(残すなら plan.md のタスク ID を付ける)。
- 公開する API(Go の exported 識別子、TS の export)には、使い方が分かる doc コメントを付ける。
- 整数で表せるものは整数で扱う(ダメージ・確定数の丸め順は ADR-0004/0008)。float でダメージを近似しない。**例外**: 表示用の確率は ADR-0006 のとおり float でよい。
- 抽象化は、変更の理由と結合度で判断する。「たまたま似ている」だけで共通化しない。使われていない汎用機構・設定項目を作らない。
- エラーは握りつぶさず、原因が分かる文脈を付けて返す。**検証は責務ごとに置く**: 構文・DTO の検証は境界(API・WASM)、ドメインの不変条件はそれを所有するパッケージ(engine など)。

## 4. 言語・領域ごとの規則

### Go
- `gofmt` / `go vet` / `go test` / `go build`(`make lint` `make test` `make build`)を通す。共有状態を持つ変更は `go test -race` も。
- エラーは `%w` で文脈を付けて包み、判別が要る失敗は sentinel(`errors.Is`)にする。可変のグローバル変数を避ける。
- 新しく書く I/O 関数(サービス・importer など)は `context` とタイムアウトを受け取る。標準インターフェースの実装など、シグネチャを変えられない場合は除く(engine は I/O を持たない)。生成コードはリンタの対象外。

### TypeScript(Web)
- `strict`。`any`・非 null 断言は原則禁止(必要なら理由をコメント)。判別 union は網羅性を検査する。
- API の型は OpenAPI からの生成型を正とし、手書きで複製しない。`tsc --noEmit` と formatter/lint を通す。
- 依存は完全固定し lockfile をコミットする。`VITE_*` など公開される環境変数に秘密を置かない。

### Swift(iOS)
- 本番コードで `!` / `try!` を使わない。並行性は `MainActor` / `Sendable` の境界を意識する。
- 生成された API 型を手編集しない。秘密はソース・plist に置かず Keychain 等を使う。XCTest を通す。

### シェル
- Bash は `set -euo pipefail`、変数展開は引用する。一時ファイルは `mktemp` と `trap` で片付ける。
- `curl | sh` を書かない。取得物は版とチェックサムを固定する。`rm` の対象が空値・広域パスにならないよう検査する。

### k8s / Kustomize
- 全 overlay が `kustomize build` できること。Secret の実値をコミットしない。イメージは不変な参照(タグ固定またはダイジェスト)にする。
- requests/limits・probe を付け、非 root・最小権限・標準 labels を基本とする。

## 5. テスト

- 原則テーブル駆動。テスト名は仕様を表し、期待値の根拠(式・外部ソース・ADR)をコメントで示す。
- テストを消したり、期待値・しきい値・シード・ケース数を弱めたりして通さない。期待値を変える理由はコミットメッセージに書く(CLAUDE.md 絶対ルール6)。
- 前提が足りないテストを黙ってスキップしない(必須の検証は明示的に失敗させる)。任意の統合テストは、スキップした事実を報告する。
- 重要な仕様(計算・丸め・契約)は、実装を壊して(変異)テストが赤になることを確認する。全テストに要求はしない。
- 検証の範囲は変更に応じて選ぶ(AGENTS.md)。計算ロジックを変えたら `make test-golden`、WASM 境界を変えたら `make test-wasm`。

## 6. レビューの観点(critic / Codex 共通)

1. 公開できる状態か(秘密・個人情報・絶対パス・第三者データ・生成物の混入)
2. ハードコードが無いか(マスタ・レギュレーション・設定・マジックナンバー・重複定義)
3. 読みやすいか(名前・責務・ネスト・「なぜ」のコメント・doc コメント)
4. 絶対ルール(CLAUDE.md)と ADR に従っているか。新しい設計判断に ADR があるか
5. テストは仕様を表し、弱められていないか

## 7. 運用

- **新しいコード・変更したコードに適用する**。既存コードの是正は plan.md の Phase R(R-1 監査 → R-2 是正)で、**挙動を変えずに**行う。
- 規約から外れる必要があるときは、その場で理由をコメントか ADR に書く。黙って外れない。
- この規約を変えるときは `docs/ai-shared/DECISIONS.md` に追記し、Claude Code と Codex の両方が確認する。
- 規約が求める作業が、その AI の担当外のモジュールにあるときは、直接編集せず `DECISIONS.md` に提案を書く(AGENTS.md の共有ファイル編集規約)。
