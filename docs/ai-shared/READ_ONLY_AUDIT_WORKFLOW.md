# 読み取り専用の継続監査ワークフロー

## 目的

実装レーンと並行して、コード・文書を変更せずにプロジェクト全体を調査し、実装担当が追加確認なしで着手できる GitHub Issue を作る。
継続監査はレーンを占有せず、`CURRENT_STATE.md` の `Active`・ブランチ・ログを更新しない。

## 変更しないもの

- リポジトリ内のファイル、Git の index・commit・branch・PR
- `docs/ai-shared/CURRENT_STATE.md`・`DECISIONS.md`・各 AI のログ
- 実装中レーンの worktree と、そこにある未コミット・未追跡ファイル

調査対象は最新の `origin/main` とする。テストやビルドが必要なら一時 worktree とリポジトリ外のキャッシュを使い、終了時に削除する。

## 監査を回す順序

次の観点を上から1周し、GitHub の `[監査運用] 継続監査カーソル` Issue に記録された次の観点から再開する。

1. プロダクト要件、主要ユーザーフロー、UI/UX、アクセシビリティ
2. ドメイン計算、境界値、エラー処理、並行処理、API・型・サービス境界
3. データ品質、更新、バックアップ、第三者データ、プライバシー
4. セキュリティ、秘密管理、権限、依存・サプライチェーン
5. 可用性、障害時動作、監視、SLO、復旧手順
6. 性能、キャッシュ、容量、スケーラビリティ
7. クラウド選定、費用、マネージドサービス、移行性、ベンダーロックイン
8. テストの空振り、CI/CD、GitOps、開発者体験、文書・手順書
9. 既存 Issue の重複、依存関係、優先順位、完了条件の不足

最新情報、価格、クラウド仕様、法令、依存バージョンは公式の一次情報を調べる。推測と確認済みの事実を分ける。

## 1回の調査手順

1. 実装レーンではない調整用リポジトリで `git status --short --branch`・`git diff`・`git diff --cached` を取得し、開始時の状態を記録する。
2. そのリポジトリで `git fetch origin` し、`mktemp -d` で監査専用の一時ルートを1つ作る。その直下に `origin/main` の detached worktree、ログ、Go・npm等のtask-specific cacheを置く。調査コマンドにはこのキャッシュを明示し、OSや他セッションの共有キャッシュを使わない。
3. `gh label list --limit 1000` で `bug`・`improvement`・`documentation`・`ready-for-implementation`・`needs-decision` の存在を確認する。5ラベルは初期セットアップで作成済みとし、欠けていれば Issue を作らず運用破損として報告する。継続監査が独断でラベルを作り直さない。
4. `gh issue list --state all --limit 1000` で既存 Issue を取得し、固定タイトル `[監査運用] 継続監査カーソル` を探す。無い場合だけ、同じ一覧で重複が無いことを確認し、`gh issue create --title "[監査運用] 継続監査カーソル" --body ... --label documentation` で作る。`--body` は次の固定形式の本文を引数へ直接渡し、一時ファイルを使わない。

   ```markdown
   ## Cursor
   - next: 1. プロダクト要件、主要ユーザーフロー、UI/UX、アクセシビリティ
   - checkedAt: 未実施
   - baseCommit: 未実施

   ## Completed
   - なし
   ```

   存在する場合は一覧からIssue番号を解決し、本文の `next` から再開する。
5. 監査観点を1つ選び、要件・ADR・実装・テストを照合する。
6. 再現できる問題、または選択肢と判断基準を示せる改善だけを候補にする。
7. 同じ原因・同じ完了条件の候補は1件にまとめ、別レーン・別リリースで直すものは分ける。
8. Issue 作成の直前に `gh issue list --state all --limit 1000` を再実行し、候補のタイトル・原因となる識別子・変更対象ファイルでも検索する。重複があれば新規作成しない。
9. Issue は `gh issue create --title ... --body ... --label "<bug または improvement>" --label "<ready-for-implementation または needs-decision>"` の形で、`--title`・`--body` を直接渡す。一時ファイルを使わない。
10. 監査カーソルIssueの番号と本文を `gh issue view` で取得する。固定形式を保ったまま、`Cursor` の `next`・確認日・基準にした `origin/main` のcommitを更新し、`Completed` に `観点: 確認日 @ commit — Issue番号または問題なし` を1行追記する。更新は `gh issue edit <番号> --body ...` へ本文を直接渡し、一時ファイルを使わない。
11. 一時 worktreeを `git worktree remove` で外し、手順2で作成してパスを検証済みの監査専用一時ルートだけを削除する。共有キャッシュや親ディレクトリは削除しない。
12. 調整用リポジトリの `git status --short --branch`・`git diff`・`git diff --cached` が開始時と一致し、一時 worktreeと一時ディレクトリが存在しないことを確認する。

## 実装担当へ渡せる Issue の条件

Issue 本文に次をすべて書く。情報が不足する間は Issue を作らず、調査を続ける。

- **担当レーン**: 変更を所有するレーン。複数なら主担当を先に書く
- **達成する結果**: 実装方式ではなく、利用者・運用者から見た完了状態
- **根拠**: 実在する相対ファイル名と行番号。外部情報は公式ページのURLと確認日
- **再現・確認手順**: 上から実行でき、現在の失敗または不足が分かる手順
- **受け入れ条件**: 正常系、境界値、異常系、回帰テスト、必要な生成差分
- **変更範囲 / 対象外**: 触ってよいレーンと、今回変更しないもの
- **依存関係**: 先に必要なIssue・PR・データ・人間の操作
- **検証コマンド**: 実装担当が完了時に実行する具体的なコマンドと成功条件
- **既定案**: 複数案がある場合の推奨案と、そのトレードオフ

Issue には第三者データ、個人情報、秘密情報、ローカルの絶対パスを載せない。テスト出力は必要なエラー要旨だけを相対パスで記述し、トークン・接続文字列・環境固有値を転記しない。

取り消しやすく、既存ADR・要件から一意に決まる事項は既定案まで書き、再確認を求めない。
費用契約、公開、データ削除、秘密・権限、法的判断など取り消しにくい選択だけを `人間の判断が必要` と明記する。

## ラベル

- 再現できる誤動作: `bug`
- 品質・運用・設計・UXの改善: `improvement`
- そのまま実装可能: `ready-for-implementation`
- 人間の選択が必要: `needs-decision`（`ready-for-implementation` と同時に付けない）

`ready-for-implementation` は「追加の仕様確認が不要」という意味だけで、着手順を変更しない。実装担当は `docs/plan.md` と `CURRENT_STATE.md` の `Next`、レーンの占有・ブランチ規約、`docs/development-workflow.md` の通常手順に従う。進行中のM1タスクへ監査Issueを割り込ませない。
