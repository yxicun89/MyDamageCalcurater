## 2026-10-11: 画面の行き来(ナビゲーション)の案 A/B/C。iOS と Web をそろえる(**案 B 採用**。ユーザー決定 2026-10-11)
Decision: **案 B を採用(ユーザー決定 2026-10-11。ユーザーは「B か F」と回答。のちに訂正: F の右下の丸ボタンは画面間の移動用ではなく『その機能の中の操作用(画面ごとの主操作)』の意味だった。したがって画面間の移動は下部タブ 4 だけにし、『最近使った画面』を出す丸ボタンは作らない。主操作用のボタンは今は実装しない)。** ユーザー要望「iOS を開くと全機能のボタンが並び、機能を移るたびにホームへ戻るのが面倒。上部のバーや下部のタブで移りやすくしてほしい」への案を 3 つ出す。
推奨は **案 B「関連画面をまとめた 4 つの下部タブ」**: ダメージ(計算・逆算・調整を上部の区切りボタンで切り替え)・構築(タイプバランス込み。ADR-0421)・素早さ・記録(お気に入り・履歴)。「このアプリについて」は各タブ右上のアイコン。Web も同じ 4 区分にし、狭い幅は下部固定、広い幅は今の上部タブのまま。
案 B に決まったので、ADR を 1 件起こし(iOS・Web 共通)、iOS レーン・Web レーンに実装を割り振る。
Reason: 今の iOS は「ホームに全機能を並べ、押して先へ積む」作り(ハブ型)。NN/g はハブ型を「利用者が 1 回の利用で 1 つの枝しか使わないときに向く」とし、毎回ハブへ戻る手間を短所に挙げる。このアプリは計算→逆算→構築→計算と行き来する使い方なので合わない。加えて iOS は戻ると画面の入力が消える(下記「現状」)。
Impact: iOS(`RootView`・`FeatureRegistry`・各 `*Feature` の入口・UI テスト)、Web(`App.tsx` のタブ列・`app/screens.tsx` の登録・`docs/design.md` の「タブは下の固定ナビにしない」の行)。API・engine の変更なし。このファイルを書いた時点ではコードを変えていない。

### 現状(2026-10-11 の origin/main)
- iOS(`ios/PokeCalc/RootView.swift`): 1 つの `NavigationStack`。ホームに `FeatureEntry.rootButton` のピルが縦に並ぶ(計算する・逆算する・構築・調整・タイプバランス・素早さ・お気に入り/履歴。判定は `FeatureVisibility` で非表示)。「このアプリについて」は右上の `toolbarIcon`。機能を移るには必ず戻る→別のピル。
- **iOS は戻ると入力が消える**: 各画面は `CalcScreenView` などが `@State private var viewModel` を持ち、`navigationDestination` で積まれる。戻る(pop)と画面ごと破棄され、次に開くと初期状態。Web は ADR-0308 で「訪れたタブは mount したまま hidden」にして入力を保っており、iOS だけ劣る。
- Web(`web/src/App.tsx`): 上部の横並びタブ(`role="tablist"`。計算・逆算・タイプバランス・素早さ・構築・お気に入り・調整の 7 つ。判定は `hidden`)。320〜375px ではタブ列だけ横スクロール(issue #333)。`docs/design.md` は「画面が 5 つを超えるので下の固定ナビにはしない」。「このアプリについて」はフッターの文字リンク(ADR-0314)。
- タイプバランスは構築編集に統合が決定済み(ADR-0421。`origin/docs/tb-balance-in-team-builder`)。統合後の画面は 計算・逆算・調整・構築・素早さ・お気に入り/履歴 の 6 つ + このアプリについて。
- 対象 iOS は 27(`IPHONEOS_DEPLOYMENT_TARGET = 27.0`)なので、SwiftUI の `Tab` / `TabSection` / `.sidebarAdaptable` はすべて使える。

### 調査で得た根拠
| 根拠 | 要点 | URL |
|---|---|---|
| Apple HIG Tab bars | タブバーは区画の移動用で、操作には使わない。「各区画の中の移動状態を保ったまま切り替えられる」。「タブは少ないほど移りやすい」。**「その他(More)タブは避ける。隠れたタブの中身は届きにくく気づかれにくい」**。区画を移ってもタブバーは見せたままにする(モーダルは例外) | https://developer.apple.com/design/human-interface-guidelines/tab-bars |
| Apple HIG Segmented controls | 「近い関係の下位画面の切り替えには区切りボタン。まったく別の区画の切り替えにはタブバー」。iPhone では 5 個まで | https://developer.apple.com/design/human-interface-guidelines/segmented-controls |
| SwiftUI TabView | `Tab` で宣言、`TabView(selection:)` で選択を外から変えられる。`.sidebarAdaptable` + `TabSection` で iPad はサイドバーにも | https://developer.apple.com/documentation/swiftui/tabview |
| Material 3 Navigation bar | 下部のナビは **3〜5 個**。5 個を超えるなら使わない(重なり・翻訳文が収まらない) | https://m3.material.io/components/navigation-bar/guidelines |
| Material 3 Navigation rail | 中〜大の幅は縦のレールで 3〜7 個 | https://m3.material.io/components/navigation-rail/guidelines |
| NN/g Hamburger menus | 隠したナビ(ハンバーガー・ドロワー)は見せたナビより**発見性が 20% 超低い**、モバイルで約 15% 遅い。「上位の項目が 4 つ以下なら見せて並べる」 | https://www.nngroup.com/articles/hamburger-menus/ |
| NN/g Mobile navigation patterns | タブバーは項目が少ないとき向き(5 を超えると収まらない)。ハブ型は「毎回ハブへ戻る」必要があり、1 回の利用で 1 枝しか使わない作業向き | https://www.nngroup.com/articles/mobile-navigation-patterns/ |
| Hoober(2013) | 片手・親指操作が 49%。下部は親指で届きやすい | https://www.uxmatters.com/mt/archives/2013/02/how-do-users-really-hold-mobile-devices.php |
| Hoober(2017) | 「親指ゾーン」を鵜呑みにしない: 人は画面中央を最も正確に押し、端・角は大きい的(約 12mm)が要る。左上の戻るも普通に使われる | https://www.uxmatters.com/mt/archives/2017/03/design-for-fingers-touch-and-people-part-1.php |

読み取り: 下部の常設ナビは「片手で届く」以上に「**常に見えていて 1 回で移れる**」ことが効く(NN/g の発見性の差)。ただし数は 4〜5 まで、More は避ける(HIG・M3)。項目が多いなら、近い関係のものを区切りボタンでまとめて上位の数を減らすのが HIG の作法。下部ナビの的は端にあるので小さくしない(Hoober 2017)。

### 検討して外したもの
- **ドロワー/ハンバーガー(左上)**: 発見性の低下(NN/g)、左上は片手で遠い。6 項目なら見せて並べられる量。
- **最近使った順・頻度順のホーム**: 並びが変わると位置で覚えられない。ハブへ戻る手間は残る。
- **検索/コマンド(HIG の検索タブ)**: 機能は 6 つしかなく、探すより並べるほうが速い。ポケモン・技の検索は各画面のピッカーにある。
- **左右スワイプでの画面送り(`.page` 型)**: 画面内の横スクロール(タブ列・表)や iOS の戻るスワイプと衝突。気づかれにくい。

### 案 A: 下部タブ 5 つ + 「その他」
- 概要: 計算・逆算・構築・素早さ・その他。その他の中に 調整・お気に入り/履歴・このアプリについて の一覧。
- iOS: `RootView` を `TabView(selection:)` に置き換え、タブごとに `NavigationStack` を持つ(構築一覧→編集の積みはタブの中)。`FeatureEntry` に `.tab` と `.more` を足し、`FeatureRegistry` から組む(ADR-0507「画面を足すとき RootView を編集しない」を保つ)。起動時に開く画面(`openAtLaunchEnvironmentKey`)は選択タブの切り替えに置き換え。コスト: 中(RootView 書き換え + UI テストの入口の約 54 か所を「タブを押す」へ)。
- Web: 5 つを下部固定(狭い幅)にし、残りは「その他」のシート。コスト: 中。
- 良い点: 計算・逆算・構築・素早さが 1 回で移れる。画面の中身はそのまま。
- 悪い点: HIG が避けよという More そのもの。調整・お気に入りが 2 回押しになり見えない(発見性の低下は NN/g の数字の通り)。「どれを その他 に入れるか」の線引きに根拠が薄い。
- 状態保持: iOS の `TabView` は各タブの画面を保持するので、タブ間の往復で入力が残る(HIG の「区画の移動状態を保つ」)。その他の中の画面は、戻ると消えないよう その他 タブ自身の `NavigationStack` に積む。
- アクセシビリティ: システムのタブバーは VoiceOver で「タブ、1/5」と読まれ、Dynamic Type の大きい文字では長押しで拡大表示(Large Content Viewer)が出る。

### 案 B(推奨): 関連画面をまとめた 4 タブ(ダメージ・構築・素早さ・記録)
- 概要: 下部タブ 4 つ。
  - **ダメージ**: 上部に区切りボタン「計算 / 逆算 / 調整」(3 つとも攻撃側・防御側・技を入力してダメージを扱う近い関係)。
  - **構築**: 一覧→編集。編集の中にタイプバランス(ADR-0421)。
  - **素早さ**: 素早さの表。
  - **記録**: お気に入り・計算履歴(今の お気に入り/履歴 画面)。行を押すと**ダメージタブの計算へ移して入力を復元**する(今は同じスタックに計算画面を新しく積んでいる。`FavoritesScreenView` の `restoreTarget`)。
  - **このアプリについて**: 各タブ右上のアイコン(今と同じ位置。設定エラー時も出す)。判定は非表示のまま(再表示するなら ダメージ か 素早さ の区切りに足す)。
- 根拠: 上位 4 つは M3 の 3〜5、NN/g の「4 つ以下は見せて並べる」に収まり、More が要らない(HIG)。近い関係の切り替えは区切りボタン(HIG Segmented controls、iPhone 5 個まで)。
- iOS の見通し: `TabView(selection:)` + タブごとの `NavigationStack`。ダメージタブの中は 3 画面を**訪れたものだけ作って保持**し(Web の ADR-0308 と同じ考え。非選択は `opacity(0)` + `accessibilityHidden(true)`、または ViewModel をタブの親で持つ)、区切りボタンで切り替えても入力が消えないようにする。`FeatureEntry` を「タブ / タブ内の区切り / ツールバー」に分け、`FeatureRegistry` から組む(RootView を画面追加で編集しない方針を保つ)。区切りボタンは既存の `PopSegmented` 系の部品があればそれ、無ければシステムの `Picker(.segmented)`。コスト: 中〜大(案 A + ダメージタブの保持の仕組み + 記録→計算の受け渡し)。
- Web の見通し: タブの定義を 4 つの区分 + 区分内の区切りにする(`defineScreen` に `group` を足す)。URL は `/calc` `/reverse` `/adjust` を残し、区分内の区切りに対応させる(直接開ける・戻る/進むは ADR-0300 §1 のまま)。**狭い幅(目安 600px 未満)は 4 つを下部固定、広い幅は今の上部タブ**。4 つなら 320px でも横スクロールなしで収まり、issue #333 の例外も不要になる。下部固定はセーフエリア(`env(safe-area-inset-bottom)`)と、本文の下余白(固定バーに隠れない)、入力中にソフトキーボードと重ならないことの確認が要る。`docs/design.md` の「下の固定ナビにはしない」の行を改める。コスト: 中。
- 良い点: 6 画面すべてが 1〜2 回の押下で、しかも**常に見える場所**にある(逆算・調整は区切りボタンのラベルとして見えている)。入力は全画面で保持。iOS と Web で同じ区分・同じ語。構築にバランスが入る ADR-0421 と整合。
- 悪い点: 逆算・調整へは「ダメージ→区切り」で、案 A より 1 回多い場合がある(ダメージタブにいれば 1 回)。区切りボタンは画面上部なので片手では遠い(ただし頻繁に押すのはタブのほうで、区切りは画面の中の入力と同じ高さ帯。Hoober 2017 の通り上部も使われる)。区分の作り直しなので、案 A より設計判断が多い。
- 状態保持: タブ間(iOS の TabView の保持)・区分内(訪れたものを保持)の両方で入力が残る。iOS で今起きている「戻ると消える」が解消。
- アクセシビリティ: タブはシステムの読み上げ・拡大表示に任せる。区切りボタンは 2 文字のラベル 3 つなので AX5 でも折り返さずに収まる見込み(要実機確認。収まらなければ縦に積む)。タップの的はタブ 49pt・区切りボタンは 36pt 以上を守る。Web の区切りは既存の `SegmentedControl`(radiogroup の作法)。
- テスト ID: iOS の入口 ID(`openCalcScreen` など)を各タブ/区切りに付け直し、UI テストは「ID を押す」ままにする(SwiftUI の `Tab` に付けた ID がタブバーのボタンへ伝わるかは要検証。伝わらなければ UI テストに `open(feature:)` の補助を 1 つ作り、各テストはそれを呼ぶ)。`POKECALC_OPEN_*_AT_LAUNCH` の環境変数は残し、意味を「そのタブ/区切りを選んで起動」に変える。Web は `role="tab"` を使うテストが 21 ファイルあるため、上部・下部とも同じタブ部品(tablist の作法)を使い、見た目だけ幅で変える。

### 案 C: 今の作りを残し、上部から移れるようにする(最小の変更)
- 概要: ホーム(ピルの一覧)は残す。各画面のナビバー中央の画面名を押すとメニュー(他の機能の一覧)が出て、そこから直接移る。あわせて iOS の ViewModel を `RootView` 側で持ち、戻っても入力が消えないようにする。
- iOS: 画面名のメニュー(`ToolbarTitleMenu` 相当)を共通の部品にし、`path` を「積む」ではなく「置き換える」で移る。ViewModel の持ち主を画面から `RootView`(または画面ごとの保持役)へ移す。コスト: 小〜中。
- Web: 今の上部タブのまま(横スクロールも残る)。変更なし〜小。
- 良い点: 変更が小さい。UI テストの入口 ID はそのまま。
- 悪い点: 移動の口がメニューの中に隠れる(NN/g の隠したナビの短所。気づかれにくい)。画面上部中央で片手では遠い。ホームとの二重の入口。要望の「ホームへ戻らずに移りたい」には応えるが、「最初に全ボタンが並ぶ」は残る。
- 状態保持: ViewModel を外へ出せば残る(この案は ViewModel の移し替えが必須)。
- アクセシビリティ: メニューはシステム標準なので VoiceOver・Dynamic Type に対応。ただし画面名がボタンだと気づける手掛かり(▼ の印)が要る。

### 比べた結果
| 観点 | 案 A | 案 B | 案 C |
|---|---|---|---|
| 1 回で移れる画面 | 4 / 6 | 4 区分(区分内は区切りで +1) | 0(メニューを開いて +1) |
| 全機能が常に見える | いいえ(その他に隠れる) | はい | いいえ |
| 入力の保持 | タブ間は残る | 全画面で残る | ViewModel を移せば残る |
| HIG・M3 との整合 | More を避けよに反する | 整合 | ナビをメニューに隠す |
| iOS のコスト | 中 | 中〜大 | 小〜中 |
| Web のコスト | 中 | 中 | なし〜小 |
| iOS と Web の一致 | 下部の 5 + その他でそろう | 4 区分でそろう | Web は今のまま(差が残る) |

### 推奨とその理由
**案 B**。理由: (1) 要望の「ホームへ戻らずに移る」を、全機能が常に見える形で満たす唯一の案(案 A は More で 2 画面を隠し、案 C はメニューに隠す。NN/g の発見性の差)。(2) 上位 4 つは HIG・M3・NN/g の推奨の範囲に収まり、More を使わない。(3) 計算・逆算・調整は近い関係なので、HIG の区切りボタンの用途にそのまま当たる。(4) iOS の「戻ると入力が消える」を構造ごと解消し、Web の ADR-0308 と同じ「訪れた画面は保持」にそろう。(5) Web は 4 つなら狭い幅で下部固定にでき、issue #333 の横スクロールの例外も不要になる。
進め方の案: ① ADR(ナビの区分・保持・テスト ID の方針)→ ② iOS: TabView 化と入口 ID の付け替え(UI テストを先に直す)→ ③ iOS: ダメージタブの区切りと保持 → ④ 記録→計算の受け渡し → ⑤ Web: 区分と下部固定。タイプバランスの構築統合(ADR-0421)と同時期になるので、構築タブの中身はそちらに合わせる。
常時動くアニメーションは入れない(タブ・区切りの切り替えは操作時の押下の反応だけ。iOS 26 以降のタブバーのスクロール時の縮小は使わない)。
